RAG 와 벡터 검색 기초
— 임베딩, 코사인 거리, pgvector

이론 RAG 임베딩 벡터 검색 pgvector LLM 2026.10.28

회사 백엔드에서 요즘 자주 붙는 기술이 RAG 다. "우리 회사 문서를 읽고 답하는 챗봇" 같은 걸 만들 때 쓴다. 이름은 어렵지만 생각은 단순하다. LLM 에게 묻기 전에, 관련 있는 문서를 먼저 찾아서 질문에 붙여 준다. 이 글은 그 "찾기"가 어떻게 도는지를 처음부터 본다.

왜 필요한가 — 오픈북 시험

LLM 은 학습할 때 본 글로만 답한다. 그래서 세 가지를 모른다. 학습 이후의 일, 공개되지 않은 문서(사내 규정, 내 메모), 그리고 그걸 모른다는 사실. 모르는 걸 물으면 그럴듯하게 지어낸다.

방법은 둘이다. 모델을 내 문서로 다시 학습시키거나(파인튜닝), 시험 볼 때 교과서를 펴 주거나. RAG 는 후자, 오픈북 시험이다. 문서가 바뀌면 교과서만 바꾸면 되고, 답에 "이 문서를 보고 답했다"는 출처도 달 수 있다.

RAG (Retrieval-Augmented Generation) — 검색(Retrieval)으로 찾은 자료를 덧붙여(Augmented) 답을 만든다(Generation).

전체 흐름 — 미리 한 번, 질문마다 한 번

임베딩 — 뜻을 좌표로

컴퓨터는 "점심 메뉴"와 "저녁 회식 장소"가 비슷한 이야기라는 걸 글자만 보고는 모른다. 겹치는 글자가 하나도 없으니까. 임베딩은 문장을 숫자 목록(벡터)으로 바꾸는데, 뜻이 비슷하면 숫자도 비슷하게 나오도록 학습된 모델이 해 준다. 문장마다 "의미 지도 위의 좌표"를 받는 셈이다.

실제 임베딩은 수백~수천 차원이다. 눈으로 보려고 3차원짜리 장난감을 만들었다. 각 칸은 [음식, 돈, 날씨] 쪽으로 얼마나 기울었나다. 

docs = {
    "점심 메뉴 추천":   [0.9, 0.1, 0.0],
    "이번 달 카드값":   [0.2, 0.9, 0.0],
    "주말 비 소식":     [0.0, 0.1, 0.9],
    "저녁 회식 장소":   [0.8, 0.3, 0.1],
}
question = [0.85, 0.2, 0.05]   # "오늘 뭐 먹지?"

코사인 거리 — 방향이 얼마나 같은가

두 좌표가 얼마나 가까운지 재는 방법 중 가장 많이 쓰는 게 코사인 유사도다. 원점에서 두 점으로 화살표를 그었을 때 두 화살표가 이루는 각도를 본다. 같은 방향이면 1, 직각이면 0. 거리로 쓰고 싶으면 1 − 유사도, 즉 코사인 거리로 바꾼다(작을수록 가깝다). 

import math

def cosine_similarity(a, b):
    dot = sum(x * y for x, y in zip(a, b))          # 같은 칸끼리 곱해서 더하기
    na = math.sqrt(sum(x * x for x in a))           # 화살표 길이
    nb = math.sqrt(sum(y * y for y in b))
    return dot / (na * nb)

scores = sorted((1 - cosine_similarity(question, v), name) for name, v in docs.items())
for dist, name in scores:
    print(f"거리 {dist:.3f}  {name}")
print("top-2:", [name for _, name in scores[:2]])
거리 0.009  점심 메뉴 추천
거리 0.010  저녁 회식 장소
거리 0.566  이번 달 카드값
거리 0.918  주말 비 소식
top-2: ['점심 메뉴 추천', '저녁 회식 장소']

"오늘 뭐 먹지?"와 글자가 하나도 안 겹치는 "저녁 회식 장소"가 2등으로 뽑혔다. 키워드 검색으로는 못 찾는 걸 뜻으로 찾았다. 이게 벡터 검색의 힘이다. 이렇게 가장 가까운 k 개를 고르는 걸 k-최근접 이웃(k-NN) 검색, 줄여서 top-k 라고 한다.

pgvector — PostgreSQL 에서 바로 벡터 검색

조각이 수백만 개면 파이썬으로 하나씩 다 재 볼 수 없다. 벡터를 저장하고 가까운 것을 빨리 찾아 주는 저장소가 필요하다. 전용 벡터 DB 도 있지만, 이미 PostgreSQL 을 쓰고 있다면 확장 기능 pgvector 를 켜서 같은 DB 안에서 할 수 있다. 데이터가 한 곳에 있다는 게 큰 장점이다. 

-- 확장 켜기
CREATE EXTENSION IF NOT EXISTS vector;

-- 조각을 담는 테이블. 차원 수는 쓰는 임베딩 모델에 맞춘다
CREATE TABLE memo_chunks (
    id        bigserial PRIMARY KEY,
    memo_id   bigint,
    content   text,
    embedding vector(1536)
);

-- 질문 좌표(:q)와 코사인 거리가 가장 가까운 5개
SELECT content, embedding <=> :q AS distance
FROM memo_chunks
ORDER BY embedding <=> :q
LIMIT 5;
연산자재는 것
<=>코사인 거리 (위에서 계산한 그것)
<->유클리드(L2) 거리 — 점과 점 사이 직선 거리
<#>내적에 음수를 붙인 값 — 작을수록 가깝게 맞춰 둔 것

인덱스 — 정확도를 조금 내주고 속도를 산다

인덱스 없이 ORDER BY … LIMIT 을 하면 모든 줄과 거리를 잰다(정확하지만 느리다). 그래서 근사 최근접 이웃(ANN) 인덱스를 단다. "거의 확실히 가까운 것"을 훨씬 빨리 찾는 대신, 아주 가끔 진짜 1등을 놓칠 수 있다. 

-- HNSW: 이웃끼리 그물처럼 이어 두고 타고 가며 찾는다. 검색이 빠르고 정확한 편, 만들 때 느리고 메모리를 더 쓴다
CREATE INDEX ON memo_chunks USING hnsw (embedding vector_cosine_ops);

-- IVFFlat: 좌표를 몇 개 무리(lists)로 나눠 두고 가까운 무리만 뒤진다. 만들기 빠르고 가볍다. 데이터가 어느 정도 쌓인 뒤 만든다
CREATE INDEX ON memo_chunks USING ivfflat (embedding vector_cosine_ops) WITH (lists = 100);

인덱스의 거리 종류(vector_cosine_ops)와 쿼리의 연산자(<=>)가 같아야 인덱스를 탄다.

자르기(chunking) — 얼마만큼씩 넣을까

문서 하나를 통째로 임베딩하면 여러 이야기가 한 좌표에 뭉개져서 무엇과도 애매하게 가까워진다. 반대로 너무 잘게 자르면 앞뒤 맥락이 사라진다. 그래서 문단 정도 크기로 자르고, 경계에서 뜻이 끊기지 않게 앞뒤를 조금씩 겹쳐서(overlap) 자르는 게 보통이다. 조각마다 원래 문서 id, 제목 같은 메타데이터를 같이 저장해 두면 "내 메모 중에서만" 같은 조건 검색과 출처 표시가 된다.

잘 안 되는 경우

증상원인흔한 대처
엉뚱한 조각이 뽑힌다조각이 너무 크거나 작다. 질문과 문서의 말투가 다르다자르는 크기·겹침 조정, 다른 임베딩 모델
제품 코드·고유명사를 못 찾는다임베딩은 뜻은 잘 잡지만 정확한 글자 맞추기는 약하다키워드 검색과 섞는 하이브리드 검색
찾았는데 답이 틀린다조각을 붙였지만 LLM 이 무시하거나 섞어 지어낸다"주어진 자료로만 답하라"는 지시, 출처 함께 표시
점점 느려진다인덱스 없이 전체 비교HNSW·IVFFlat 인덱스

벡터 — 숫자를 순서대로 늘어놓은 목록. 여기서는 의미 공간의 좌표.
임베딩 모델 — 글을 벡터로 바꿔 주는 모델. 색인과 질문에 반드시 같은 모델을 써야 한다.
코사인 유사도 / 거리 — 두 벡터 방향이 얼마나 같은지. 유사도 1 = 같은 방향, 거리 = 1 − 유사도.
k-NN / top-k — 가장 가까운 k 개를 고르는 검색.
ANN (근사 최근접 이웃) — 조금 덜 정확한 대신 훨씬 빠르게 가까운 것을 찾는 방법. HNSW, IVFFlat 이 대표적이다.
chunk — 임베딩하기 좋게 자른 문서 조각.

정리

단계한 줄로
RAG찾아서 붙여 주고 답하게 한다 — 오픈북 시험
임베딩뜻이 비슷하면 좌표가 가깝다
코사인 거리화살표 방향이 얼마나 같은가. 작을수록 가깝다
top-k가장 가까운 k 조각을 프롬프트에
pgvectorPostgreSQL 안에서 ORDER BY embedding <=> :q LIMIT k
chunking문단 크기 + 조금 겹치게 + 메타데이터

구조 시리즈와 이어 보면, 이 "찾기"도 결국 영속 층의 일이다. 서비스는 "관련 문서를 가져온다"만 말하고(SLAP), 그 아래에서 "질문을 임베딩하고 → pgvector 로 코사인 거리 top-k 를 가져온다"는 저수준 일이 일어난다.
