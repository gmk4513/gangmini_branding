THEORY · CI/CD 01/13

CI/CD 한눈에
— 개발 환경과 아키텍처는 어떻게 바뀌었나

이론 CI/CD DevOps 컨테이너 MSA 파이프라인 2026.11.10

내 사이트(gangmini.com)는 main 브랜치에 push 하면 1~2분 뒤 저절로 바뀐다. 파일을 서버에 올리는 일을 내가 한 번도 안 한다. 이게 아주 작은 CI/CD 다. 회사에서는 같은 일을 훨씬 큰 규모로 한다. 서버가 수십 대, 서비스가 수십 개, 하루 배포가 수십 번이다.

이 글은 CI/CD 실습 시리즈 13편의 첫 글이다. 명령은 하나도 안 친다. 대신 "왜 이런 게 생겼나"를 개발 방식·서버·코드 구조가 바뀐 순서대로 짚고, CI/CD 가 정확히 무엇인지, 앞으로 13편 동안 무엇을 만드는지 지도를 그린다. 실습은 2편 환경 준비부터 시작한다.

먼저, 손으로 배포하면 무슨 일이 생기나

CI/CD 가 없는 팀의 배포 날은 대략 이렇다.

  1. 개발자가 운영 서버에 SSH 로 접속한다.
  2. git pull 로 최신 코드를 받는다. (테스트는? "내 컴퓨터에서 돌려 봤어요.")
  3. 패키지를 설치하고, 서버 프로그램을 껐다 켠다.
  4. 화면을 열어 눌러 보고 "됐다"고 메신저에 쓴다.

이 방식은 작을 때는 돌아간다. 사람이 늘고 배포가 잦아지면 이런 일이 생긴다.

문제실제 모습
내 컴퓨터에서만 된다내 노트북은 파이썬 3.12, 서버는 3.10. 내 컴퓨터엔 깔려 있던 라이브러리가 서버엔 없다
순서를 빼먹는다열 단계 중 "설정 파일 복사"를 깜빡해서 운영이 멈춘다. 매번 사람이 기억에 의존한다
합칠 때 터진다다섯 명이 2주 동안 따로 만든 걸 금요일에 한꺼번에 합치니 충돌과 버그가 쏟아진다("통합 지옥")
무엇이 나갔는지 모른다지금 운영에 도는 게 어느 커밋인지, 누가 언제 올렸는지 기록이 없다
되돌리기가 어렵다배포 후 에러가 나면 "전에 뭐였더라"부터 찾는다. 되돌리는 데 한 시간이 걸린다
배포가 무섭다무서우니까 덜 하고, 덜 하니까 한 번에 바뀌는 게 커지고, 커지니까 더 자주 터진다

CI/CD 는 이 문제들을 "사람이 기억해서 하던 순서를, 기계가 매번 똑같이 하게" 바꿔서 푼다. 그런데 왜 하필 지금 이게 필수가 됐을까. 세 가지가 동시에 바뀌었기 때문이다. 일하는 방식, 서버, 코드 구조.

1. 일하는 방식의 변화 — 워터폴, 애자일, DevOps

  • 워터폴 — 요구사항 → 설계 → 개발 → 테스트 → 배포를 폭포처럼 한 방향으로 한 번씩. 계획대로 갈 때는 깔끔하지만, 몇 달 뒤 배포했는데 고객이 원하던 게 아니면 처음부터 다시다.
  • 애자일 — 1~4주짜리 짧은 주기(스프린트)를 반복하며 조금씩 만들고 보여 준다. 개발 속도는 빨라졌지만, 만든 걸 운영 서버에 올리는 일은 여전히 별도 운영팀의 몫이라 거기서 막혔다.
  • DevOps — 개발(Development)과 운영(Operations)의 벽을 없앤다. 만든 팀이 배포하고, 운영 중 문제도 직접 본다. 사람이 줄을 서서 넘겨주던 단계를 자동화로 이어 붙이는 것이 핵심이고, 그 자동화의 중심이 CI/CD 파이프라인이다.

스프린트(sprint) — 애자일에서 정해 둔 짧은 개발 주기. 보통 2주. 회차가 끝날 때마다 돌아가는 결과물을 보여 준다.
DevOps — 도구 이름이 아니라 일하는 문화. "만든 사람이 운영까지 책임지고, 그 사이를 자동화로 잇는다"는 생각이다. 회사에서 "데브옵스 엔지니어"는 대개 이 자동화(파이프라인·인프라)를 만드는 사람을 말한다.

2. 서버의 변화 — 물리 서버, 가상 머신, 컨테이너, 쿠버네티스

프로그램을 "어디에 올리나"도 크게 바뀌었다. 바뀔 때마다 배포의 단위가 작아지고 빨라졌다.

단계배포가 어떻게 바뀌었나
물리 서버서버를 사고 설치하는 데 몇 주. 배포는 그 서버에 접속해서 파일을 바꾸는 것. 회사 건물이나 데이터센터에 직접 둔다(온프레미스)
가상 머신서버 한 대를 여러 대처럼 나눠 쓴다. 클라우드(AWS 등)에서 몇 분 만에 빌린다. 그래도 VM 마다 운영체제가 통째로 있어서 무겁다
컨테이너 (Docker)앱을 이미지로 포장해서 어디서든 같은 모습으로 실행한다. 배포 = "새 이미지로 바꿔 띄우기". 되돌리기 = "이전 이미지로 다시 띄우기"
쿠버네티스컨테이너 수백 개를 서버 여러 대에 나눠 띄우고, 죽으면 살리고, 새 버전으로 하나씩 바꿔 끼운다. 사람은 "원하는 상태"를 파일로 적기만 한다

온프레미스(on-premises) — 서버를 회사가 직접 사서 회사 안(또는 직접 계약한 데이터센터)에 두고 운영하는 방식. 반대말은 클라우드(남의 서버를 빌려 쓰기).
하이퍼바이저(hypervisor) — 컴퓨터 한 대 위에서 여러 개의 가상 컴퓨터(VM)를 만들어 돌리는 프로그램.
이미지(image) — 컨테이너를 만들기 위한 "포장된 틀". 운영체제 일부 + 언어(파이썬 등) + 라이브러리 + 내 코드가 들어 있다. 이미지를 실행한 것이 컨테이너다. 붕어빵 틀(이미지)과 붕어빵(컨테이너).
쿠버네티스(Kubernetes, k8s) — 여러 서버에 걸쳐 컨테이너를 배치·관리해 주는 시스템. 이런 일을 오케스트레이션(지휘)이라고 부른다. k 와 s 사이 글자가 8개라 k8s.

3. 코드 구조의 변화 — 모놀리스에서 MSA 로

한 프로그램에 모든 기능을 넣은 모놀리스는 배포할 것이 하나다. 기능별로 서버를 쪼갠 MSA(마이크로서비스 아키텍처)는 서비스마다 따로 만들고 따로 배포한다. 서비스가 20개고 각자 하루 두 번 배포하면, 하루 40번이다. 이걸 사람이 SSH 로 할 수는 없다.

즉 MSA 와 컨테이너가 퍼지면서 CI/CD 는 "있으면 좋은 것"에서 "없으면 못 하는 것"이 됐다. 모놀리스와 MSA 를 고르는 기준은 코드 구조 한눈에에 따로 정리했다(결론: 이유가 생기기 전엔 쪼개지 않는다).

모놀리스(monolith) — 모든 기능이 프로그램 하나로 묶인 구조. 빌드·배포·로그가 한 곳이라 단순하다.
MSA(Microservice Architecture) — 기능마다 작은 서버로 나누고 네트워크로 서로 부르는 구조. 따로 늘리고 따로 배포할 수 있지만, 관리할 것이 서비스 수만큼 늘어난다.

4. 그래서 CI/CD 란

CI/CD 는 두 덩어리다. 앞의 CI 는 "합치기", 뒤의 CD 는 "내보내기"다. CD 는 두 가지 뜻으로 쓰이니 구분해 둔다.

CI — 지속적 통합 (Continuous Integration)

여러 사람의 변경을 자주(하루에도 여러 번) 합치되, 합칠 때마다 기계가 빌드하고 테스트해서 깨진 걸 바로 찾는 방식이다. 2주 모았다가 한꺼번에 합치면 어디서 깨졌는지 찾기 어렵다. 한 시간 전 커밋이 깨뜨렸다면 범인은 그 커밋 하나다. CI 의 질문은 하나다. "이 변경을 main 에 합쳐도 되나?"

CD — 지속적 전달 (Continuous Delivery)

CI 를 통과한 코드를 언제든 운영에 내보낼 수 있는 상태(버전이 붙은 이미지 + 개발 서버 배포·확인)까지 자동으로 만들어 둔다. 운영 배포는 사람이 버튼 하나로 한다. 금융·의료처럼 확인 절차가 필요한 곳은 대개 여기까지.

CD — 지속적 배포 (Continuous Deployment)

버튼도 없앤다. 테스트를 통과하면 운영까지 자동으로 나간다. 대신 테스트와 모니터링, 자동 되돌리기를 그만큼 믿을 수 있어야 한다. 내 사이트(main 에 push → Cloudflare 가 바로 반영)는 테스트는 없지만 모양만 보면 이쪽이다.

통합(integration) — 내 브랜치의 변경을 팀의 기준 브랜치(main)에 합치는 것.
파이프라인(pipeline) — 빌드 → 테스트 → 패키징 → 배포처럼 정해진 단계를 차례로 자동 실행하는 흐름. 한 단계가 실패하면 거기서 멈춘다. 공장 컨베이어 벨트를 떠올리면 된다.
운영(production, 프로덕션) — 실제 사용자가 쓰는 서버. 그 전 단계에서 확인용으로 쓰는 서버는 개발(dev)·스테이징(staging) 서버라고 부른다.

5. 왜 필요한가 — 바뀌는 것

손으로 할 때CI/CD 가 있으면
"내 컴퓨터에선 됐는데"매번 깨끗한 환경에서 같은 순서로 빌드·테스트한다. 컨테이너면 실행 환경까지 같다
순서를 사람이 기억순서가 파일(Jenkinsfile 등)에 코드로 적혀 있고, 그 파일도 Git 으로 관리한다
2주 모아 한꺼번에 합치기작게 자주 합친다. 깨지면 방금 그 커밋이 범인이다
무엇이 나갔는지 모름이미지 태그에 빌드 번호·커밋 해시를 붙인다. 운영의 버전에서 커밋까지 거슬러 간다
되돌리기 한 시간이전 버전 이미지로 다시 배포하면 끝. ArgoCD 라면 Git 커밋 하나 되돌리기
배포가 무서운 행사배포가 지루한 일상이 된다. 자주 하니 한 번의 변경이 작고, 작으니 덜 터진다

팀의 배포 실력을 잴 때 흔히 쓰는 네 숫자가 있다(DORA 지표). 얼마나 자주 배포하나, 커밋에서 운영까지 얼마나 걸리나, 배포 중 몇 번이 장애를 내나, 장애에서 얼마나 빨리 회복하나. 네 가지 모두 CI/CD 로 좋아지는 숫자다.

DORA 지표 — 구글의 DevOps 연구 프로그램(DORA)이 정리한 배포 성과 지표 네 개: 배포 빈도, 변경 리드 타임, 변경 실패율, 서비스 복구 시간. 면접에서 "CI/CD 가 왜 좋은가"를 숫자로 말할 때 쓴다.
롤백(rollback) — 문제가 생긴 배포를 이전 버전으로 되돌리는 것.

6. 파이프라인은 보통 이 단계로 짠다

단계하는 일이 시리즈에서
체크아웃Git 저장소에서 코드를 받는다젠킨스가 GitHub 의 cicd-hello 를 받음
빌드패키지 설치, 컴파일pip install
테스트자동 테스트, 코드 검사pytest (Dockerfile 의 test 단계)
패키징실행할 수 있는 묶음 만들기 + 버전 붙이기도커 이미지 cicd-hello:12-a1b2c3d
저장만든 묶음을 보관소에 올린다Docker Hub 에 push
배포서버에서 새 버전으로 바꿔 띄운다systemd 재시작 → docker run → 쿠버네티스
확인정말 살아 있나 확인(헬스 체크)/health 가 ok 인지

레지스트리(registry) — 도커 이미지를 올려 두고 내려받는 보관소. Docker Hub 가 대표적이고, 회사는 AWS ECR·Harbor 같은 자체 레지스트리를 쓴다. 코드의 GitHub 에 해당한다.
헬스 체크(health check) — 서버가 살아 있는지 확인하려고 부르는 주소. 이 시리즈의 앱은 /health 가 {"status":"ok"} 를 돌려준다.

7. 도구 지도

도구맡는 일비유
Git · GitHub코드와 변경 기록 보관. 모든 자동화의 출발점설계도 보관실
젠킨스 (Jenkins)파이프라인을 실행하는 서버. 내가 직접 설치해서 운영한다공장 반장
GitHub ActionsGitHub 안에 들어 있는 파이프라인 실행기설계도 보관실에 딸린 반장
Docker앱을 이미지로 포장하고 컨테이너로 실행규격 상자
Docker Hub이미지 보관소(레지스트리)상자 창고
쿠버네티스컨테이너를 여러 서버에 띄우고 관리물류 센터
ArgoCDGit 에 적힌 "원하는 상태"대로 쿠버네티스를 맞춰 둔다도면대로 됐는지 계속 보는 감독

젠킨스와 GitHub Actions — 언제 무엇을

둘 다 파이프라인을 돌린다. 이 시리즈는 커리큘럼대로 젠킨스를 쓰고, GitHub Actions 는 따로 정리한 글이 있다.

젠킨스GitHub Actions
어디서 도나내가 설치한 서버 (회사 안에도 둘 수 있다)GitHub 가 빌려주는 컴퓨터 (내 서버를 붙일 수도 있다)
설정화면 + Jenkinsfile(Groovy 문법).github/workflows/*.yml(YAML)
장점플러그인이 아주 많고, 회사 내부망·사내 Git 과 잘 붙는다. 오래 써서 자료가 많다설치할 게 없다. GitHub 저장소와 바로 붙는다
단점서버·플러그인 업데이트·보안을 내가 관리해야 한다GitHub 밖 환경과 엮기 번거롭고, 많이 쓰면 비용
흔한 곳금융·대기업·온프레미스가 많은 회사스타트업, 오픈소스

밀어 넣기(push)와 끌어오기(pull) — 배포 방식 두 가지

9편까지는 젠킨스가 서버에 접속해서 "이걸 띄워"라고 밀어 넣는다(push 방식). 12편부터는 방향이 바뀐다. 젠킨스는 Git 저장소에 "이제 이 버전이 맞다"고 적기만 하고, 쿠버네티스 안의 ArgoCD 가 그 저장소를 보고 있다가 스스로 끌어와 맞춘다(pull 방식). Git 을 배포의 기준으로 삼는 이 방식을 GitOps 라고 한다. 젠킨스가 운영 클러스터의 열쇠를 들고 있지 않아도 되고, 배포 기록이 Git 커밋으로 남는다.

GitOps — 서버가 어떤 상태여야 하는지(어떤 이미지를 몇 개 띄울지 등)를 Git 저장소에 파일로 적어 두고, 도구가 실제 상태를 그 파일에 계속 맞추는 운영 방식. 배포 = Git 커밋, 롤백 = 커밋 되돌리기.
매니페스트(manifest) — 쿠버네티스에 "이렇게 띄워 줘"라고 적어 주는 YAML 파일.

8. 이 시리즈에서 만드는 것 — 13편 지도

앱은 하나만 쓴다. cicd-hello — 주소를 열면 Hello, CI/CD! version=… 를 돌려주는 파이썬(Flask) 서버다. 같은 앱을 세 번, 점점 현대적인 방식으로 자동 배포한다. 앱이 단순해야 바뀌는 것이 배포 방식뿐이라는 게 잘 보인다.

편주제끝나면 손에 남는 것
01CI/CD 한눈에 (이 글)왜 하는지, 무엇을 하는지의 지도

편마다 앞 편에서 만든 것을 그대로 이어 쓴다. 건너뛰지 말고 순서대로 가는 게 가장 빠르다. 한 편은 대략 30분~1시간 걸린다(설치·다운로드 시간 포함).

용어 정리

CI (지속적 통합) — 변경을 자주 합치고, 합칠 때마다 자동으로 빌드·테스트해 깨진 걸 바로 찾는 것.
지속적 전달 (Continuous Delivery) — 운영 직전까지 자동. 운영 배포는 사람이 버튼으로.
지속적 배포 (Continuous Deployment) — 테스트를 통과하면 운영까지 자동.
파이프라인 — 체크아웃 → 빌드 → 테스트 → 패키징 → 배포를 차례로 자동 실행하는 흐름.
온프레미스 — 회사가 직접 가진 서버에서 운영하는 것. 이 시리즈에서는 WSL2 우분투가 그 서버 역할을 한다.
컨테이너 · 이미지 — 앱과 실행 환경을 담은 상자(컨테이너)와 그 상자의 틀(이미지).
레지스트리 — 이미지 보관소. Docker Hub.
쿠버네티스 — 여러 서버에 컨테이너를 배치·관리하는 시스템.
GitOps — Git 에 적힌 상태대로 서버를 맞추는 배포 방식. ArgoCD 가 대표 도구.
DevOps — 개발과 운영의 벽을 없애고 그 사이를 자동화로 잇는 일하는 방식.
