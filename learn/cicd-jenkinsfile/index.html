Jenkinsfile 로
— 파이프라인 만들기

실습 Jenkins Jenkinsfile 선언형 파이프라인 Pipeline as Code 멀티브랜치 2026.11.10

앞 글의 Freestyle 잡은 잘 돌았다. 그런데 그 설정은 젠킨스 화면 안에만 있다. 누가 배포 명령 한 줄을 바꿔도 기록이 남지 않고, 리뷰도 없고, 젠킨스 서버가 날아가면 설정도 같이 사라진다.

그래서 요즘 회사에서는 빌드 설정을 코드 파일로 써서 앱 저장소에 같이 넣는다. 파일 이름은 Jenkinsfile 이다. 앱 코드처럼 커밋하고, PR 로 리뷰하고, 되돌릴 수 있다. 이걸 Pipeline as Code 라고 부른다. 이번 글에서는 앞 글의 잡과 똑같은 일을 하는 Jenkinsfile 을 쓰고, 젠킨스가 그 파일을 읽어 돌게 만든다.

이번 단계에서 할 것

  1. 선언형(Declarative) 파이프라인 문법을 블록 하나씩 뜯어보기
  2. cicd-hello 저장소에 Jenkinsfile 넣기
  3. Pipeline 잡 cicd-hello-pipeline 을 "Pipeline script from SCM" 으로 만들기
  4. Stage View 로 단계별 결과 보기, 일부러 실패시켜 로그 읽기
  5. Replay, Snippet Generator, 자격 증명 쓰기, 멀티브랜치 맛보기

끝나면: 젠킨스 화면에 Checkout · Test · Deploy · Health check 네 칸이 초록으로 서고, curl localhost:8000/ 이 이 잡의 빌드 번호를 말한다.

파이프라인(pipeline) — 코드를 받아서 운영에 내보내기까지의 단계를 순서대로 이은 것. 젠킨스에서는 그걸 표현하는 잡 종류의 이름이기도 하다.
Jenkinsfile — 파이프라인을 적은 텍스트 파일. 저장소 맨 위에 둔다. 확장자는 없다.
Pipeline as Code — 빌드·배포 절차를 화면 설정이 아니라 코드로 관리하는 방식. 변경 기록, 리뷰, 되돌리기, 복사가 앱 코드와 똑같이 된다.
Groovy — Jenkinsfile 이 쓰는 언어. Java 와 비슷한 문법의 스크립트 언어인데, 선언형 파이프라인은 정해진 블록만 채우면 돼서 Groovy 를 몰라도 쓸 수 있다.

한눈에 — 파일이 화면이 되기까지

1. 선언형 파이프라인 문법 해부

Jenkinsfile 은 정해진 블록을 정해진 자리에 채우는 형식이다. 뼈대만 보면 이렇다.

pipeline {                 // 전체를 감싸는 블록. 반드시 하나
    agent any              // 어디서 돌릴까

    options { ... }        // 잡 전체 옵션 (시간 제한, 기록 보관 개수 …)
    triggers { ... }       // 언제 저절로 돌까
    parameters { ... }     // 돌릴 때 받을 값
    environment { ... }    // 환경 변수

    stages {               // 단계들. 위에서부터 차례로
        stage('이름') {
            when { ... }   // 이 단계를 할지 말지 조건 (선택)
            steps {        // 실제로 할 일
                sh '셸 명령'
            }
            post { ... }   // 이 단계가 끝난 뒤 (선택)
        }
    }

    post { ... }           // 파이프라인 전체가 끝난 뒤
}
블록뜻이번 파일에서
agent어느 노드(컴퓨터)에서 돌릴지. any 는 "아무 데나 빈 곳". 9번 글에서는 도커 컨테이너, 11번에서는 쿠버네티스 파드가 된다agent any → 젠킨스 서버 자신
options잡 전체에 거는 설정10분 제한, 기록 20개, 동시 실행 금지, 시각 표시
triggers저절로 도는 조건. 앞 글 Poll SCM 칸과 같다pollSCM('H/2 * * * *')
parametersBuild with Parameters 화면에 뜰 입력 칸DEPLOY 체크박스
environment모든 단계에서 쓸 환경 변수. 셸에서는 $이름, Groovy 에서는 env.이름배포 폴더, 헬스 체크 주소
stages / stage단계 묶음 / 단계 하나. 화면에 칸으로 보인다네 단계
steps단계 안에서 실제로 실행할 것. sh(셸 명령), echo, junit, checkout, retry 같은 스텝을 나열
when조건이 참일 때만 그 단계를 한다. 거짓이면 회색 "건너뜀"으로 표시params.DEPLOY 가 참일 때만 배포
post끝난 뒤 결과에 따라. always(항상), success, failure, unstable, changed(지난번과 결과가 달라졌을 때) 등. 파일에 적은 순서와 상관없이 always 가 먼저 돈다테스트 결과 게시, 성공·실패 메시지

스텝(step) — 파이프라인에서 쓸 수 있는 명령 하나. sh, echo, junit 처럼 플러그인이 제공한다. 플러그인을 깔면 쓸 수 있는 스텝이 늘어난다.
params / env — Groovy 안에서 파라미터 값과 환경 변수를 읽는 이름. params.DEPLOY, env.BUILD_NUMBER.

선언형 vs 스크립트형

Jenkinsfile 에는 두 가지 문법이 있다. 처음부터 pipeline { } 으로 시작하는 게 선언형(Declarative), node { } 으로 시작해 Groovy 코드를 자유롭게 쓰는 게 스크립트형(Scripted)이다.

선언형스크립트형
시작pipeline { agent … stages { … } }node { stage('…') { … } }
자유도정해진 블록만. 대신 읽기 쉽고 실수가 적다Groovy 의 if·for·함수를 마음대로. 그만큼 복잡해지기 쉽다
문법 검사돌리기 전에 구조를 검사해서 틀린 곳을 알려 준다돌려 봐야 안다
지금 추천새로 쓰는 건 거의 다 이쪽예전 파일, 아주 특수한 흐름

선언형 안에서도 복잡한 로직이 꼭 필요하면 script { } 블록을 열어 그 안에서만 Groovy 를 쓴다. 이 시리즈는 선언형만 쓴다.

2. Jenkinsfile 넣기

우분투 터미널에서 실습 저장소로 간다(3번 글에서 ~/cicd/cicd-hello 로 받아 두었다).

cd ~/cicd/cicd-hello
git pull                 # 앞 글에서 GitHub 웹으로 고친 커밋을 받아 온다
nano Jenkinsfile

아래 전체를 붙여 넣는다. 주석(//)은 지워도 된다.

// cicd-hello 파이프라인: 받기 → 테스트 → 배포 → 확인
pipeline {
    agent any

    options {
        skipDefaultCheckout(true)          // 받기는 Checkout 단계에서 직접 한다
        timeout(time: 10, unit: 'MINUTES') // 10분 넘으면 강제 종료
        buildDiscarder(logRotator(numToKeepStr: '20'))
        disableConcurrentBuilds()          // 같은 잡이 동시에 두 번 배포하지 않게
        timestamps()                       // 로그 줄마다 시각
    }

    triggers {
        pollSCM('H/2 * * * *')             // 2분마다 새 커밋 확인
    }

    parameters {
        booleanParam(name: 'DEPLOY', defaultValue: true, description: '테스트 통과 후 배포할지')
    }

    environment {
        APP_DIR    = '/opt/cicd-hello'
        HEALTH_URL = 'http://localhost:8000/health'
    }

    stages {
        stage('Checkout') {
            steps {
                checkout scm
                sh 'git log -1 --oneline'
            }
        }

        stage('Test') {
            steps {
                sh '''
                    python3 -m venv venv
                    venv/bin/pip install -q -r requirements-dev.txt
                    venv/bin/python -m pytest -q --junitxml=test-results.xml
                '''
            }
            post {
                always {
                    junit allowEmptyResults: true, testResults: 'test-results.xml'
                }
            }
        }

        stage('Deploy') {
            when { expression { params.DEPLOY } }
            steps {
                sh '''
                    cp app.py requirements.txt "$APP_DIR/"
                    "$APP_DIR/venv/bin/pip" install -q -r "$APP_DIR/requirements.txt"
                    echo "APP_VERSION=$BUILD_NUMBER" > "$APP_DIR/version.env"
                    sudo -n systemctl restart cicd-hello
                '''
            }
        }

        stage('Health check') {
            when { expression { params.DEPLOY } }
            steps {
                retry(10) {
                    sleep(time: 1, unit: 'SECONDS')
                    sh 'curl -fsS "$HEALTH_URL"'
                }
            }
        }
    }

    post {
        always {
            echo "결과: ${currentBuild.currentResult}"
        }
        success {
            echo "성공: 빌드 #${env.BUILD_NUMBER} (DEPLOY=${params.DEPLOY})"
        }
        failure {
            echo "실패: ${env.BUILD_URL}console 에서 처음 나온 에러를 찾는다"
        }
    }
}

'''…''' 는 여러 줄 문자열이다. 젠킨스는 그 안을 셸 스크립트 하나로 실행하고, 앞 글처럼 한 줄이라도 실패하면 멈춘다. timeout, disableConcurrentBuilds 는 Freestyle 화면에 없던 안전장치다. 테스트가 멈춰 서서 실행자를 영원히 붙잡거나, 커밋 두 개가 연달아 와서 배포 두 개가 엉키는 걸 막는다.

checkout scm — "이 Jenkinsfile 을 가져온 바로 그 저장소·브랜치·커밋을 워크스페이스에 받아라". 저장소 주소를 Jenkinsfile 에 다시 적지 않아도 된다.
skipDefaultCheckout — 선언형은 원래 맨 앞에 받기 단계를 자동으로 넣는다. 그걸 끄고 Checkout 단계에서 직접 받게 해서 화면에 단계가 또렷이 보이게 했다.
retry(n) — 안쪽이 실패하면 n 번까지 다시 해 보는 스텝. 여기서는 "앱이 뜰 때까지 최대 10초 기다리기"에 썼다.

저장하고 커밋한다.

git add Jenkinsfile
git commit -m "Jenkinsfile: 테스트 후 8000 포트로 배포하는 파이프라인"
git push

3. Pipeline 잡 만들기 — Pipeline script from SCM

먼저 앞 글의 Freestyle 잡 cicd-hello-freestyle 의 Poll SCM 이 꺼져 있는지 확인한다. 둘 다 켜져 있으면 커밋 한 번에 배포가 두 번 된다.

  1. + New Item → 이름 cicd-hello-pipeline → Pipeline → OK
  2. 설정 화면 맨 아래 Pipeline 칸으로 내려간다. 위쪽 칸들(트리거, 파라미터)은 비워 둔다. Jenkinsfile 에 다 있다
  3. Definition: Pipeline script from SCM
  4. SCM: Git → Repository URL https://github.com/<내아이디>/cicd-hello.git, Credentials 없음
  5. Branch Specifier: */main
  6. Script Path: Jenkinsfile (기본값 그대로)
  7. Save

Definition 의 다른 선택지인 Pipeline script 는 Jenkinsfile 내용을 화면의 칸에 직접 붙여 넣는 방식이다. 문법 연습할 때는 편하지만, 그러면 다시 "설정이 젠킨스 안에만 있는" 상태가 된다. 실제 잡은 SCM 쪽으로 한다.

첫 빌드는 손으로 한 번

Build Now 를 누른다. 첫 빌드가 중요한 이유가 있다. 젠킨스는 Jenkinsfile 을 한 번 읽어 봐야 그 안의 triggers 와 parameters 를 잡 설정에 등록한다. 그래서 첫 빌드 전에는 폴링도 안 돌고 파라미터 칸도 없다. 첫 빌드가 끝나면 왼쪽 메뉴가 Build with Parameters 로 바뀌어 있다. Configure 를 다시 열어 보면 Poll SCM 이 저절로 체크돼 있다.

4. Stage View 와 로그 읽기

잡 화면 가운데에 빌드마다 한 줄씩, 단계마다 한 칸씩 표가 생긴다. 이게 Stage View 다. 칸 색은 단계 결과, 칸 안 숫자는 걸린 시간이다. 칸에 마우스를 올려 Logs 를 누르면 그 단계의 로그만 볼 수 있다. Freestyle 처럼 긴 콘솔을 뒤질 필요가 없다.

표가 안 보이면 Manage Jenkins → Plugins → Available plugins 에서 Pipeline: Stage View 를 설치한다. 최근 젠킨스에는 같은 역할의 새 화면인 Pipeline Graph View(빌드 화면의 Pipeline Overview) 플러그인도 있다. 어느 쪽이든 "단계별로 나눠 보기"는 같다.

5. 일부러 실패시켜 보기

이번에는 내 컴퓨터에서 고쳐서 push 한다. 앞 글처럼 테스트를 깨뜨린다.

sed -i 's/Hello, CI\/CD!/Hi!/' app.py
git commit -am "일부러 테스트 깨뜨리기"
git push

2분 남짓 뒤 폴링이 새 빌드를 띄운다(기다리기 싫으면 Build with Parameters → Build). Stage View 에서 보이는 것:

  • Checkout 초록, Test 빨강
  • Deploy, Health check 는 실행되지 않고 건너뛴 칸으로 남는다. 로그에는 Stage "Deploy" skipped due to earlier failure(s). (DEPLOY 체크를 끄고 돌렸을 때는 skipped due to when conditional 로 이유가 다르게 찍힌다)
  • 콘솔 끝에 post { failure } 의 메시지 실패: http://localhost:8080/job/cicd-hello-pipeline/2/console …
  • 잡 화면의 테스트 결과 그래프에 빨간 구간이 생긴다

curl localhost:8000/ 은 여전히 지난 성공 번호다. 되돌린다.

git revert --no-edit HEAD
git push

git revert — 지정한 커밋을 "거꾸로 하는" 새 커밋을 만든다. 기록을 지우지 않고 되돌리는 방법이라 이미 push 한 커밋에 쓴다. 자세히는 되돌리기.

6. Replay — 커밋 없이 한 번만 고쳐 돌리기

Jenkinsfile 을 고칠 때마다 커밋·push 하고 2분 기다리는 건 느리다. 빌드 화면 왼쪽의 Replay 를 누르면 그 빌드가 쓴 Jenkinsfile 이 편집 칸에 나온다. 고쳐서 Run 하면 그 한 번만 고친 내용으로 돈다. 예를 들어 Test 단계의 pytest -q 를 pytest -v 로 바꿔 테스트 이름이 다 찍히는지 본다.

Replay 로 고친 건 저장소에 저장되지 않는다. 마음에 들면 같은 내용을 Jenkinsfile 에 옮겨 커밋한다. 실험은 Replay, 확정은 커밋이다.

7. 문법이 생각 안 날 때 — Pipeline Syntax

잡 화면 왼쪽 Pipeline Syntax 를 누르면 도우미가 열린다. 두 가지를 쓴다.

  • Snippet Generator — Sample Step 에서 스텝을 고르고 칸을 채운 뒤 Generate Pipeline Script 를 누르면 Jenkinsfile 에 붙여 넣을 한 줄이 나온다. 예: junit 을 고르고 파일 이름을 넣으면 junit 'test-results.xml'
  • Declarative Directive Generator — options, triggers, when, post 같은 블록을 화면으로 골라 만든다

같은 화면의 Global Variables Reference 에는 env, params, currentBuild 로 읽을 수 있는 값 목록이 있다. 내 젠킨스에 깔린 플러그인 기준으로 나오기 때문에 인터넷 예제보다 정확하다.

8. 자격 증명 쓰기 — withCredentials

4번 글에서 등록한 github-token 을 Jenkinsfile 에서 꺼내 쓰는 방법이다. 13번 글에서 젠킨스가 GitHub 에 push 할 때 이대로 쓴다. 지금은 확인만 해 본다. Replay 로 Checkout 단계 steps 안에 넣고 돌려 본다. 

withCredentials([usernamePassword(credentialsId: 'github-token',
                                  usernameVariable: 'GH_USER',
                                  passwordVariable: 'GH_TOKEN')]) {
    sh 'curl -fsS -o /dev/null -w "GitHub 인증: %{http_code}\\n" -u "$GH_USER:$GH_TOKEN" https://api.github.com/user'
}
Masking supported pattern matches of $GH_TOKEN
+ curl -fsS -o /dev/null -w … -u <내아이디>:**** https://api.github.com/user
GitHub 인증: 200
  • 블록 안에서만 GH_USER, GH_TOKEN 환경 변수가 생기고, 블록이 끝나면 사라진다
  • 로그에 비밀번호(토큰)가 찍히면 **** 로 가려진다. 아이디는 가리지 않는다. 그리고 가림은 "글자가 똑같을 때"만 통해서, 값을 잘라 찍거나 바꿔 찍으면 새어 나간다. 일부러 출력하지 않는다
  • sh 뒤 문자열은 작은따옴표로 쓴다. 큰따옴표("…$GH_TOKEN…")로 쓰면 Groovy 가 먼저 값을 끼워 넣어 버려서, 비밀값이 명령 문자열 자체에 박힌다. 젠킨스도 이때 A secret was passed to "sh" using Groovy String interpolation 경고를 띄운다. 작은따옴표면 셸이 실행할 때 환경 변수에서 읽는다

짧게 쓰는 방법도 있다. environment 블록에서 credentials() 로 부르면 아이디·비밀번호가 _USR, _PSW 를 붙인 이름으로 들어온다.

environment {
    GH = credentials('github-token')   // → $GH_USR, $GH_PSW
}

withCredentials — 자격 증명을 블록 안에서만 환경 변수로 꺼내 주는 스텝(Credentials Binding 플러그인). 쓰는 범위를 좁혀 새는 걸 줄인다.
문자열 끼워 넣기(interpolation) — Groovy 에서 큰따옴표 문자열 안의 ${…}·$이름 을 값으로 바꾸는 것. 작은따옴표 문자열은 바꾸지 않고 글자 그대로 셸에 넘긴다.

9. 멀티브랜치 파이프라인 — 브랜치마다 저절로

지금 잡은 main 하나만 본다. 회사에서는 기능 브랜치와 PR 에서도 테스트를 돌리고 싶다. 그렇다고 브랜치마다 잡을 손으로 만들 수는 없다. Multibranch Pipeline 은 저장소를 훑어서 Jenkinsfile 이 있는 브랜치마다 잡을 저절로 만들고, 브랜치가 지워지면 잡도 정리한다.

만들어 보기

  1. 먼저 cicd-hello-pipeline 잡의 폴링을 끈다(Disable Project 버튼으로 잡을 통째로 멈춰도 된다). 둘이 같이 main 을 배포하지 않게
  2. + New Item → 이름 cicd-hello-multi → Multibranch Pipeline
  3. Branch Sources → Add source → Git → Project Repository 에 저장소 주소
  4. Build Configuration: by Jenkinsfile, Script Path Jenkinsfile
  5. Scan Multibranch Pipeline Triggers → Periodically if not otherwise run → 간격 2 minutes (새 브랜치를 찾는 주기)
  6. Save → 저절로 Scan 이 돌고, main 하위 잡이 생겨 빌드된다

Jenkinsfile 의 배포 두 단계 when 을 바꾼다.

        stage('Deploy') {
            when {
                allOf {
                    branch 'main'                       // main 브랜치일 때만
                    expression { params.DEPLOY }        // 그리고 DEPLOY 체크일 때만
                }
            }
            ...
        stage('Health check') {
            when {
                allOf {
                    branch 'main'
                    expression { params.DEPLOY }
                }
            }

커밋해서 main 에 올린 뒤, 기능 브랜치를 하나 만들어 push 해 본다. 

git switch -c feature/greeting
echo "# 인사말 바꿀 예정" >> app.py
git commit -am "인사말 작업 시작"
git push -u origin feature/greeting

2분쯤 뒤 cicd-hello-multi 안에 feature/greeting 잡이 생기고, Test 까지 돈 뒤 Deploy·Health check 는 회색으로 건너뛴다. 운영(8000)은 그대로다. 브랜치를 PR 로 합치면 main 잡이 돌아서 그때 배포된다. GitHub 소스(GitHub Branch Source 플러그인)로 연결하면 PR 마다 하위 잡이 생기고 결과가 PR 화면에 체크로 붙는다.

주의: when { branch 'main' } 은 멀티브랜치에서만 뜻이 있다. 3번 단계의 일반 Pipeline 잡에서는 브랜치 이름(BRANCH_NAME)이 비어 있어서 이 조건이 늘 거짓이 되고, 배포가 영영 안 된다. 그래서 일반 잡용 Jenkinsfile 에는 params.DEPLOY 만 걸었다.

멀티브랜치 파이프라인 — 저장소의 브랜치(와 PR)마다 하위 파이프라인 잡을 자동으로 만들고 지우는 잡 종류.
BRANCH_NAME — 멀티브랜치에서 지금 도는 브랜치 이름을 담은 환경 변수. when { branch … } 이 이 값을 본다.
allOf / anyOf — when 안에서 조건을 "모두 참" / "하나라도 참"으로 묶는 말.

다음 단계로 가기 전 정리

  • 온프레미스 단계는 여기까지다. 지금까지 만든 것: 우분투에 직접 깐 젠킨스(8080), 잡 세 개, systemd 앱(8000).
  • 다음부터는 젠킨스를 도커 컨테이너로 다시 띄운다(8090). 우분투 젠킨스는 지우지 않아도 되지만, 메모리를 아끼려면 sudo systemctl stop jenkins 와 sudo systemctl disable jenkins 로 꺼 둔다. 8000 앱도 sudo systemctl disable --now cicd-hello 로 꺼도 된다.
  • Jenkinsfile 은 저장소에 남겨 둔다. 9번 글에서 이 파일을 도커용으로 고쳐 쓴다. 멀티브랜치로 바꾼 when 은 그대로 둬도 되고, 연습용 feature/greeting 브랜치는 지운다(git push origin --delete feature/greeting).
