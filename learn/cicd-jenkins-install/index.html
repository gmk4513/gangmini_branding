온프레미스란

온프레미스(on-premises)는 회사가 직접 가진 서버에 프로그램을 깔아 쓰는 방식이다. 서버실에 있는 컴퓨터든, 데이터센터에 빌린 자리에 넣어 둔 컴퓨터든 "우리가 관리하는 리눅스 한 대"에 직접 설치한다는 점이 같다. 반대말은 클라우드 서비스다. GitHub Actions 처럼 남이 돌려 주는 CI 를 쓰면 서버 관리는 안 해도 되지만, 사내망 안의 서버에 배포하거나 빌드 환경을 마음대로 바꾸기는 어렵다. 그래서 은행, 공공기관, 오래된 회사일수록 사내 서버에 젠킨스를 직접 깔아 둔 곳이 많다.

실습에서는 진짜 서버 대신 내 윈도우 안의 WSL2 우분투를 "회사 서버"로 친다. 명령은 전부 우분투 터미널에서 친다. 리눅스 서버에 SSH 로 접속해서 치는 것과 같은 명령이다.

온프레미스(on-premises, 줄여서 온프레) — 클라우드 서비스를 빌려 쓰지 않고, 회사가 직접 관리하는 서버에 소프트웨어를 설치해 운영하는 방식.
WSL2 — 윈도우 안에서 진짜 리눅스 커널을 돌리는 기능. 실습에서는 이 안의 우분투를 서버 한 대처럼 쓴다. 준비는 실습 환경 준비 글에서 했다.

젠킨스는 어떻게 생겼나

컨트롤러(controller) — 젠킨스의 본체. 웹 화면을 띄우고, 설정과 기록을 저장하고, "이 빌드는 어디서 돌려라"를 정한다. 예전 문서에는 master 라고 적혀 있다.
에이전트(agent)·노드(node) — 빌드를 실제로 돌리는 컴퓨터. 컨트롤러 자신도 노드 하나(built-in node)로 친다. 예전 이름은 slave.
실행자(executor) — 노드 하나가 동시에 돌릴 수 있는 빌드 칸 수. 2 면 빌드 두 개까지 동시에 돈다.
잡(job)·프로젝트 — "어떤 저장소를 받아서 무엇을 하라"는 설정 한 묶음. 빌드(build)는 그 잡을 한 번 돌린 것. 빌드마다 #1, #2 번호가 붙는다.
플러그인(plugin) — 젠킨스에 기능을 더하는 부품. Git 연동, 파이프라인, 테스트 결과 그래프까지 거의 모든 기능이 플러그인이다.
워크스페이스(workspace) — 잡이 코드를 받아 두고 명령을 실행하는 폴더. 잡마다 하나씩 생긴다.

1. Java 21 설치

젠킨스는 Java 로 만든 프로그램이라 Java 가 먼저 있어야 한다. 지금 젠킨스 LTS 는 Java 17 또는 21 에서 돈다. 우분투 24.04 에는 21 이 들어 있다. 우분투 터미널을 열고 친다. 

sudo apt update
sudo apt install -y fontconfig openjdk-21-jre
java -version
openjdk version "21.0.x" ...
OpenJDK Runtime Environment (build 21.0.x+...-Ubuntu-...)
OpenJDK 64-Bit Server VM ...

첫 줄에 21 이 보이면 된다. 뒤의 작은 숫자는 설치한 날에 따라 다르다.

JRE(Java Runtime Environment) — Java 프로그램을 실행만 하는 데 필요한 것. 개발 도구까지 들어 있는 건 JDK 다. 젠킨스를 돌리기만 하니 JRE 면 된다.
fontconfig — 글꼴 설정 라이브러리. 젠킨스가 그래프 그림을 만들 때 필요해서 공식 문서가 같이 깔라고 한다.
LTS(Long-Term Support) — 장기 지원판. 젠킨스는 매주 나오는 weekly 판과 12주마다 안정화해서 내는 LTS 판이 있다. 회사 서버에는 LTS 를 쓴다.

2. 젠킨스 LTS 설치

우분투 기본 저장소에는 젠킨스가 없다. 젠킨스가 운영하는 apt 저장소를 추가하고 거기서 받는다. 아래는 공식 설치 문서의 Debian/Ubuntu LTS 줄이다. 

# 1) 젠킨스 저장소의 서명 키를 받아 둔다
sudo mkdir -p /etc/apt/keyrings
sudo wget -O /etc/apt/keyrings/jenkins-keyring.asc \
  https://pkg.jenkins.io/debian-stable/jenkins.io-2026.key

# 2) 저장소 주소를 등록한다 (이 키로 서명된 것만 믿는다)
echo "deb [signed-by=/etc/apt/keyrings/jenkins-keyring.asc] https://pkg.jenkins.io/debian-stable binary/" \
  | sudo tee /etc/apt/sources.list.d/jenkins.list > /dev/null

# 3) 목록을 새로 받고 설치
sudo apt update
sudo apt install -y jenkins

주의: 키 파일 이름은 몇 년마다 바뀐다. 2025년 12월에 jenkins.io-2023.key 에서 jenkins.io-2026.key 로 바뀌었고(2026-11-10 공식 문서 기준), 인터넷의 예전 글에는 아직 2023 이 많다. apt update 에서 NO_PUBKEY 나 is not signed 같은 에러가 나면 키가 낡은 것이다. 위 공식 문서를 열어 지금 적혀 있는 줄로 1)·2) 를 다시 한다.

apt 저장소 — 우분투가 프로그램을 받아 오는 창고 주소 목록. /etc/apt/sources.list.d/ 에 파일을 하나 넣으면 창고가 하나 늘어난다.
서명 키(GPG key) — 창고에서 받은 파일이 진짜 젠킨스가 만든 것인지 확인하는 열쇠. 키가 없거나 다르면 apt 가 설치를 거부한다. 중간에 누가 파일을 바꿔치기하는 걸 막는 장치다.

설치가 끝나면 젠킨스는 서비스로 등록돼 바로 켜진다. 상태를 본다.

systemctl status jenkins
● jenkins.service - Jenkins Continuous Integration Server
     Loaded: loaded (/usr/lib/systemd/system/jenkins.service; enabled; ...)
     Active: active (running) since ...
   Main PID: 1234 (java)

active (running) 이 보이면 된다. q 를 눌러 빠져나온다. 처음 켜질 때 1분 가까이 걸릴 수 있어서, activating 이면 잠깐 기다렸다가 다시 본다.

systemd·서비스 — 리눅스에서 "켜 두고 계속 돌아야 하는 프로그램"을 관리하는 장치. 서버가 켜지면 자동으로 띄우고, 죽으면 다시 살리고, 로그를 모아 둔다. systemctl 이 그 리모컨이다.
enabled — 서버(여기서는 WSL)가 켜질 때 자동으로 시작하도록 등록돼 있다는 뜻.

WSL 에서 System has not been booted with systemd 가 나오면 systemd 가 꺼져 있는 것이다. 실습 환경 준비 글의 /etc/wsl.conf 설정을 확인하고, 윈도우 PowerShell 에서 wsl --shutdown 뒤 우분투를 다시 연다.

3. 브라우저로 첫 설정

3-1. 잠금 풀기 (Unlock Jenkins)

윈도우 브라우저에서 http://localhost:8080 을 연다. WSL2 는 우분투 안의 포트를 윈도우의 localhost 로 연결해 주기 때문에 그대로 열린다. Unlock Jenkins 화면이 나오고, 관리자 비밀번호를 넣으라고 한다. 이 비밀번호는 설치할 때 서버 안 파일에 적혀 있다. 

sudo cat /var/lib/jenkins/secrets/initialAdminPassword
3f9c0a6e1b2d4c5e8f7a9b0c1d2e3f4a     ← 32자리 글자. 사람마다 다르다

이 줄을 복사해서 Administrator password 칸에 붙여 넣고 Continue. 이 파일을 서버 안에서만 볼 수 있게 한 이유는, 젠킨스 주소를 아는 아무나 먼저 들어와서 관리자가 되는 걸 막으려는 것이다.

3-2. 플러그인 설치 (Customize Jenkins)

Install suggested plugins 를 누른다. Git, Pipeline, Credentials, JUnit 처럼 거의 모든 회사가 쓰는 플러그인 묶음이 깔린다. 인터넷 속도에 따라 몇 분 걸린다. 몇 개가 빨갛게 실패하면 Retry 를 누른다. 대개 일시적인 다운로드 실패다.

3-3. 관리자 계정 (Create First Admin User)

아이디, 비밀번호, 이름, 이메일을 넣는다. 이 계정이 앞으로 쓰는 관리자다. 실습이라도 admin/admin 같은 비밀번호는 쓰지 않는다. 습관이 회사 서버까지 따라간다. Save and Continue.

3-4. 주소 설정 (Instance Configuration)

Jenkins URL 에 http://localhost:8080/ 이 채워져 있다. 그대로 둔다. 이 값은 젠킨스가 이메일·알림·GitHub 상태 표시에 "자기 주소"를 적을 때 쓴다. 회사 서버라면 https://jenkins.회사.com/ 처럼 다른 사람이 들어올 수 있는 주소를 넣는다. Save and Finish → Start using Jenkins.

대시보드가 나오면 설치는 끝이다. 왼쪽 위 "Jenkins" 로고를 누르면 언제든 이 첫 화면으로 돌아온다.

대시보드(dashboard) — 젠킨스 첫 화면. 잡 목록과 각 잡의 마지막 빌드 상태(초록 체크·빨간 X), 날씨 아이콘(최근 빌드들이 얼마나 성공했나)이 보인다.

4. 관리 화면 둘러보기

왼쪽 메뉴 또는 오른쪽 위 톱니바퀴의 Manage Jenkins 로 들어간다. 메뉴가 많지만 실습에서 실제로 쓰는 건 네 개다.

메뉴하는 일이 시리즈에서
System젠킨스 전체 설정. Jenkins URL, 관리자 이메일, 전역 환경 변수, 각 플러그인의 전역 설정주소 바꿀 때
Plugins플러그인 설치·업데이트·삭제. Available plugins 에서 검색해 설치9번 글에서 Docker Pipeline 등을 더 깐다
Nodes빌드를 돌리는 컴퓨터 목록과 실행자 수. 에이전트 추가도 여기아래 보안 기본값
Credentials비밀번호·토큰·SSH 키를 암호화해서 보관. 잡에서는 ID 로만 부른다바로 아래에서 github-token 등록

그 밖에 Security(누가 무엇을 할 수 있나), Users(계정), Tools(JDK·Git·Maven 같은 도구 위치), System Log(젠킨스 자체 로그), Script Console(관리자용 Groovy 실행 창 — 서버 전체를 건드릴 수 있어서 조심)이 있다. 화면 위쪽에 노란 경고(업데이트 있음, 보안 경고)가 뜨면 무시하지 말고 한 번씩 읽는다.

5. GitHub 자격 증명 등록 — github-token

실습 저장소 cicd-hello 는 공개라 받아 오는 데는 비밀번호가 필요 없다. 그래도 지금 등록해 두는 이유가 있다. 비공개 저장소를 받을 때, 그리고 13번 글에서 젠킨스가 GitHub 에 커밋을 push 할 때 이 자격 증명을 쓴다. 등록 방법은 어느 비밀값이든 똑같아서 한 번 익혀 두면 된다.

5-1. GitHub 에서 토큰 만들기

  1. GitHub 오른쪽 위 프로필 → Settings → Developer settings → Personal access tokens → Fine-grained tokens → Generate new token
  2. Token name: jenkins-local, Expiration: 30일 정도
  3. Repository access: Only select repositories → cicd-hello (나중에 만들 cicd-hello-manifests 는 그때 토큰 설정에서 추가할 수 있다)
  4. Permissions → Repository permissions → Contents: Read and write
  5. Generate token → 나온 github_pat_... 문자열을 복사. 이 화면을 닫으면 다시 볼 수 없다

PAT(Personal Access Token, 개인 접근 토큰) — GitHub 비밀번호 대신 쓰는 긴 문자열. 저장소·권한·만료일을 좁혀서 만들 수 있어서, 새어도 피해가 그 범위로 끝난다. GitHub 는 git 명령에 계정 비밀번호를 받지 않으니 토큰이 필수다.
Fine-grained token — 저장소 단위로 권한을 고르는 새 방식 토큰. 예전 방식(classic)은 내 모든 저장소에 권한이 걸려서 위험하다.

5-2. 젠킨스에 넣기

  1. Manage Jenkins → Credentials
  2. 표에서 Store 가 System, Domain 이 (global) 인 줄의 (global) 을 누른다
  3. + Add Credentials
  4. Kind: Username with password
  5. Username: GitHub 아이디 / Password: 방금 복사한 토큰
  6. ID: github-token (이 시리즈의 Jenkinsfile 이 이 이름으로 부른다. 철자가 다르면 못 찾는다)
  7. Description: GitHub PAT (cicd-hello) → Create

목록에 github-token 이 생기고, 비밀번호 칸은 다시 열어도 가려져 있다. 젠킨스는 이 값을 /var/lib/jenkins/credentials.xml 에 암호화해서 저장한다. 잡 설정과 Jenkinsfile 에는 값이 아니라 ID 만 적는다. 그래서 코드를 공개 저장소에 올려도 토큰은 새지 않는다.

자격 증명(credentials) — 젠킨스가 대신 들고 있는 비밀값(비밀번호, 토큰, SSH 키, 인증서). 빌드할 때만 꺼내 쓰고 로그에는 **** 로 가린다.
ID — 자격 증명을 부르는 이름. 사람이 읽는 Description 과 달리 잡과 Jenkinsfile 이 이 값으로 찾는다. 비워 두면 무작위 문자열이 붙어서 나중에 쓰기 불편하다.

6. 젠킨스 홈 폴더 — 모든 게 여기 있다

젠킨스의 설정, 잡, 빌드 기록, 플러그인은 전부 젠킨스 홈 한 폴더에 파일로 저장된다. 데이터베이스가 따로 없다.

sudo ls /var/lib/jenkins
경로무엇
config.xml젠킨스 전체 설정 (보안, 실행자 수 등)
jobs/잡이름/config.xml잡 하나의 설정. 화면에서 고친 내용이 여기 저장된다
jobs/잡이름/builds/번호/빌드 한 번의 기록. log 파일이 콘솔 출력이다
workspace/잡이름/워크스페이스. 코드를 받아 빌드하는 곳
plugins/설치된 플러그인 파일들
credentials.xml, secrets/자격 증명(암호화)과 그걸 푸는 열쇠. 함부로 복사해 돌리지 않는다
users/계정 정보

그래서 백업은 이 폴더를 통째로 하면 된다(workspace/ 는 다시 받으면 되니 빼도 된다). 서버를 옮길 때도 이 폴더를 옮긴다. 폴더 주인은 jenkins 라는 리눅스 사용자다. 젠킨스는 이 사용자 권한으로 돌기 때문에, 빌드에서 치는 명령도 전부 jenkins 사용자로 실행된다. 다음 글에서 배포할 때 이게 중요해진다. 

id jenkins
uid=xxx(jenkins) gid=xxx(jenkins) groups=xxx(jenkins)

JENKINS_HOME — 젠킨스 홈 폴더를 가리키는 이름. apt 로 깔면 /var/lib/jenkins, 도커로 띄우면 /var/jenkins_home(8번 글)이다.

7. 보안 기본값 두 가지

7-1. 로그인 안 한 사람은 아무것도 못 보게

Manage Jenkins → Security 에서 확인한다. 첫 설정 마법사를 거쳤다면 이미 이렇게 돼 있다.

  • Security Realm: Jenkins' own user database (젠킨스 안에 계정을 만든다)
  • Authorization: Logged-in users can do anything
  • 그 아래 Allow anonymous read access 는 꺼져 있어야 한다

익명 읽기를 켜면 로그인 안 한 사람도 잡 목록과 콘솔 출력을 본다. 콘솔에는 서버 경로, 내부 주소, 실수로 찍힌 비밀값이 섞이기 쉽다. 인터넷에 열린 젠킨스가 이 설정 하나로 털린 사례가 많다. 팀에서 쓸 때는 Matrix-based security 로 사람마다 권한을 나눈다.

7-2. 컨트롤러에서 빌드를 돌리는 문제

Manage Jenkins → Nodes → Built-In Node → Configure 를 보면 Number of executors 가 2 로 돼 있다. 컨트롤러 자신이 빌드를 두 개까지 돌린다는 뜻이다.

공식 권장은 0 이다. 컨트롤러에서 빌드가 돌면, 빌드 스크립트가 jenkins 사용자 권한으로 젠킨스 홈(secrets/ 포함)을 읽을 수 있기 때문이다. 그래서 회사에서는 컨트롤러는 관리만, 빌드는 에이전트에서 한다. 다만 이 실습은 서버가 한 대뿐이라 2 로 둔다. 0 으로 바꾸면 빌드가 영원히 "대기 중"에 머문다. 에이전트로 빌드를 내보내는 방식은 11번 글에서 쿠버네티스 파드로 해 본다.

Security Realm(보안 영역) — "이 사람이 누구인가"를 확인하는 방법. 젠킨스 자체 계정, 회사 LDAP, GitHub 로그인 등.
Authorization(권한 부여) — "확인된 사람이 무엇을 할 수 있나". 둘을 합쳐 인증·인가라고 부른다.

8. 끄고 켜기

sudo systemctl stop jenkins       # 끄기
sudo systemctl start jenkins      # 켜기
sudo systemctl restart jenkins    # 껐다 켜기 (플러그인 설치 뒤 등)
sudo systemctl disable jenkins    # WSL 켤 때 자동 시작 안 함 (enable 은 반대)
journalctl -u jenkins -f          # 젠킨스 로그 실시간 보기 (Ctrl+C 로 나감)

브라우저에서도 할 수 있다. 주소 뒤에 /safeRestart 를 붙여 열면 돌고 있는 빌드가 끝나길 기다렸다가 재시작한다. /restart 는 바로 재시작한다. 회사 서버에서는 남의 빌드를 끊지 않게 safeRestart 를 쓴다.

포트를 바꾸고 싶으면(8080 을 다른 프로그램이 쓰고 있을 때) 서비스 설정에 덮어쓴다. 

sudo systemctl edit jenkins
# 열린 편집기의 주석 사이 빈 곳에 적고 저장
[Service]
Environment="JENKINS_PORT=8081"
sudo systemctl restart jenkins

WSL 은 우분투 창을 다 닫고 몇 분 지나면 통째로 잠든다. 그러면 젠킨스도 같이 멈춘다. 실습 중에는 우분투 창을 하나 열어 둔다. 진짜 서버라면 이런 일은 없다.
