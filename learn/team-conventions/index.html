ROLE

팀 규칙에 맞추는 능력
— 사람도 AI 도 같은 규칙을 따르게

직무 ESLint Prettier EditorConfig 컨벤션 2026.10.28

팀 코드에서 가장 먼저 눈에 띄는 건 기능이 아니라 모양이다. 따옴표가 작은따옴표인지 큰따옴표인지, 들여쓰기가 2칸인지 4칸인지, 파일 이름이 posterEditor.tsx 인지 PosterEditor.tsx 인지. 하나하나는 사소한데, 섞이면 리뷰가 모양 얘기로 다 끝난다.

이 글의 요점은 하나다. 규칙은 사람의 기억이 아니라 도구와 문서에 둔다. 그러면 사람도, AI 도, 내일의 나도 같은 규칙을 따른다.

규칙이 사는 세 곳

도구 — 모양은 사람이 지키지 않는다

도구하는 일예
EditorConfig편집기 기본값을 맞춘다들여쓰기 2칸, 줄바꿈 LF, 파일 끝 빈 줄
Prettier (포매터)코드 모양을 저장할 때 자동으로 고친다따옴표, 줄 길이, 쉼표
ESLint (린터)모양이 아닌 실수를 잡는다안 쓰는 변수, == 대신 ===, React hook 규칙 위반
.gitattributes저장소 안 줄바꿈을 통일한다* text=auto eol=lf
# .editorconfig — 저장소 맨 위에 둔다
root = true

[*]
indent_style = space
indent_size = 2
end_of_line = lf
insert_final_newline = true
charset = utf-8

줄바꿈은 실제로 당한 적이 있다. 다이어리 저장소에서 커밋 안 된 변경이 3,316줄로 보였는데 의미 있는 변경은 86줄이었다. 나머지는 윈도우의 줄바꿈(CRLF)과 리눅스·맥의 줄바꿈(LF)이 섞여 생긴 가짜 변경이었다. 팀이었다면 리뷰어가 진짜 변경을 찾을 수 없었을 것이다. .editorconfig 와 .gitattributes 두 파일이면 처음부터 막힌다.

린터(linter) — 코드를 실행하지 않고 읽어서 실수일 가능성이 높은 패턴을 찾아 주는 도구.
포매터(formatter) — 코드의 뜻은 그대로 두고 모양(띄어쓰기·줄바꿈·따옴표)만 정해진 대로 바꾸는 도구. 모양 논쟁을 없앤다.
CRLF / LF — 줄을 바꾸는 보이지 않는 문자. 윈도우는 두 글자(CR+LF), 맥·리눅스는 한 글자(LF). 섞이면 모든 줄이 바뀐 것처럼 보인다.

저장할 때 · 커밋할 때 · PR 때

도구는 세 번 건다. 편집기가 저장할 때 Prettier 를 돌리고, 커밋할 때 바뀐 파일만 린트하고(husky + lint-staged), PR 이 열리면 CI 가 전체를 한 번 더 본다. 앞에서 놓쳐도 뒤에서 잡힌다.

이름과 폴더 — 예측할 수 있게

좋은 규칙의 기준은 "처음 온 사람이 파일 위치를 찾지 않고 짐작할 수 있나"다.

정할 것흔한 규칙
컴포넌트 파일PascalCase.tsx — 다이어리의 src/screens/PosterEditor.tsx 처럼
함수 · 변수camelCase, 불리언은 is·has로 시작 (hasPremium)
상수UPPER_SNAKE — TRIAL_DAYS = 7
폴더종류별(screens/, components/) 또는 기능별(diary/, meal/). 섞지 않는다
브랜치 · 커밋feat/…, fix/… · 커밋 메시지 언어와 형식

문서 — AI 도 읽는 규칙

나는 프로젝트마다 CLAUDE.md 를 둔다. AI 가 작업을 시작할 때 읽는 설명서다. 그런데 써 보니 이건 사람에게도 그대로 필요한 문서다. 예를 들어 gangmini 사이트의 CLAUDE.md 에는 이런 규칙이 있다.

  • "빌드 단계를 늘리지 않는다. 허브는 순수 HTML/CSS/JS다."
  • "note.css 를 고치면 그 파일을 불러오는 html 의 ?v= 숫자를 함께 올린다." (이유: 4시간 캐시)
  • "SVG 는 반드시 .fig__scroll 로 감싼다." (이유: 폰에서 글씨가 6px 가 된다)

셋 다 규칙 + 이유다. 이유가 같이 있으면 사람은 납득하고, AI 는 비슷한 다른 상황에도 같은 판단을 한다.

파일누가 읽나담는 것
README.md처음 온 사람이게 뭔가, 어떻게 실행하나
CONTRIBUTING.md코드를 고치려는 사람브랜치·커밋 규칙, 테스트 방법, PR 절차
CLAUDE.md · AGENTS.mdAI 도구 (그리고 사람)구조, 하지 말 것, 지켜야 할 규칙과 이유

둘레의 코드를 따라 쓴다

문서에 없는 건 이미 있는 코드가 규칙이다. 새 화면을 만들 때 옆 화면이 상태를 어떻게 다루는지, 에러를 어떻게 보여 주는지 먼저 본다. "내 방식이 더 낫다"고 생각해도, 한 파일 안에 두 방식이 섞이는 것보다는 기존 방식이 낫다. 바꾸고 싶으면 따로 제안해서 한 번에 바꾼다.

AI 에게 일을 맡길 때도 같다. "이 폴더의 다른 화면과 같은 방식으로"라고 붙이면 결과가 훨씬 팀 코드처럼 나온다.
