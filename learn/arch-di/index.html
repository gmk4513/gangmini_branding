— 직접 넣기부터 컨테이너까지

실습 Python DI dependency-injector FastAPI pytest 2026.10.28

앞 글에서 메모 API 를 router · service · repository 세 층으로 나눴다. 그때 서비스가 저장소를 "직접 만들지 않고 받는다"고만 하고 넘어갔다. 이 글은 그 "받는다"를 파고든다. 취업 준비하며 본 설계 자료에서 container.py 에 의존 관계를 모아 둔 걸 보고, 왜 그렇게 하는지 직접 돌려 보며 이해한 과정이다.

한 줄로 줄이면 이렇다. 부품이 자기 부품을 직접 만들지 말고, 바깥에서 끼워 받게 한다. 그리고 누가 누구를 끼우는지는 한 곳(컨테이너)에 적어 둔다.

문제 — 서비스가 저장소를 직접 만들면

class MemoService:
    def __init__(self) -> None:
        conn = sqlite3.connect("memo.db")
        self.repository = SqliteMemoRepository(conn)   # 안에서 직접 만든다

얼핏 편해 보인다. 쓰는 쪽은 MemoService() 만 부르면 된다. 그런데 이러면 세 가지가 막힌다.

  • 테스트가 진짜 DB 를 건드린다. 서비스를 시험하려고 만들기만 해도 memo.db 파일이 생기고, 이전 테스트가 남긴 데이터가 다음 테스트에 섞인다.
  • 저장소를 못 바꾼다. 앞 글의 "바꿔 끼우기"가 안 된다. 바꾸려면 서비스 코드를 고쳐야 한다.
  • 설정이 숨는다. DB 경로 "memo.db" 가 서비스 깊숙이 박혀 있다. 운영과 테스트에서 다른 DB 를 쓰기 어렵다.

전기 제품으로 생각하면 쉽다. 선풍기 안에 발전기를 넣어 팔지 않는다. 선풍기는 플러그(약속된 모양)만 갖고, 전기는 벽(바깥)이 넣어 준다. 그래서 집에서든 사무실에서든, 발전기든 배터리든 같은 선풍기를 쓸 수 있다.

의존(dependency) — A 가 일하려면 B 가 필요할 때 "A 는 B 에 의존한다"고 한다. MemoService 는 저장소에 의존한다.
의존성 주입(Dependency Injection, DI) — 필요한 B 를 A 가 직접 만들지 않고, 바깥에서 만들어 A 에게 넣어 주는 방식.

1단계 — 손으로 넣기 (생성자 주입)

따라 하기 — 이 글의 예제 코드는 github.com/gmk4513/memo-api-practice 에 있다. dev 브랜치가 한 파일짜리 시작 상태, solution 브랜치가 완성본이다. 처음부터 해 보려면 실습 글의 순서를 따른다. 명령은 VS Code 안의 터미널에서 친다 → 실습 환경 준비. 

# src/memo/service.py
class MemoService:
    def __init__(self, repository: MemoRepository) -> None:   # 받는다
        self.repository = repository

이게 DI 의 전부다. 라이브러리도 필요 없다. 타입은 구현(SqliteMemoRepository)이 아니라 약속(MemoRepository)으로 적는다. 이제 쓰는 쪽이 무엇을 넣을지 고른다. 

# 운영: 진짜 DB
service = MemoService(repository=SqliteMemoRepository(sqlite3.connect("memo.db")))

# 테스트: dict 저장소
service = MemoService(repository=InMemoryMemoRepository())

바로 얻는 것 — DB 없는 테스트

2단계 — 조립이 늘어나면: 컨테이너

부품이 몇 개일 땐 손으로 넣어도 된다. 그런데 모듈이 늘면 조립 코드가 길어지고 여기저기 흩어진다. user 모듈의 ProfileService 는 MemoService 가 필요하고, 그건 저장소가, 저장소는 DB 연결이 필요하다. 이 "누가 누구를 쓰나"를 한 파일에 적어 두고, 실제로 만들어 끼우는 일까지 맡기는 게 DI 컨테이너다. 파이썬에서는 dependency-injector 라이브러리를 썼다. 

# src/memo/container.py — memo 모듈 안의 지도
class MemoContainer(containers.DeclarativeContainer):
    db = providers.Dependency(instance_of=sqlite3.Connection)   # 바깥이 넣어 준다

    repository = providers.Singleton(SqliteMemoRepository, conn=db)
    service = providers.Singleton(MemoService, repository=repository)


# src/user/container.py
class UserContainer(containers.DeclarativeContainer):
    memo_service = providers.Dependency(instance_of=MemoService)

    profile_service = providers.Singleton(ProfileService, memo_service=memo_service)


# src/container.py — 앱 전체 지도. 모듈 컨테이너를 엮는다
class AppContainer(containers.DeclarativeContainer):
    config = providers.Configuration()

    db = providers.Singleton(sqlite3.connect, config.db_path, check_same_thread=False)

    memo = providers.Container(MemoContainer, db=db)
    user = providers.Container(UserContainer, memo_service=memo.service)

provider 종류 — 어떻게 만들어 줄지

provider하는 일여기서 쓴 곳
Singleton처음 한 번 만들고, 그 뒤로는 같은 것을 준다DB 연결, 저장소, 서비스
Factory부를 때마다 새로 만든다요청마다 상태가 달라야 하는 것 (이 앱엔 없음)
Configuration설정 값을 담는다. 파일·환경 변수·코드로 채운다config.db_path
Dependency"여긴 바깥이 채워 줘" 하고 비워 둔 자리MemoContainer 의 db
Container다른 컨테이너를 통째로 끼운다AppContainer 의 memo, user

Singleton 과 Factory 의 차이, 그리고 바꿔 끼우기(override)를 직접 눌러 봤다.

# provider_demo.py
class Box(containers.DeclarativeContainer):
    factory = providers.Factory(list)      # 부를 때마다 새로
    singleton = providers.Singleton(list)  # 한 번만

box = Box()
print("Factory   같은 객체?", box.factory() is box.factory())
print("Singleton 같은 객체?", box.singleton() is box.singleton())

app = AppContainer(); app.config.db_path.from_value(":memory:")
print("기본 저장소:", type(app.memo.service().repository).__name__)

app2 = AppContainer(); app2.config.db_path.from_value(":memory:")
with app2.memo.repository.override(providers.Singleton(InMemoryMemoRepository)):
    print("override 중:", type(app2.memo.service().repository).__name__)

컨테이너 — 여기서는 "부품 목록 + 조립 설명서"를 들고 있다가, 요청하면 조립된 부품을 내주는 객체. 도커의 컨테이너와는 다른 말이다.
provider — 컨테이너 안에서 "이 부품을 어떻게 만들지"를 정한 항목 하나.

3단계 — 수명: 앱에 한 번 vs 요청마다

자료에서 가장 와닿은 부분이 이거였다. 컨테이너는 앱이 켜질 때 한 번 만들고, 앱이 꺼질 때까지 재활용한다(앱 수명 = 컨테이너 수명). 반면 FastAPI 의 기본 의존성(Depends)은 요청이 올 때마다 함수를 다시 부른다. 그 함수 안에서 무거운 객체를 만들면, 요청마다 새로 만든다.

정말 그런지 세어 봤다. 만들기 비싼 객체(HeavyClient)가 몇 번 만들어지는지 출력하게 했다.

# lifecycle_demo.py
class HeavyClient:
    made = 0
    def __init__(self) -> None:
        HeavyClient.made += 1
        print(f"  HeavyClient 생성 #{HeavyClient.made}")

class Container(containers.DeclarativeContainer):
    heavy = providers.Singleton(HeavyClient)

def per_request() -> HeavyClient:      # FastAPI 의존성: 요청마다 불린다
    return HeavyClient()

app = FastAPI()
app.state.container = Container()      # 앱이 켜질 때 한 번

@app.get("/a")
def a(heavy: HeavyClient = Depends(per_request)): ...

@app.get("/b")
def b(request: Request):
    heavy = request.app.state.container.heavy()
    ...

그래서 memo-api 에서는 앱을 조립할 때 컨테이너를 한 번 만들어 app.state 에 붙여 두고, 라우터의 의존성 함수는 그걸 꺼내기만 하게 했다. 의존성 함수 자체는 요청마다 불리지만, 꺼내는 건 이미 만들어 둔 Singleton 이라 새로 만들지 않는다. 

# webapp/main.py
def create_app(db_path: str = "memo.db", container: AppContainer | None = None) -> FastAPI:
    if container is None:
        container = AppContainer()
        container.config.db_path.from_value(db_path)
    app = FastAPI(title="memo-api")
    app.state.container = container          # 앱 수명 = 컨테이너 수명
    app.include_router(memo.router)
    ...

# webapp/routers/memo.py
def memo_service(request: Request) -> MemoService:
    return request.app.state.container.memo.service()   # 꺼내기만 한다

dependency-injector 에는 @inject 와 Provide[...] 로 라우터에 바로 꽂아 주는 "wiring" 기능도 있다. 나는 흐름을 눈으로 따라가기 쉬워서 app.state 에서 꺼내는 방식을 썼다. 어느 쪽이든 핵심은 같다. 만드는 건 한 번, 쓰는 건 여러 번.

4단계 — 테스트에서 바꿔 끼우기 (override)

컨테이너의 진짜 힘은 테스트에서 나온다. 앱 전체(라우터 → 서비스 → 저장소)를 그대로 두고, 저장소 하나만 dict 저장소로 바꿔 끼운다. 라우터·서비스 코드는 테스트 때문에 한 줄도 바뀌지 않는다. 

# tests/conftest.py
@pytest.fixture
def container():
    c = AppContainer()
    c.config.db_path.from_value(":memory:")
    c.memo.repository.override(providers.Singleton(InMemoryMemoRepository))
    yield c
    c.memo.repository.reset_override()

@pytest.fixture

create_app 이 컨테이너를 인자로 받을 수 있게 한 것도 같은 이유다. 앱을 조립하는 함수 자체도 "받는" 구조라서, 테스트가 미리 손본 컨테이너를 넣을 수 있다.

정리

단계한 일얻은 것
직접 만들기서비스 안에서 SqliteMemoRepository()(문제) 테스트가 진짜 DB 를 쓴다, 못 바꾼다
생성자 주입MemoService(repository=…)가짜 저장소로 DB 없는 테스트
컨테이너container.py 에 누가 누구를 쓰는지조립을 한 곳에서, 의존 관계가 한눈에
수명앱 시작 때 한 번 만들고 app.state 에비싼 객체를 요청마다 다시 만들지 않는다
override테스트에서 저장소만 바꿔 끼움앱 전체를 그대로 두고 HTTP 까지 시험

처음엔 "그냥 import 해서 쓰면 되지 왜 이렇게 돌아가나" 싶었다. 직접 만들어 보니 DI 는 코드를 줄이는 기술이 아니라 바꿀 수 있는 자리를 미리 만들어 두는 기술이었다. 그 자리가 있으니 테스트에서는 가짜를, 운영에서는 진짜를, 나중에는 다른 DB 를 끼울 수 있다.
