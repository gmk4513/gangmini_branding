패키지와 모듈 나누기
— 기능별? 도메인별? 그리고 참조 방향

이론 Python 순환 참조 logging 패키지 구조 2026.10.28

앞 글에서 코드를 세 층으로 나눴다. 이번엔 한 단계 바깥, 폴더(패키지)를 어떻게 자르고 서로 어느 쪽으로 부르게 할지를 본다. 예시는 그대로 memo-api 다.

src 와 webapp — 주방과 홀

memo-api/
├── src/        ← 비즈니스 로직. HTTP 가 뭔지 모른다
├── webapp/     ← FastAPI. 요청을 받아 src 를 부른다
└── tests/      ← src 를 직접 부른다 (서버를 안 띄워도 된다)

식당으로 치면 src 는 주방, webapp 은 홀이다. 주방은 주문이 홀에서 왔는지 배달 앱에서 왔는지 몰라도 요리를 한다. 그래서 같은 src 를 웹 서버(webapp), 테스트(tests), 나중에 배치 스크립트나 CLI 에서도 그대로 쓸 수 있다.

참조는 한 방향 — webapp → src, 거꾸로는 금지

거꾸로 부르면 실제로 이렇게 된다

말로만 들으면 "그냥 지저분해지는 거 아냐?" 싶어서 직접 만들어 봤다. webapp/main.py 가 서비스를 부르고, 서비스가 앱 이름을 쓰려고 webapp 을 거꾸로 부른다. 

# webapp/main.py
from src.memo.service import MemoService

APP_NAME = "memo-api"

# src/memo/service.py
from webapp.main import APP_NAME   # src 가 webapp 을 거꾸로 참조한다

class MemoService:
    pass
$ python -c "import webapp.main"
  File "...\webapp\main.py", line 1, in <module>
    from src.memo.service import MemoService
  File "...\src\memo\service.py", line 1, in <module>
    from webapp.main import APP_NAME   # src 가 webapp 을 거꾸로 참조한다
    ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
ImportError: cannot import name 'APP_NAME' from partially initialized module 'webapp.main' (most likely due to a circular import)

파이썬은 webapp.main 을 읽기 시작하자마자 첫 줄에서 service 를 읽으러 간다. 그런데 service 가 다시 webapp.main 을 찾는다. webapp.main 은 아직 첫 줄에 멈춰 있어서 APP_NAME 이 만들어지기 전이다. 그래서 "반쯤 만들어진 모듈(partially initialized module)"이라는 말이 나온다. 이게 순환 참조다. 에러가 안 나는 경우에도(함수 안에서 import 하는 식으로 피해 가면) 두 패키지가 서로를 붙잡고 있어서 하나만 떼어 낼 수 없게 된다.

가장 흔한 함정: 로거

순환 참조가 가장 잘 생기는 곳이 로그다. "로그를 JSON 으로 예쁘게 찍는 설정"을 webapp 에 만들어 두고, 서비스에서 로그를 남기려고 그 설정을 import 하는 순간 화살표가 거꾸로 선다.

푸는 방법은 역할을 둘로 쪼개는 것이다. src 는 무엇을 남길지(내용)만, webapp 은 어떻게 남길지(형식)만 정한다. 파이썬 logging 은 원래 이렇게 나뉘어 있다. getLogger(__name__) 로 받은 로거는 내용만 넘기고, 형식은 프로그램 시작점에서 붙인 핸들러·포매터가 정한다. 

# src/memo/service.py — 무엇을 남길지만
import logging

logger = logging.getLogger(__name__)

class MemoService:
    def create(self, user_id: int, title: str) -> int:
        memo_id = 42
        logger.info("메모를 만들었다", extra={"memo_id": memo_id, "user_id": user_id})
        return memo_id

# webapp/logging_setup.py — 어떻게 남길지 (서비스용: JSON 한 줄)
class JsonFormatter(logging.Formatter):
    def format(self, record):
        data = {"level": record.levelname, "logger": record.name, "msg": record.getMessage()}
        for key in ("memo_id", "user_id"):
            if hasattr(record, key):
                data[key] = getattr(record, key)
        return json.dumps(data, ensure_ascii=False)

def setup_logging():
    handler = logging.StreamHandler()
    handler.setFormatter(JsonFormatter())
    logging.getLogger().handlers[:] = [handler]
    logging.getLogger().setLevel(logging.INFO)

같은 MemoService().create(...) 를 두 곳에서 불러 봤다. 서비스 코드는 한 글자도 안 바꿨다.

# 웹 서버에서 (setup_logging 을 부른 뒤)
{"level": "INFO", "logger": "src.memo.service", "msg": "메모를 만들었다", "memo_id": 42, "user_id": 7}

# 테스트에서 (basicConfig 로 사람이 읽기 좋은 한 줄)
INFO src.memo.service: 메모를 만들었다

폴더를 무엇으로 자를까 — 기능별 vs 도메인별

같은 코드를 두 방식으로 담아 보면 차이가 보인다.

# 기능(역할)별                    # 도메인별
src/                               src/
├── routers/                       ├── memo/
│   ├── memo.py                    │   ├── domains.py
│   └── user.py                    │   ├── entities.py
├── services/                      │   ├── repository.py
│   ├── memo.py                    │   ├── service.py
│   └── user.py                    │   └── container.py
├── repositories/                  ├── user/
│   ├── memo.py                    │   └── (같은 다섯 파일)
│   └── user.py                    └── common/
└── models/                            ├── exceptions.py
    ├── memo.py                        └── logger.py
    └── user.py
기능별도메인별
처음 보기익숙하다. 튜토리얼이 대부분 이 모양폴더 이름이 곧 서비스가 하는 일의 목록
메모 기능 하나 고칠 때폴더 네 군데를 오간다memo/ 한 폴더 안에서 끝난다
기능이 늘면각 폴더에 파일이 수십 개씩 쌓인다폴더가 하나씩 는다
나중에 떼어 내기여기저기 흩어져 있어 어렵다폴더째 들어서 다른 서비스로 옮기기 쉽다
잘 맞는 곳작은 프로젝트, 도메인이 한두 개도메인이 여럿인 백엔드

실무에서 많이 보는 건 섞은 모양이다. 바깥은 도메인별(memo/, user/)로 자르고, 그 안은 기능별 파일(repository.py, service.py)로 나눈다. 그리고 여러 도메인이 같이 쓰는 것만 common/ 에 둔다. 프론트엔드도 비슷해서 features/memo, features/auth 처럼 기능 단위 폴더를 많이 쓴다.

도메인 폴더 하나 안의 파일들

파일하는 일누가 부르나
domains.py도메인 객체 Memo. 서비스가 생각하는 메모모두
entities.pyDB 테이블 한 줄 MemoRowrepository 만
repository.py저장·조회. 엔티티 ↔ 도메인 변환service 만
service.py규칙과 흐름webapp, tests
container.py이 모듈의 부품 조립도앱 시작점

표의 "누가 부르나" 칸이 곧 참조 방향이다. entities.py 는 저장소 말고는 아무도 몰라야 한다. 이 이야기는 다음 글에서 "데이터 주권"이라는 이름으로 이어진다.

패키지 · 모듈 — 파이썬에서 .py 파일 하나가 모듈, __init__.py 가 든 폴더가 패키지다. 이 글에서 "모듈"은 memo/ 같은 도메인 폴더 한 덩어리를 가리키기도 한다.
순환 참조(circular import) — A 가 B 를, B 가 다시 A 를 import 하는 것. 파이썬에서는 "partially initialized module" 에러로 드러난다.
핸들러 · 포매터 — logging 에서 로그를 어디로 보낼지(핸들러), 어떤 모양으로 찍을지(포매터)를 맡는 부품.

정리

약속한 줄 이유
src 와 webapp 을 나눈다같은 로직을 웹·테스트·배치에서 그대로 쓴다
참조는 webapp → src 한 방향거꾸로 가면 순환 참조, 떼어 낼 수 없는 덩어리
로그는 내용(src)과 형식(webapp)을 나눈다서비스는 JSON, 테스트는 한 줄. 코드는 그대로
바깥은 도메인별, 안은 역할별한 기능을 고칠 때 한 폴더 안에서 끝난다
