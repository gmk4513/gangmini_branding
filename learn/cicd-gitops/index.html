PRACTICE · CI/CD 13/13

ArgoCD 로 배포 자동화
— 커밋 하나가 운영까지

실습 GitOps ArgoCD Jenkins Kaniko 롤백 2026.11.10

11편에서 젠킨스가 이미지를 만들어 Docker Hub 에 올렸다(CI). 12편에서 ArgoCD 가 Git 의 매니페스트대로 클러스터를 맞췄다(CD). 그런데 둘 사이가 아직 끊겨 있다. 새 이미지가 나와도 매니페스트의 image: 태그는 사람이 고쳐야 한다.

이 글에서 그 마지막 한 칸을 젠킨스에게 맡긴다. 젠킨스는 이미지를 올린 뒤 매니페스트 저장소의 태그 한 줄을 고쳐 커밋만 한다. 클러스터에는 손대지 않는다. 그 커밋을 ArgoCD 가 보고 배포한다. 이렇게 되면 개발자는 앱 코드를 push 하는 것 말고는 아무것도 안 해도 된다.

이번 단계에서 할 것

  1. 젠킨스에 매니페스트 저장소에 쓸 수 있는 GitHub 토큰 넣기
  2. Jenkinsfile.gitops — 11편 파이프라인 끝에 "매니페스트 태그 고쳐 커밋" 단계 붙이기
  3. 앱 문구를 바꿔 push 하고, 운영(클러스터)까지 저절로 바뀌는 걸 끝까지 따라가 보기
  4. 테스트가 깨지면 멈추는 것, git revert 로 되돌리는 것 확인

끝나면: app.py 를 고쳐 push 하고 몇 분 기다리면 curl localhost:8200/ 의 답이 바뀐다. 그 사이 사람은 아무것도 누르지 않는다.

전체 흐름

왜 저장소를 둘로 나누나

앱 코드와 매니페스트를 한 저장소에둘로 나눔 (이 시리즈)
무한 반복젠킨스가 태그를 커밋 → 그 커밋이 또 젠킨스를 깨움 → 또 빌드… 막으려면 "봇 커밋은 건너뛰기" 규칙이 따로 필요젠킨스는 앱 저장소만 보고, 커밋은 매니페스트 저장소에만 한다. 고리가 안 생긴다
기록"기능 고침"과 "배포: 태그 12" 커밋이 섞인다매니페스트 저장소의 커밋 목록 = 배포 이력 그 자체
권한앱 개발자 누구나 운영 설정을 바꿀 수 있다운영 저장소는 승인 규칙을 따로 건다
되돌리기배포만 되돌리려 해도 코드 기록과 엉킨다매니페스트에서 revert 하면 코드는 그대로, 배포만 뒤로

매니페스트 저장소(config repo, GitOps repo) — "무엇이 어떤 설정으로 배포되어 있어야 하나"만 담은 저장소. 앱 저장소와 나누는 게 ArgoCD 공식 문서의 권장이다.
봇 커밋 — 사람이 아니라 자동화 도구가 만든 커밋. 작성자 이름을 jenkins-bot 처럼 따로 둬서 사람 커밋과 구별한다.

1. 젠킨스에 쓰기 토큰 넣기

젠킨스가 매니페스트 저장소에 push 하려면 쓰기 권한이 필요하다. 3편에서 만든 fine-grained PAT 를 쓴다 (저장소: cicd-hello-manifests 포함, 권한: Contents Read and write). 없다면 GitHub → Settings → Developer settings → Fine-grained tokens 에서 만든다.

  1. 11편의 젠킨스(http://localhost:8095, port-forward 켜기) → Manage Jenkins → Credentials
  2. System → Global credentials → Add Credentials
  3. Kind Username with password, Username = GitHub 아이디, Password = PAT, ID = github-token → Create

fine-grained PAT — 저장소와 권한을 골라서 주는 GitHub 토큰. "이 저장소 하나에 내용 쓰기만" 처럼 좁힐 수 있어서, 새어 나가도 피해가 그 저장소에 그친다. 옛 방식(classic)은 계정 전체 저장소에 권한이 간다.
자격 증명 ID — Jenkinsfile 이 비밀값을 부르는 이름. Jenkinsfile 에는 토큰이 아니라 github-token 이라는 이름만 적힌다.

2. Jenkinsfile.gitops 쓰기

cicd-hello 저장소에 Jenkinsfile.gitops 를 만든다. 11편의 Jenkinsfile.k8s 를 복사하고 끝에 Update manifest 단계만 더한 것이다. <도커허브아이디> 를 바꾼다. 

cd ~/cicd/cicd-hello
cp Jenkinsfile.k8s Jenkinsfile.gitops
// Jenkinsfile.gitops — 테스트 → Kaniko 빌드·푸시 → 매니페스트 태그 커밋 (배포는 ArgoCD 가)
pipeline {
  agent {
    kubernetes {
      yaml '''
apiVersion: v1
kind: Pod
spec:
  containers:
    - name: python
      image: python:3.12-slim
      command: ["sleep"]
      args: ["infinity"]
    - name: kaniko
      image: gcr.io/kaniko-project/executor:debug
      command: ["/busybox/cat"]
      tty: true
      volumeMounts:
        - name: docker-config
          mountPath: /kaniko/.docker
  volumes:
    - name: docker-config
      secret:
        secretName: dockerhub-cred
        items:
          - key: .dockerconfigjson
            path: config.json
'''
    }
  }

  environment {
    IMAGE = '<도커허브아이디>/cicd-hello'
    MANIFEST_REPO = 'cicd-hello-manifests'
  }

  options {
    timeout(time: 20, unit: 'MINUTES')
    buildDiscarder(logRotator(numToKeepStr: '20'))
    disableConcurrentBuilds()          // 두 빌드가 동시에 매니페스트를 고치지 않게
  }

  triggers {
    pollSCM('H/2 * * * *')
  }

  stages {
    stage('Tag') {
      steps {
        script {
          def shortSha = sh(script: 'git rev-parse --short=7 HEAD', returnStdout: true).trim()
          env.IMAGE_TAG = "${env.BUILD_NUMBER}-${shortSha}"
        }
        echo "이번 이미지: ${env.IMAGE}:${env.IMAGE_TAG}"
      }
    }

    stage('Test') {
      steps {
        container('python') {
          sh '''
            python -m venv /tmp/venv
            . /tmp/venv/bin/activate
            pip install -q -r requirements-dev.txt
            python -m pytest -q --junitxml=test-results.xml
          '''
        }
      }
      post {
        always { junit 'test-results.xml' }
      }
    }

    stage('Build & Push') {
      steps {
        container(name: 'kaniko', shell: '/busybox/sh') {
          sh '''#!/busybox/sh
            /kaniko/executor \
              --context="$WORKSPACE" \
              --dockerfile="$WORKSPACE/Dockerfile" \
              --build-arg "APP_VERSION=$IMAGE_TAG" \
              --destination="$IMAGE:$IMAGE_TAG" \
              --skip-unused-stages
          '''
        }
      }
    }

    stage('Update manifest') {
      steps {
        withCredentials([usernamePassword(credentialsId: 'github-token',
                                          usernameVariable: 'GIT_USER',
                                          passwordVariable: 'GIT_TOKEN')]) {
          sh '''
            rm -rf manifests
            git clone --depth 1 "https://${GIT_USER}:${GIT_TOKEN}@github.com/${GIT_USER}/${MANIFEST_REPO}.git" manifests
            cd manifests

            # image: 줄의 태그만 새것으로
            sed -i "s|image: .*/cicd-hello:.*|image: ${IMAGE}:${IMAGE_TAG}|" k8s/deployment.yaml
            git diff

            git config user.name  "jenkins-bot"
            git config user.email "jenkins-bot@users.noreply.github.com"
            git commit -am "배포: cicd-hello ${IMAGE_TAG}"
            git push origin HEAD:main
          '''
        }
      }
    }
  }

  post {
    success { echo "매니페스트를 ${env.IMAGE_TAG} 로 올렸다. 이제 ArgoCD 가 배포한다." }
    failure { echo '실패. 매니페스트는 바뀌지 않았으니 운영은 그대로다.' }
  }
}
새로 생긴 것뜻
disableConcurrentBuilds()빌드가 겹치면 두 빌드가 동시에 매니페스트를 push 하다 하나가 거절당한다. 한 번에 하나씩
withCredentials([usernamePassword(…)])1번의 github-token 을 이 블록 안에서만 GIT_USER·GIT_TOKEN 환경변수로 꺼낸다. 로그에 찍히면 젠킨스가 **** 로 가린다
sh '''…''' (작은따옴표 세 개)${GIT_TOKEN} 을 젠킨스(Groovy)가 아니라 셸이 풀게 한다. 큰따옴표 """ 로 쓰면 토큰이 명령 문자열에 박혀 젠킨스가 경고를 낸다
git clone --depth 1최신 커밋 하나만 받는다. 기록 전체가 필요 없으니 빠르다
${GIT_USER}/${MANIFEST_REPO}토큰 주인 = 저장소 주인이라고 가정한 주소. 조직(organization) 저장소라면 그 부분을 조직 이름으로 바꾼다
sed -i "s|image: …|…|"image: 로 시작하는 줄을 새 이미지로 바꾼다. 구분자를 | 로 쓴 건 이미지 이름의 / 와 안 헷갈리게
git diff무엇이 바뀌는지 로그에 남긴다. 나중에 콘솔 출력만 봐도 알 수 있게
git push origin HEAD:main지금 커밋을 원격의 main 으로

Groovy 문자열 보간 — Jenkinsfile 은 Groovy 언어다. 큰따옴표 문자열 안의 ${…} 는 Groovy 가 먼저 값을 채워 넣는다. 비밀값이 이렇게 채워지면 프로세스 목록 같은 곳에 노출될 수 있어서, 비밀값은 작은따옴표로 셸에 넘기는 게 원칙이다.
Kustomize — sed 대신 쓰는 정석 도구. kustomization.yaml 에 이미지 태그를 따로 적어 두고 kustomize edit set image 로 바꾼다. YAML 구조를 알고 고치니 sed 처럼 엉뚱한 줄을 바꿀 위험이 없다. ArgoCD 는 kustomization.yaml 이 있으면 알아서 읽는다. 

git add Jenkinsfile.gitops
git commit -m "젠킨스가 매니페스트 태그를 고쳐 커밋하는 GitOps 파이프라인"
git push

3. 잡 만들기

  1. 11편 잡 cicd-hello-k8s 는 Disable Project 로 꺼 둔다. 같은 저장소를 둘이 보고 있으면 push 한 번에 빌드가 두 번 돈다.
  2. New Item → cicd-hello-gitops → Pipeline
  3. Pipeline script from SCM → Git → https://github.com/<내아이디>/cicd-hello.git, 브랜치 */main, Script Path Jenkinsfile.gitops → Save
  4. Build Now 한 번 (첫 실행이 끝나야 Poll SCM 이 등록된다)

첫 빌드가 초록이면 확인할 곳이 세 군데다.

  • 젠킨스 콘솔 출력의 git diff 부분: - image: …:1-a1b2c3d / + image: …:1-9f8e7d6 같은 두 줄
  • GitHub 의 cicd-hello-manifests → Commits: jenkins-bot 의 "배포: cicd-hello …" 커밋
  • ArgoCD 화면: 잠시 OutOfSync → 자동으로 Synced, 파드가 새 이름으로 바뀜 (기다리기 싫으면 REFRESH)

4. 진짜 변경 하나를 끝까지 따라가기

앱 문구를 바꾼다. 지금 문구는 9편에서 바꾼 Hello, Docker CI/CD! 다(9편을 건너뛰었다면 Hello, CI/CD!). 테스트도 같이 고쳐야 한다(안 고치면 어떻게 되는지는 5번에서).

# app.py
    return f"Hello, GitOps! version={VERSION}\n"

# test_app.py
    assert b"Hello, GitOps!" in res.data
git commit -am "인사말을 GitOps 로"
git push

이제 손을 뗀다. 터미널 두 개로 지켜본다.

# 터미널 A — 파드가 바뀌는 순간
kubectl -n cicd-hello get pods -w

# 터미널 B — 앱의 답 (port-forward 는 파드가 바뀌면 끊기니 다시 켠다)
kubectl -n cicd-hello port-forward svc/cicd-hello 8200:80 &
watch -n 5 curl -s localhost:8200/
시간(대략)일어나는 일어디서 보나
0분git pushGitHub cicd-hello
~2분젠킨스가 변경 감지(Poll SCM), 에이전트 파드 생성kubectl -n jenkins get pods
~2–5분Test → Build & Push → Update manifest젠킨스 Stage View, Docker Hub Tags
~5–8분ArgoCD 가 매니페스트 변경 감지 → 자동 SyncArgoCD 화면, argocd app get cicd-hello
+20초롤링 업데이트: 새 파드 Ready → 옛 파드 종료터미널 A
끝Hello, GitOps! version=3-…터미널 B

몇 분씩 기다리는 구간은 둘 다 "주기적으로 확인하기(폴링)" 때문이다. 실서버에서는 GitHub 웹훅을 젠킨스(/github-webhook/)와 ArgoCD(/api/webhook)에 걸어 push 즉시 움직이게 한다. 이 실습의 젠킨스·ArgoCD 는 내 컴퓨터 안에 있어서 GitHub 가 찾아올 수 없으니 폴링을 쓴 것이다.

폴링(polling) — 바뀐 게 있는지 일정 간격으로 가서 물어보는 방식. 단순하지만 느리고 헛걸음이 많다.
웹훅(webhook) — 일이 생기면 상대가 내 주소로 알려 주는 방식. 빠르지만 내 주소가 인터넷에서 보여야 한다.

5. 테스트가 깨지면 — 멈춘다

app.py 의 문구만 "Hi!" 로 바꾸고 테스트는 그대로 둔 채 push 한다.

  • 젠킨스: Test 에서 빨간 X. Build & Push, Update manifest 는 회색(실행 안 됨)
  • Docker Hub: 새 태그 없음
  • 매니페스트 저장소: 새 커밋 없음 → ArgoCD 는 할 일이 없다
  • curl: 여전히 Hello, GitOps! — 운영은 멀쩡하다

파이프라인의 단계 순서 자체가 안전장치다. 확인을 통과한 것만 다음 칸으로 간다. 고쳐서(또는 되돌려서) push 하면 다시 흐른다.

이미지는 만들어졌는데 뜨지 않는다면

테스트는 통과했지만 운영에서만 죽는 이미지(예: 환경변수가 없어 시작하자마자 에러)가 나갈 수도 있다. 이때 쿠버네티스의 롤링 업데이트가 한 번 더 막아 준다. 새 파드가 readinessProbe 를 통과하지 못하면 옛 파드를 내리지 않는다. ArgoCD 는 Degraded·Progressing 으로 알려 주고, 서비스는 옛 파드가 계속 받는다. 그 상태에서 6번처럼 되돌리면 된다.

6. 되돌리기 — git revert 한 줄

"방금 배포한 버전에 문제가 있다." 이미지를 다시 빌드할 필요가 없다. Docker Hub 에는 이전 태그가 그대로 있으니 매니페스트만 한 칸 뒤로 돌린다.

cd ~/cicd/cicd-hello-manifests
git pull                         # 젠킨스가 올린 커밋 받기
git log --oneline -3
9c1d2e3 배포: cicd-hello 3-7a6b5c4      ← 문제 버전
4b5a6c7 배포: cicd-hello 2-9f8e7d6
…

git revert --no-edit HEAD
git push

ArgoCD 가 바뀐 매니페스트를 보고 2-9f8e7d6 로 되돌린다. "누가 언제 왜 되돌렸나" 도 revert 커밋으로 남는다. 앱 저장소에서 원인을 고쳐 다시 push 하면, 새 빌드가 새 태그로 다시 앞으로 나아간다.

롤백(rollback) — 배포를 이전 버전으로 되돌리는 것. GitOps 에서는 "매니페스트를 revert" 와 같은 말이다. 이미지를 빌드할 때마다 고유 태그를 붙이고 지우지 않는 이유가 여기 있다. latest 하나만 덮어쓰면 돌아갈 곳이 없다.

더 나아가면

주제한 줄
환경 나누기 (dev → prod)매니페스트 저장소에 envs/dev, envs/prod 폴더(또는 Kustomize overlay)를 두고 Application 을 둘 만든다. 젠킨스는 dev 만 자동으로 고치고, prod 는 사람이 PR 로 태그를 올린다(승인 = 배포 승인)
Argo CD Image Updater젠킨스가 매니페스트를 고치는 대신, 레지스트리에 새 태그가 생기면 ArgoCD 쪽 도구가 알아서 매니페스트를 고친다
Helm 차트로 배포YAML 대신 차트와 values 파일. 젠킨스는 values.yaml 의 image.tag 를 고친다
알림ArgoCD Notifications 로 동기화 성공·실패를 슬랙에
Argo Rollouts새 버전에 트래픽을 10% → 50% → 100% 로 조금씩(카나리 배포), 지표가 나쁘면 자동 되돌리기
CI 를 GitHub Actions 로젠킨스 자리를 Actions 로 바꿔도 "이미지 푸시 → 매니페스트 커밋" 만 하면 ArgoCD 쪽은 그대로다

! [rejected] … (fetch first)그 사이 누가 매니페스트를 고쳤다. 다시 빌드하면 새로 clone 해서 된다. 자주 나면 disableConcurrentBuilds() 가 있는지

ArgoCD Degraded, 파드 ImagePullBackOff태그는 커밋됐는데 그 이미지가 Docker Hub 에 없다(푸시 실패를 무시하고 넘어간 경우 등). 6번처럼 revert 하고 젠킨스 로그 확인

실습 뒷정리 (모두 끝났다면)

kind delete cluster --name cicd                    # 10~13편: 젠킨스·ArgoCD·앱 모두 사라진다
cd ~/cicd/jenkins-docker && docker compose down    # 8~9편 젠킨스 (볼륨까지 지우려면 -v)
docker rm -f cicd-hello                            # 9편 앱 컨테이너
sudo systemctl disable --now jenkins cicd-hello    # 4~6편 우분투의 젠킨스와 앱 서비스

Docker Hub·GitHub 토큰은 실습이 끝나면 지우거나 만료일을 짧게 둔다. 저장소(cicd-hello, cicd-hello-manifests)는 남겨 두면 나중에 다시 따라 할 때 그대로 쓸 수 있다. 8~9편 폴더 이름(~/cicd/jenkins-docker)은 그 글에서 만든 이름을 쓴다.
