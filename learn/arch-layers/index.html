실습 Python FastAPI 레이어드 아키텍처 DTO Repository 2026.10.28

취업 준비를 하며 백엔드 코드 구조를 설명한 자료를 봤다. 슬라이드로 읽을 때는 고개가 끄덕여졌는데, 막상 "그래서 파일을 어떻게 나누라는 거지?" 하면 손이 안 나갔다. 그래서 아주 작은 메모 API(memo-api)를 처음부터 직접 만들어 보면서, 자료에 나온 원칙을 하나씩 코드로 옮겨 봤다. 이 글은 그 첫 번째, 층을 나누는 법이다.

한 줄로 줄이면 이렇다. HTTP 를 다루는 코드, 규칙을 지키는 코드, DB 를 만지는 코드를 서로 다른 층에 두고, 위층만 아래층을 부른다.

왜 나누나 — 한 파일짜리의 문제

처음엔 app.py 한 파일(78줄)로 만들었다. 잘 돌아간다. 문제는 고칠 때 생긴다. 메모를 읽는 함수 하나에 세 가지 일이 뒤섞여 있다. 

@app.get("/memos/{memo_id}")
def get_memo(memo_id: int, x_user: str = Header()):
    row = db.execute("SELECT id, owner, ... FROM memo WHERE id = ?", (memo_id,)).fetchone()  # ① DB
    if row is None:
        raise HTTPException(404, f"메모 {memo_id} 가 없습니다")                          # ② HTTP
    if row[1] != x_user:
        raise HTTPException(403, "내 메모가 아닙니다")                                    # ③ 규칙
    return {"id": row[0], "title": row[2], "body": row[3], "created_at": row[4]}
  • 같은 규칙이 여러 번 나온다. "내 메모만 볼 수 있다", "제목은 비면 안 된다"가 읽기·고치기·지우기 함수마다 복사돼 있다. 한 군데만 고치면 버그가 된다.
  • 규칙을 시험하려면 DB 와 서버가 다 있어야 한다. "남의 메모는 못 읽는다"를 확인하려면 HTTP 요청을 보내야 한다.
  • DB 를 바꾸면 모든 함수가 바뀐다. SQL 이 라우트 함수마다 흩어져 있다.

식당으로 생각하면 쉽다. 홀 직원이 주문을 받다가 주방에 들어가 요리하고, 창고에 가서 재료까지 꺼내 오는 꼴이다. 홀(주문 받기), 주방(요리 규칙), 창고(재료 보관)를 나누면 각자 자기 일만 잘하면 된다.

세 층과 그 사이를 오가는 것

(파일 경로의 routers/ 는 webapp/ 아래, memo/ 는 src/ 아래다.)

층 · 파일알아도 되는 것몰라야 하는 것
표현
routers/memo.py		URL, 헤더, JSON 모양, 상태 코드SQL, 제목 규칙
비즈니스
memo/service.py
memo/domains.py		메모 규칙, 일의 순서HTTP, SQL
영속
memo/repository.py
memo/entities.py		테이블, SQL, 행 ↔ 도메인 변환HTTP, 누가 요청했는지

계층(layer) — 하는 일이 비슷한 코드끼리 묶은 층. 위층은 아래층을 부를 수 있지만 반대는 안 된다.
도메인(domain) — 이 프로그램이 다루는 대상 그 자체와 그 규칙. 여기서는 "메모"와 "제목은 비면 안 된다" 같은 것.
영속(persistence) — 프로그램이 꺼져도 데이터가 남게 저장하는 것. 보통 DB.

1단계 — 도메인: 규칙을 한 곳에

가장 먼저 만드는 건 HTTP 도 DB 도 아닌 메모 그 자체다. 제목 규칙과 주인 확인을 메모 객체가 직접 지키게 한다. 그러면 "제목은 비면 안 된다"는 이 파일에 딱 한 번만 쓰인다. 

# src/memo/domains.py
@dataclass
class Memo:
    owner: str
    title: str
    body: str = ""
    id: int | None = None
    created_at: datetime = field(default_factory=lambda: datetime.now(timezone.utc))

    def __post_init__(self) -> None:          # 만들 때 바로 검사
        self.validate_title(self.title)

    @staticmethod
    def validate_title(title: str) -> None:
        if not title.strip():
            raise InvalidInput("제목이 비었습니다")
        if len(title) > TITLE_MAX:
            raise InvalidInput(f"제목은 {TITLE_MAX}자까지입니다")

    def rename(self, title: str) -> None:
        self.validate_title(title)
        self.title = title

    def ensure_owner(self, user: str) -> None:
        if self.owner != user:
            raise PermissionDenied("내 메모가 아닙니다")

예외도 HTTP 를 모른다. NotFound, PermissionDenied, InvalidInput 을 src/common/exceptions.py 에 두고, 이걸 404·403·400 으로 바꾸는 건 표현 계층이 한다. 같은 서비스를 나중에 HTTP 가 아닌 곳(배치 작업, gRPC)에서 불러도 그대로 쓸 수 있다.

2단계 — 영속: 엔티티와 저장소

엔티티는 테이블 한 줄을 그대로 옮긴 모양이다. 도메인과 비슷하지만 다르다. 예를 들어 DB 에는 시간이 문자열로 들어가고, 도메인은 datetime 을 쓴다. 이 둘을 오가는 변환을 엔티티에 둔다. 

# src/memo/entities.py
@dataclass(frozen=True)
class MemoRow:
    id: int
    owner: str
    title: str
    body: str
    created_at: str        # sqlite 에는 ISO 문자열

    @classmethod
    def from_domain(cls, memo: Memo) -> "MemoRow": ...
    def to_domain(self) -> Memo: ...

저장소(repository)는 "메모를 어디에 어떻게 넣고 꺼내나"만 안다. 서비스는 저장소에게 "1번 메모 줘"라고만 하고, 그게 sqlite 인지 다른 DB 인지 모른다. 먼저 약속(추상 클래스)을 정하고, 그 약속을 지키는 구현을 만든다. 

# src/memo/repository.py
class MemoRepository(ABC):                       # 약속
    @abstractmethod
    def find_memo(self, memo_id: int) -> Memo | None: ...
    @abstractmethod
    def find_memos_by_owner(self, owner: str) -> list[Memo]: ...
    @abstractmethod
    def create(self, memo: Memo) -> Memo: ...
    # update, delete …

    def get_memo(self, memo_id: int) -> Memo:   # 없으면 예외
        memo = self.find_memo(memo_id)
        if memo is None:
            raise NotFound(f"메모 {memo_id} 가 없습니다")
        return memo


class SqliteMemoRepository(MemoRepository):      # 구현 ①
    def find_memo(self, memo_id: int) -> Memo | None:
        row = self.conn.execute(
            "SELECT id, owner, title, body, created_at FROM memo WHERE id = ?", (memo_id,)
        ).fetchone()
        return MemoRow(*row).to_domain() if row else None
    ...

이름만 보고 동작을 알게 — 이름 규칙

이름돌려주는 것없으면
get_memoMemo (반드시)NotFound 예외
find_memoMemo | NoneNone
find_memos_by_ownerlist[Memo]빈 리스트. by_ 뒤가 WHERE 조건

이 규칙을 모든 저장소에 똑같이 쓰면, 처음 보는 모듈도 함수 이름만 보고 "이건 없으면 예외구나"를 안다. 이렇게 모양을 통일하는 원칙은 코드 작성 원칙에 이어서 적었다.

3단계 — 비즈니스: 서비스

서비스는 "사용자가 하려는 일" 하나를 메서드 하나로 만든다. 일의 순서만 쓰고, 규칙은 도메인에, 저장은 저장소에 맡긴다. 

# src/memo/service.py
class MemoService:
    def __init__(self, repository: MemoRepository) -> None:
        self.repository = repository             # 직접 만들지 않고 받는다

    def get_memo(self, user: str, memo_id: int) -> Memo:
        memo = self.repository.get_memo(memo_id)
        memo.ensure_owner(user)
        return memo

    def rename_memo(self, user: str, memo_id: int, title: str) -> Memo:
        memo = self.get_memo(user, memo_id)      # 주인 확인까지 재사용
        memo.rename(title)                       # 제목 규칙은 도메인이
        return self.repository.update(memo)      # 저장은 저장소가

한 파일짜리에서 세 번 복사돼 있던 "없으면 404, 남의 것이면 403" 이 get_memo 한 곳으로 모였다. 저장소를 생성자로 받는 이유는 다음 글 의존성 주입의 주제다.

4단계 — 표현: 라우터와 DTO

DTO(Data Transfer Object)는 바깥과 주고받는 모양이다. 도메인을 그대로 JSON 으로 내보내지 않고 응답용 모양을 따로 둔다. 그래야 도메인에 필드를 더해도 응답이 저절로 바뀌지 않는다. 여기서는 owner 를 응답에 안 내보낸다. 

# webapp/routers/memo.py
class MemoCreateRequest(BaseModel):     # 들어오는 모양
    title: str
    body: str = ""

class MemoResponse(BaseModel):          # 나가는 모양
    id: int
    title: str
    body: str
    created_at: datetime

    @classmethod
    def from_domain(cls, memo: Memo) -> "MemoResponse":
        return cls(id=memo.id, title=memo.title, body=memo.body, created_at=memo.created_at)


@router.post("", status_code=201, response_model=MemoResponse)
def create_memo(req: MemoCreateRequest, x_user: str = Header(),
                service: MemoService = Depends(memo_service)):
    return MemoResponse.from_domain(service.create_memo(x_user, req.title, req.body))

라우트 함수에는 이제 SQL 도, 규칙도 없다. 받아서 넘기고, 돌려받은 걸 응답 모양으로 바꿀 뿐이다.

DTO — 층과 층 사이, 또는 바깥과 데이터를 주고받을 때 쓰는 모양. 규칙 없이 값만 담는다.
엔티티 — 이 글에서는 DB 테이블 한 줄과 1:1 로 대응하는 객체. (책마다 뜻이 조금 다르다. JPA 에서는 DB 와 연결된 도메인 객체를 엔티티라 부르기도 한다.)

응답에 owner 가 없는 것(DTO 덕분), 남의 메모는 403, 빈 제목은 도메인 규칙에 걸려 400 이 나오는 걸 볼 수 있다. 첫 줄의 JSON 로그는 아래 "참조는 한 방향" 에서 다시 본다.

데이터 주권 — 내 테이블은 나만 만진다

user 모듈에 "내 프로필(메모 몇 개 썼는지)"을 만들 때, 가장 쉬운 길은 user 쪽에서 SELECT COUNT(*) FROM memo 를 직접 날리는 것이다. 한 파일짜리 버전이 실제로 그랬다. 그런데 이러면 memo 테이블 모양을 바꿀 때 user 모듈까지 깨진다. memo 가 자기 데이터를 통제하지 못하게 된다. 

# src/memo/service.py
def count_memos(self, user: str) -> int:
    """다른 모듈이 메모 수를 알고 싶을 때 여는 문. 테이블을 직접 읽게 하지 않는다."""
    return len(self.repository.find_memos_by_owner(user))

# src/user/service.py
class ProfileService:
    def __init__(self, memo_service: MemoService) -> None:
        self.memo_service = memo_service

    def profile(self, user: str) -> dict:
        return {"user": user, "memo_count": self.memo_service.count_memos(user)}

"데이터와 그 데이터를 다루는 로직은 가까이 둔다"는 원칙과 같은 이야기다. 메모 데이터를 어떻게 세는지는 메모 모듈이 정하고, 바깥은 결과만 받는다.

바꿔 끼우기 — 확장에는 열려 있고 수정에는 닫혀 있게

저장소를 약속(MemoRepository)으로 정해 둔 덕분에, 구현을 하나 더 만들어 끼울 수 있다. DB 없이 dict 에 담는 InMemoryMemoRepository 다. 서비스 코드는 한 글자도 안 고치고 저장소만 바꿔 봤다. 

# swap_demo.py
for repo in [SqliteMemoRepository(sqlite3.connect(":memory:")), InMemoryMemoRepository()]:
    service = MemoService(repository=repo)          # 서비스 코드는 그대로
    memo = service.create_memo("kim", "장보기")
    print(type(repo).__name__, "->", service.get_memo("kim", memo.id).title, service.count_memos("kim"))

$ python swap_demo.py
SqliteMemoRepository -> 장보기 1
InMemoryMemoRepository -> 장보기 1

이게 개방-폐쇄 원칙(OCP)이다. 새 기능(새 저장소)을 더하는 건 열려 있고, 이미 잘 돌아가는 코드(서비스)를 고치는 건 닫혀 있다. 나중에 PostgreSQL 이나 검색 엔진으로 옮길 때도 저장소 구현 하나만 새로 쓰면 된다. 표현 계층도 마찬가지다. REST 대신 gRPC 를 붙여도 서비스는 그대로다.

참조는 한 방향 — 로거로 보는 예

webapp 이 src 를 부르는 건 당연하다. 반대로 src 가 webapp 안의 무언가를 import 하면 순환 참조가 생긴다. 흔한 함정이 로거다. 서비스에서 로그를 남기려고 webapp 에 만든 JSON 로거를 import 하는 순간, 비즈니스 계층이 표현 계층에 묶인다.

그래서 둘로 쪼갰다.

어디서정하는 것코드
src/무엇을 남길지 (내용)log.info("메모를 만들었다", extra={"memo_id": …})
webapp/어떻게 남길지 (형식)서비스로 돌 때는 JSON 한 줄 — 로그 수집기가 필드별로 읽기 좋다
tests/어떻게 남길지 (형식)테스트할 때는 사람이 읽는 한 줄 — 터미널에서 보기 좋다
# src/common/logger.py — 내용만. 형식은 모른다
def get_logger(name: str) -> logging.Logger:
    return logging.getLogger(f"memo_api.{name}")

# webapp/log_format.py — 형식만
class JsonFormatter(logging.Formatter):
    def format(self, record): return json.dumps({"level": …, "msg": …, **extra}, ensure_ascii=False)

같은 log.info(...) 한 줄이 서비스에서는 위 "돌려 보기" 첫 줄처럼 JSON 으로, 테스트에서는 INFO memo_api.memo: 메모를 만들었다 로 찍힌다. 맥락에 따라 형식을 바꿀 수 있는 건 형식을 바깥(위층)이 쥐고 있어서다.

순환 참조 — A 가 B 를 import 하고 B 도 A 를 import 하는 것. 파이썬에서는 실행 순서에 따라 import 오류가 나고, 그렇지 않더라도 둘을 따로 떼어 낼 수 없게 된다.

파일 수는 1개에서 20개 남짓으로 늘었다. 처음엔 과해 보였다. 그런데 테스트를 쓰려는 순간 차이가 났다. 서비스를 DB 없이 바로 시험할 수 있었고, "제목 규칙을 바꿔 달라"는 요청이 오면 어디를 고칠지 바로 안다. 작은 앱에서는 과할 수 있다. 자료에서도 "가능한 가장 간단한 구조로, 나눌 이유가 분명할 때 나눠라(KISS)"를 첫 원칙으로 뒀다. 층을 나누는 건 그 이유가 생겼을 때 꺼내 쓰는 도구다.
