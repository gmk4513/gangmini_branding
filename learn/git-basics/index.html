Git 첫걸음
— 저장소 만들고 커밋하기

실습 Git GitHub 커밋 .gitignore 2026.10.28

Git·GitHub 실습 시리즈의 첫 글이다. 빈 폴더 하나에서 시작해 커밋 세 개를 만들고 GitHub 에 올리는 데까지 간다. 명령은 전부 그대로 따라 치면 되고, 아래에 붙인 출력은 실제로 돌려서 나온 것이다(경로·해시는 사람마다 다르다).

나는 한동안 프로젝트를 git 없이 만들었다. 감스트 스쿠터 게임은 다 만들고 배포까지 한 뒤인 2026-10-28 에야 저장소를 만들어 첫 커밋을 했다. 혼자일 땐 티가 안 나지만, 누가 무엇을 왜 바꿨는지 남지 않는 프로젝트는 팀에서 이어받을 수가 없다. 그래서 처음부터 정리한다.

Git 은 세 칸으로 생각한다

Git 을 처음 쓸 때 가장 헷갈리는 건 "저장"이 두 단계라는 점이다. 파일을 고친다고 기록되지 않는다. 올릴 것을 고르고(add), 그것을 한 묶음으로 기록한다(commit).

저장소(repository, repo) — Git 이 기록을 쌓는 곳. 프로젝트 폴더 안의 숨은 .git 폴더가 그 정체다. 지우면 기록이 다 사라진다.
커밋(commit) — 어느 순간의 파일 상태 + 누가·언제·왜 를 적은 기록 하나. 고유 번호(해시, 예: b0366a2)가 붙는다.
원격(remote) — 다른 곳(대개 GitHub)에 있는 같은 저장소. 기본 이름이 origin 이다.

0. 준비 — 설치 확인과 내 이름

git --version
git version 2.47.0.windows.2

버전이 나오면 설치돼 있다. 안 나오면 git-scm.com 에서 받는다(윈도는 설치하면 "Git Bash" 도 같이 생긴다. 이 글의 명령은 Git Bash 기준이다). 다음은 커밋에 찍힐 이름과 이메일이다. 컴퓨터마다 한 번만 하면 된다. 

git config --global user.name "홍길동"
git config --global user.email "me@example.com"   # GitHub 가입 이메일과 같게

회사 컴퓨터라면 회사 이메일로 맞춘다. 이 이메일이 GitHub 계정과 맞아야 커밋 옆에 내 프로필이 뜬다.

1. 저장소 만들기 — init 과 clone

저장소를 갖는 방법은 두 가지다.

상황명령언제
새 프로젝트git init지금 폴더를 저장소로 만든다. 혼자 시작할 때
이미 있는 프로젝트git clone 주소GitHub 에 있는 저장소를 통째로 내려받는다. 회사 첫날 하는 일

여기서는 init 으로 시작한다.

mkdir git-practice
cd git-practice
git init -b main
Initialized empty Git repository in .../git-practice/.git/

-b main 은 첫 브랜치 이름을 main 으로 정한다. 요즘 GitHub 기본값이 main 이라 맞춰 둔다. 바로 상태를 본다. 

git status
On branch main

No commits yet

nothing to commit (create/copy files and use "git add" to track)

2. 첫 커밋 — status, add, commit

① 파일을 하나 만든다. 편집기로 만들어도 되고, 아래처럼 한 줄로 만들어도 된다.

printf '# git-practice\n\nGit 연습용 저장소.\n' > README.md
git status
Untracked files:
  (use "git add <file>..." to include in what will be committed)
	README.md

nothing added to commit but untracked files present (use "git add" to track)

Untracked — Git 이 아직 모르는 파일이다. 작업 폴더 칸에만 있다.

② 스테이징에 올린다.

git add README.md
git status
Changes to be committed:
  (use "git rm --cached <file>..." to unstage)
	new file:   README.md

Changes to be committed — 스테이징 칸에 올라갔다. 아직 기록은 아니다.

③ 커밋한다. -m 뒤가 커밋 메시지다.

git commit -m "README 추가"
[main (root-commit) b0366a2] README 추가
 1 file changed, 3 insertions(+)
 create mode 100644 README.md

b0366a2 가 이 커밋의 번호다. root-commit 은 "이 저장소의 첫 커밋"이라는 뜻이다.

3. 무엇이 바뀌었나 — diff 와 diff --staged

README 에 몇 줄을 더 붙이고, 커밋하기 전에 무엇이 바뀌었는지 본다.

printf '\n## 오늘 배운 것\n- git init\n' >> README.md
git diff
diff --git a/README.md b/README.md
--- a/README.md
+++ b/README.md
@@ -1,3 +1,6 @@
 # git-practice

 Git 연습용 저장소.
+
+## 오늘 배운 것
+- git init

+ 로 시작하는 줄이 새로 생긴 줄, - 는 지운 줄이다. @@ -1,3 +1,6 @@ 는 "원래 1~3번째 줄이, 지금은 1~6번째 줄"이라는 위치 표시다.

여기서 한 번 헷갈린다. git add 를 하고 나면 git diff 는 아무것도 안 보여 준다. git diff 는 "작업 폴더 ↔ 스테이징" 차이고, 스테이징에 올린 것은 --staged 를 붙여야 보인다.

명령비교하는 두 칸질문
git diff작업 폴더 ↔ 스테이징아직 add 안 한 변경은?
git diff --staged스테이징 ↔ 마지막 커밋이번 커밋에 들어갈 변경은?
git add README.md
git diff            # 아무것도 안 나온다
git diff --staged   # 위와 같은 diff 가 나온다
git commit -m "오늘 배운 것 추가"

커밋 직전에 git diff --staged 를 한 번 보는 습관이 실무에서 가장 쓸모 있다. 디버그용으로 넣은 출력, 비밀 키, 의도하지 않은 파일이 여기서 걸린다. AI 가 고친 코드를 커밋할 때는 더 그렇다. 이 화면에서 한 줄씩 설명할 수 없는 변경은 아직 올리면 안 된다.

4. 올리면 안 되는 것 — .gitignore

비밀 키(.env), 설치하면 생기는 폴더(node_modules/), 로그 파일은 저장소에 넣지 않는다. 폴더 맨 위에 .gitignore 를 만들어 이름을 적는다. 

printf 'node_modules/\n.env\n*.log\n' > .gitignore
echo "SECRET=1" > .env
echo hi > debug.log
git status --short
?? .gitignore

.env 와 debug.log 를 만들었는데 목록에 없다. Git 이 무시하고 있다는 뜻이다. .gitignore 자체는 커밋한다. 팀 전체가 같은 규칙을 써야 하니까. 

git add .gitignore
git commit -m ".gitignore 추가"
git log --oneline
e6f7baf .gitignore 추가
9e2c3cc 오늘 배운 것 추가
b0366a2 README 추가

위가 최신이다. 자세히 보려면 git log(작성자·날짜까지), 한 커밋의 내용은 git show e6f7baf.

.gitignore 는 이미 올라간 파일엔 효과가 없다 — 한 번 커밋된 파일은 계속 추적된다. 실수로 올렸다면 git rm --cached 파일 로 추적만 끊고, 비밀 키였다면 키 자체를 새로 발급해야 한다. 기록에 이미 남았기 때문이다.
.gitattributes — 줄바꿈(윈도 CRLF / 맥·리눅스 LF) 규칙을 저장소에 적어 두는 파일. 감스트 스쿠터 저장소를 만들 때 * text=auto eol=lf 를 같이 넣었다. 안 그러면 윈도에서 한 번 저장한 파일이 diff 상으로 "전체가 바뀐" 것처럼 보인다.

5. GitHub 에 올리기 — 저장소 만들고 push

두 가지 방법이 있다. 결과는 같다.

방법 A. 웹에서

  1. github.com 오른쪽 위 + → New repository
  2. Repository name 에 git-practice, Private 선택
  3. "Add a README file" 은 체크하지 않는다. 체크하면 GitHub 쪽에도 첫 커밋이 생겨서 내 커밋과 엇갈린다
  4. Create repository → 나오는 화면의 "…or push an existing repository" 세 줄을 복사해 실행
git remote add origin https://github.com/내아이디/git-practice.git
git push -u origin main

방법 B. gh 명령 한 줄로

GitHub 공식 명령줄 도구 gh 를 깔고(gh auth login 으로 한 번 로그인) 저장소 폴더에서: 

gh repo create git-practice --private --source=. --push

GitHub 에 저장소를 만들고, origin 을 연결하고, 지금까지의 커밋을 올리는 것까지 한 번에 한다. 감스트 스쿠터 저장소도 이 한 줄로 만들었다.

push 가 되면 이렇게 나온다.

branch 'main' set up to track 'origin/main'.
To https://github.com/내아이디/git-practice.git
 * [new branch]      main -> main

-u 는 "내 main 이 origin 의 main 을 따라간다"를 한 번 정해 두는 옵션이다. 그 뒤로는 그냥 git push, git pull 만 쳐도 된다. GitHub 저장소 페이지를 새로고침하면 README 가 보이고, 커밋 3개가 올라가 있다.

6. 다른 컴퓨터에서 받아 보기 — clone

cd ..
git clone https://github.com/내아이디/git-practice.git practice-copy
cd practice-copy
git log --oneline
Cloning into 'practice-copy'...
done.
e6f7baf .gitignore 추가
9e2c3cc 오늘 배운 것 추가
b0366a2 README 추가

기록이 통째로 따라온다. .env 는 없다. 올리지 않았으니까. 회사에서 처음 받는 프로젝트에 ".env.example 을 복사해서 .env 를 만드세요" 같은 안내가 있는 이유가 이것이다.

명령하는 일
