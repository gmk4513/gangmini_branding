THEORY

테스트와 CI/CD
— 손으로 하던 확인을 자동으로

이론 테스트 pytest CI/CD Docker GitHub Actions 2026.10.28

오늘 다이어리 앱에 R8 을 켜고 나서, 에뮬레이터를 켜 놓고 그림판·저장·선생님 한마디·결제 가격을 하나씩 눌러 봤다. 다 정상이었다. 그런데 이 확인은 나만 했고, 다음에 누가 같은 설정을 건드리면 또 처음부터 손으로 해야 한다.

코드 구조를 공부하며 본 자료의 마지막 두 장이 바로 이 얘기였다. 테스트 코드는 "일일이 동작하는지 확인하던 것"을 코드로 자동화한 것이고, 그 확인은 배포 환경과 비슷할수록 믿을 만하다. 그리고 CI/CD 는 그 테스트를 매번 돌리고, 통과한 코드에 버전을 붙여 내보내고, 문제가 나면 되돌리는 일을 자동으로 한다. 이 글은 연습용 앱 memo-api(메모를 만들고 꺼내는 작은 FastAPI 서버)를 예로 그 흐름을 따라간다.

테스트는 무엇을 대신하나

손으로 확인할 때 머릿속에서 하는 일을 적어 보면 세 단계다. "이런 상태에서(준비) → 이걸 하면(행동) → 이렇게 돼야 한다(확인)." 테스트 코드는 이 세 단계를 그대로 코드로 쓴 것이다. 그래서 테스트를 given / when / then 으로 나눠 쓰는 습관이 있다. 

# tests/test_memo_service.py
def test_create_memo_assigns_id():
    # given: 빈 저장소
    service = MemoService(FakeMemoRepository())
    # when: 메모를 하나 만들면
    memo = service.create_memo(owner_id=1, text="장보기")
    # then: 1번이 붙고 다시 꺼낼 수 있다
    assert memo.id == 1
    assert service.get_memo(1).text == "장보기"


def test_reject_memo_over_500_chars():
    service = MemoService(FakeMemoRepository())
    with pytest.raises(MemoTooLong):          # 이 줄 안에서 에러가 나야 통과
        service.create_memo(owner_id=1, text="가" * 501)

실제로 돌리면 이렇게 나온다(파이썬 3.11, pytest 9.2). 

$ pytest -q
...                                                    [100%]
3 passed in 0.02s

일부러 규칙을 망가뜨려 봤다. 서비스 코드의 글자 수 제한을 500 에서 5000 으로 바꾸고 다시 돌리면, 내가 눈치채기 전에 테스트가 먼저 잡는다. 

$ pytest -q
.F.                                                    [100%]
___________________ test_reject_memo_over_500_chars ___________________
>       with pytest.raises(MemoTooLong):
E       Failed: DID NOT RAISE MemoTooLong
FAILED tests/test_memo_service.py::test_reject_memo_over_500_chars
1 failed, 2 passed in 0.06s

이게 테스트의 값어치다. 0.06초 만에, 누가 고쳐도, 몇 번을 돌려도 같은 확인을 한다.

pytest — 파이썬에서 가장 많이 쓰는 테스트 도구. test_ 로 시작하는 함수를 찾아 돌리고, assert 가 틀리면 실패로 보여 준다.
단언(assert) — "이 값은 이래야 한다"는 확인 한 줄. 틀리면 그 자리에서 테스트가 멈추고 무엇이 달랐는지 보여 준다.

단위 · 통합 · E2E — 얼마나 크게 묶어서 확인하나

종류memo-api 에서 예를 들면빠르기잡아내는 것
단위 테스트MemoService 하나만. 저장소는 가짜(딕셔너리)로 끼운다수 밀리초규칙 — 500자 제한, 없는 메모 에러
통합 테스트서비스 + 진짜 Postgres 저장소. 실제로 저장하고 다시 읽는다수 초SQL 실수, 칸 이름 오타, DB 설정
E2E 테스트서버를 띄우고 HTTP 로 POST /memos → GET /memos/1수 초~분주소·요청 모양·인증까지 이어 붙인 결과

작은 것을 많이, 큰 것은 꼭 필요한 흐름만 조금 둔다. 작을수록 빠르고, 실패했을 때 어디가 문제인지 바로 보인다. 큰 것은 느리지만 "합쳐 놓으면 정말 되나"를 본다. 이 비율 이야기는 검증을 남기는 능력의 테스트 피라미드에 그림으로 있다.

가짜 저장소와 진짜 DB

위 단위 테스트에서 MemoService(FakeMemoRepository()) 처럼 저장소를 밖에서 끼워 넣을 수 있었던 덕에 DB 없이 테스트했다. 서비스가 안에서 직접 DB 에 연결했다면 이게 안 된다. 코드 구조 공부에서 말하는 의존성 주입(DI)이 테스트에서 이렇게 쓰인다. 

# tests/fakes.py — 진짜 DB 대신 딕셔너리에 담는 가짜 저장소
class FakeMemoRepository:
    def __init__(self):
        self.rows = {}

    def create(self, memo):
        memo.id = len(self.rows) + 1
        self.rows[memo.id] = memo
        return memo

    def find_by_id(self, memo_id):
        return self.rows.get(memo_id)      # 없으면 None

가짜는 빠르지만 한계가 분명하다. 진짜 Postgres 라면 실패했을 SQL 오타, 칸 길이 제한, 같은 값 중복 금지 같은 것은 딕셔너리가 잡지 못한다. 그래서 저장소 자체는 진짜 DB 로 한 번 더 테스트한다. 자료의 표현대로라면 "배포 환경과 최대한 비슷하게"다.

배포 환경과 비슷하게 — 테스트 때만 진짜 DB 띄우기

예전에는 테스트용 DB 서버를 따로 하나 켜 두고 다 같이 썼다. 그러면 누가 남긴 데이터 때문에 테스트가 들쭉날쭉해진다. 요즘은 테스트가 시작될 때 Docker 로 깨끗한 Postgres 를 하나 띄우고, 끝나면 지우는 방식을 많이 쓴다. 파이썬에서는 testcontainers 라는 도구가 이걸 해 준다. 

# tests/conftest.py — 예시 (아래 설명 참고)
import pytest
from testcontainers.postgres import PostgresContainer


@pytest.fixture(scope="session")
def postgres_url():
    # 테스트 묶음이 시작될 때 운영과 같은 버전의 Postgres 를 띄우고
    with PostgresContainer("postgres:16") as pg:
        yield pg.get_connection_url()
    # with 를 빠져나가면 컨테이너를 지운다 — 다음 실행은 늘 빈 DB 에서 시작


def test_repository_saves_and_reads(postgres_url):
    repo = PostgresMemoRepository(postgres_url)
    saved = repo.create(Memo(id=None, owner_id=1, text="장보기"))
    assert repo.find_by_id(saved.id).text == "장보기"

이 코드는 모양을 보여 주려는 예시다. 이 글을 쓴 컴퓨터에는 Docker 명령은 깔려 있었지만 Docker 엔진이 꺼져 있어서 직접 돌려 보지 않았다. 위의 단위 테스트(가짜 저장소)만 실제로 돌린 결과다.

fixture — 테스트가 쓸 준비물을 만들어 주는 함수. scope="session" 이면 테스트 전체에서 한 번만 만들고 같이 쓴다.
Docker 컨테이너 — 프로그램과 그 실행 환경을 통째로 묶어, 어느 컴퓨터에서나 똑같이 띄울 수 있게 한 것. 묶음 자체는 이미지, 그걸 띄운 것이 컨테이너다.
가짜(fake) · 목(mock) — 진짜 대신 끼우는 대역. fake 는 간단히 실제로 동작하는 대역(딕셔너리 저장소), mock 은 "이렇게 불렸는지"를 기록·확인하는 대역이다.

CI 와 CD — 합쳐도 되나, 그리고 내보내기

테스트를 써 놓아도 아무도 안 돌리면 소용없다. 그래서 GitHub 같은 곳에서 PR 이 열리거나 브랜치에 합칠 때마다 자동으로 돌게 한다. 여기서부터 두 단어가 나온다.

이름묻는 것하는 일
CI (지속적 통합)이 변경을 합쳐도 되나?PR 마다 lint · 테스트를 돌리고, 실패하면 합치기 버튼을 막는다
CD (지속적 배포)합친 것을 어떻게 내보내나?통과한 코드로 이미지를 만들고, 버전을 붙여 보관하고, 서버에 배포한다

CI 부분은 GitHub Actions 첫걸음에서 따라 해 봤다. 여기서는 CD 쪽, 즉 "이미지에 버전을 붙이는 일"을 본다.

1. 이미지 만들기 — Dockerfile

# Dockerfile — memo-api 를 이미지로 묶는 설명서 (예시)
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY src ./src
COPY webapp ./webapp
ENV PYTHONPATH=/app/src:/app
CMD ["uvicorn", "webapp.main:app", "--host", "0.0.0.0", "--port", "8000"]

위에서부터 "파이썬이 깔린 바탕에서 → 필요한 라이브러리를 깔고 → 내 코드를 넣고 → 서버를 켠다"는 순서다. 이 이미지는 내 노트북에서 띄우든 회사 서버에서 띄우든 똑같이 돈다. "내 컴퓨터에선 됐는데"가 줄어드는 이유다. (Docker 엔진이 꺼져 있어 이 글에서는 실제로 빌드하지 않았다.)

2. 버전 이름표 붙여 올리기 — GitHub Actions

# .github/workflows/build-image.yml (예시 — 문법만 검사함)
name: build-image

on:
  push:
    branches: [dev]       # dev 에 합치면 개발 서버용 이미지
    tags: ["v*"]          # v0.1.0 같은 태그를 달면 운영용 이미지

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
      - run: pip install -r requirements.txt pytest
      - run: pytest -q

  image:
    needs: test           # 테스트가 통과해야만 이미지를 만든다
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
    steps:
      - uses: actions/checkout@v4
      - name: 레지스트리 로그인
        run: echo "${{ secrets.GITHUB_TOKEN }}" | docker login ghcr.io -u ${{ github.actor }} --password-stdin
      - name: 빌드하고 이름표 붙이기
        run: |
          IMAGE=ghcr.io/${{ github.repository_owner }}/memo-api
          docker build -t $IMAGE:sha-${GITHUB_SHA::7} .
          if [ "${{ github.ref_type }}" = "tag" ]; then
            docker tag $IMAGE:sha-${GITHUB_SHA::7} $IMAGE:${{ github.ref_name }}
          fi
          docker push --all-tags $IMAGE

이 파일은 파이썬 YAML 라이브러리(PyYAML)로 읽어 구조(test, image 두 작업, needs: test)가 의도대로 읽히는 것까지만 확인했다. 실제 GitHub 에서 돌려 보지는 않았다.

이름표를 둘 붙이는 이유가 있다.

  • sha-53cbd22 — 커밋 번호 앞 7자리. 이 이미지가 정확히 어느 코드로 만들어졌는지 한 치의 오차 없이 가리킨다. dev 에 합칠 때마다 새로 생긴다.
  • v0.1.0 — 사람이 읽는 버전. main 에 릴리스하며 단 태그와 같은 이름이라, "운영에 v0.1.0 이 떠 있다"는 말만으로 코드까지 바로 찾아간다.

3. 되돌리기(롤백)

v0.1.1 을 내보냈는데 문제가 생겼다. 코드를 다시 고쳐 빌드할 시간이 없다. 이때 레지스트리에 memo-api:v0.1.0 이 그대로 남아 있으니, 서버에 "이전 이름표의 이미지로 다시 띄워"라고만 하면 된다. 몇 분 안에 직전 상태로 돌아가고, 원인은 그다음에 천천히 찾는다. 이미지에 버전을 붙여 보관하는 진짜 이유가 이것이다.

레지스트리 — Docker 이미지를 올려 두고 받아 가는 보관소. GitHub 의 ghcr.io, Docker Hub, 클라우드 회사들의 것이 있다.
GITHUB_SHA — GitHub Actions 가 넣어 주는 값으로, 지금 돌고 있는 커밋의 번호(40자). ${GITHUB_SHA::7} 은 앞 7자만 잘라 쓰는 셸 문법이다.
롤백(rollback) — 배포한 것을 이전 버전으로 되돌리는 일. 코드를 되돌리는 git revert 와 달리, 이미 만들어 둔 이전 이미지를 다시 띄우는 것이라 빠르다.

정리

원칙한 줄
테스트 = 확인의 자동화given / when / then 으로, 손으로 하던 확인을 그대로 코드로
작은 것 많이, 큰 것 조금규칙은 단위 테스트로 빠르게, 이어 붙인 결과는 통합·E2E 로 몇 개만
끼워 넣을 수 있게저장소를 밖에서 받으면 가짜로도, 진짜로도 테스트할 수 있다
배포 환경과 비슷하게저장소는 운영과 같은 DB 로, 매번 깨끗하게 띄워서
CI 는 문지기PR 마다 돌고, 실패하면 합치지 못한다
CD 는 이름표통과한 코드를 이미지로, 버전과 커밋 번호를 붙여 보관, 되돌릴 땐 이전 이름표로

오늘 에뮬레이터에서 손으로 한 확인 네 가지가 바로 "아직 코드가 되지 못한 테스트"다. 앱은 화면을 눌러야 해서 자동화가 더 어렵지만, 규칙(무료 체험 7일 계산, 글자 수 같은 것)부터 단위 테스트로 옮기면 다음 사람은 그만큼 손을 덜 쓴다.
