GitHub Actions 첫걸음
— PR 마다 자동 검사

실습 GitHub Actions CI YAML 브랜치 보호 Secrets 2026.10.28

혼자 만들 때는 "내 컴퓨터에서 돌려 봤으니 됐다"로 끝난다. 팀에서는 다섯 명이 하루에 PR 을 열 개씩 올리고, 그때마다 누군가 받아서 설치하고 테스트를 돌려 볼 수는 없다. 그래서 PR 이 올라오면 기계가 대신 돌려 보고 결과를 PR 에 붙이게 한다. 이걸 CI 라고 하고, GitHub 에서는 GitHub Actions 로 한다.

파일 하나면 시작할 수 있다. 이 글은 연습용 저장소에 그 파일을 넣고, 일부러 실패시켜 보고, 통과해야만 합칠 수 있게 막는 데까지 따라 한다.

어떻게 도나

CI (Continuous Integration, 지속적 통합) — 여러 사람의 변경을 자주 합치되, 합칠 때마다 자동으로 빌드·검사·테스트를 돌려 깨진 걸 바로 찾는 방식.
워크플로(workflow) — "어떤 일이 생기면(on) 어떤 컴퓨터에서(runs-on) 무엇을 차례로(steps) 할지" 적은 YAML 파일. 저장소의 .github/workflows/ 에 둔다.
액션(action) — 남이 만들어 둔 단계 묶음. actions/checkout 은 코드 받기, actions/setup-node 는 Node 설치를 한 줄로 해 준다.

준비 — 연습용 저장소

GitHub 에 빈 저장소를 하나 만든다(예: actions-practice). 공개 저장소면 Actions 는 무료이고, 비공개 저장소도 무료 플랜에서 한 달 2,000분까지 쓸 수 있다. 내 컴퓨터에서 Node 프로젝트를 만든다. 

git clone https://github.com/내아이디/actions-practice.git
cd actions-practice
npm init -y

검사할 코드와 테스트를 하나씩 넣는다. Node 에 들어 있는 테스트 도구(node --test)를 쓰면 설치할 게 없다.

// sum.js
exports.sum = (a, b) => a + b;

// sum.test.js
const test = require("node:test");
const assert = require("node:assert");
const { sum } = require("./sum");
test("1 + 2 = 3", () => assert.strictEqual(sum(1, 2), 3));

package.json 의 "scripts" 를 이렇게 바꾼다. lint 는 실습이라 문법 검사(node --check)로 대신한다. 실제 팀은 ESLint 를 쓴다.

"scripts": {
  "lint": "node --check sum.js && node --check sum.test.js",
  "test": "node --test"
}
npm test
✔ 1 + 2 = 3
ℹ pass 1
ℹ fail 0

npm install          # package-lock.json 을 만든다 (npm ci 가 이 파일을 쓴다)
git add . && git commit -m "합계 함수와 테스트" && git push

1. 워크플로 파일 넣기

새 브랜치에서 .github/workflows/check.yml 을 만든다. 폴더 이름의 점(.)과 철자가 틀리면 GitHub 가 못 찾는다.

git switch -c add-ci
mkdir -p .github/workflows
# .github/workflows/check.yml
name: check

on:
  pull_request:
    branches: [main]
  push:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm
      - run: npm ci
      - run: npm run lint
      - run: npm test
줄뜻
on:언제 도나. main 으로 가는 PR 이 열리거나 새 커밋이 올라올 때, 그리고 main 에 push 될 때
jobs: test:일 하나의 이름. 일이 여럿이면 기본으로 동시에 돈다
runs-on러너 종류. ubuntu-latest 가 가장 흔하고 빠르다
uses: …@v4남이 만든 액션을 버전을 박아서 쓴다. 버전 없이 쓰면 어느 날 바뀐 액션 때문에 갑자기 깨질 수 있다
cache: npm패키지를 다음 실행 때 다시 받지 않게 저장
run:러너에서 칠 명령. 0 이 아닌 값으로 끝나면 그 단계가 실패
npm cipackage-lock.json 그대로 깨끗하게 설치. CI 에서는 npm install 대신 이걸 쓴다
git add .github
git commit -m "PR 마다 lint·test 자동 실행"
git push -u origin add-ci

GitHub 저장소 화면에 뜨는 Compare & pull request 를 눌러 PR 을 연다. PR 아래쪽 검사 칸에 노란 점(실행 중)이 생기고, 1분쯤 뒤 check / test 옆에 초록 체크가 붙는다.

2. 일부러 실패시켜 보기

같은 브랜치에서 함수를 틀리게 고쳐 push 한다. 열려 있는 PR 에 커밋이 더해지면서 검사가 다시 돈다.

// sum.js
exports.sum = (a, b) => a - b;      // 실수

git commit -am "합계 계산 바꿈" && git push

이번엔 빨간 X 가 붙는다. 검사 줄의 Details 를 누르면 로그가 나온다. 단계마다 접혀 있고, 실패한 단계(Run npm test)가 펼쳐져 있다. 거기서 ✖ 1 + 2 = 3 과 기대값(3)·실제값(-1)을 찾는다. 로그 읽는 순서는 늘 같다. 어느 단계가 빨간지 → 그 단계의 맨 아래 에러부터 위로.

고쳐서 다시 push 하면 초록으로 돌아온다. 로그 화면의 Re-run jobs 로 코드 변경 없이 다시 돌릴 수도 있다(네트워크가 잠깐 끊겨 실패했을 때).

3. 통과해야만 합칠 수 있게

빨간 X 가 떠도 "Merge" 버튼은 눌린다. 팀에서는 이걸 막아 둔다. 저장소의 Settings → Branches(또는 Settings → Rules → Rulesets)에서 main 에 규칙을 건다.

  1. 대상 브랜치: main
  2. Require a pull request before merging — main 에 직접 push 금지, PR 로만
  3. Require status checks to pass — 검사 목록에서 test 를 고른다 (한 번이라도 돌아야 목록에 뜬다)
  4. 저장

이제 검사가 실패한 PR 은 Merge 버튼이 잠긴다. 비공개 저장소의 규칙 기능은 무료 플랜에서 제한이 있을 수 있으니, 연습은 공개 저장소로 한다.

4. 비밀값 — 코드에 쓰지 않고 넘기기

배포 같은 단계에는 API 키가 필요하다. 키를 워크플로 파일에 쓰면 저장소를 보는 누구나 본다. Settings → Secrets and variables → Actions → New repository secret 에 넣고, 워크플로에서는 이름으로만 부른다. 

      - run: node scripts/deploy.js
        env:
          API_TOKEN: ${{ secrets.API_TOKEN }}
  • 스크립트 안에서는 process.env.API_TOKEN 으로 읽는다.
  • 로그에 값이 찍히면 GitHub 가 *** 로 가려 주지만, 값을 일부러 echo 하거나 변형해서 출력하면 가림을 피해 새어 나갈 수 있다. 출력하지 않는다.
  • 다른 사람이 포크해서 올린 PR 에는 비밀값이 전달되지 않는다. 남의 코드가 내 키를 빼 가지 못하게 하려는 것이다.

5. 정적 사이트라면 — 깨진 링크 검사

내 사이트(gangmini.com)처럼 빌드도 테스트도 없는 정적 사이트에도 걸 만한 검사가 있다. 글이 늘수록 늘어나는 깨진 내부 링크다. lychee 라는 링크 검사 도구의 액션을 쓰면 몇 줄이다. 

# .github/workflows/links.yml
name: links

on:
  pull_request:

jobs:
  links:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: lycheeverse/lychee-action@v2
        with:
          args: --offline --no-progress './**/*.html'
          fail: true

--offline 은 바깥 사이트에 접속하지 않고 저장소 안의 파일끼리 연결만 본다. 바깥 사이트가 잠깐 느려서 PR 이 실패하는 일을 피하려는 것이다. 아직 내 사이트에는 넣지 않았다. 글이 스무 편을 넘으면 넣을 생각이다.

자주 걸리는 것

증상원인
PR 을 올렸는데 아무것도 안 돈다폴더 이름(.github/workflows) 오타, 또는 on: 의 브랜치 이름이 다름
npm ci 에서 실패package-lock.json 을 커밋 안 했거나, package.json 과 어긋남
내 컴퓨터에선 되는데 CI 에서만 실패Node 버전 차이, 커밋 안 한 파일, 윈도·리눅스 차이(파일 이름 대소문자, 경로 구분자)
YAML 에러들여쓰기. YAML 은 탭을 못 쓰고 공백만 쓴다
필수 검사 목록에 내 검사가 안 보임그 검사가 아직 한 번도 안 돌았다. PR 을 하나 올려 한 번 돌린다

CI 가 해 주는 일은 결국 "매번 같은 확인을, 사람 대신, 빠짐없이"다. 처음엔 lint 와 테스트 한두 개로 시작해도 충분하다. 검사가 하나라도 있으면 PR 을 리뷰하는 사람은 "돌아가긴 하나"가 아니라 "잘 만들었나"에만 집중할 수 있다.

러너(runner) — 워크플로를 실제로 실행하는 컴퓨터. GitHub 가 빌려주는 것(hosted)과 내가 직접 띄우는 것(self-hosted)이 있다.
상태 검사(status check) — 커밋이나 PR 에 붙는 ✓/✗ 결과. 브랜치 보호 규칙에서 "이게 통과해야 합칠 수 있다"로 쓴다.
Secrets — 저장소 설정에 숨겨 두는 값. 워크플로에서만 이름으로 꺼내 쓰고, 저장한 뒤에는 설정 화면에서도 다시 볼 수 없다.

이어서 볼 것

  • 브랜치와 PR — CI 가 붙는 자리
  • GitHub 로 같이 일하기 — 리뷰, 브랜치 보호, CODEOWNERS
  • 검증을 남기는 법 — 손으로 하던 확인을 자동으로
  • 최신 main 따라가기 — CI 가 빨개졌을 때 main 부터 따라잡기
