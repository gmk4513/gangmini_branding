되돌리기
— 실수했을 때 쓰는 명령 6개

실습 Git restore revert reset stash reflog 2026.10.28

Git 을 쓰다 보면 반드시 실수한다. 파일을 망치고, 넣으면 안 되는 파일을 커밋에 올리고, 커밋 메시지에 오타를 내고, 이미 올린 커밋이 틀렸다는 걸 뒤늦게 안다. 명령이 많아 보이지만 고르는 기준은 하나다. 실수가 지금 어디까지 갔나.

이 글은 직접 따라 치는 실습이다. 연습용 폴더를 하나 만들고, 실수를 일부러 하나씩 저지른 뒤 되돌린다. 아래 출력은 Git 2.47 (윈도우) 에서 실제로 돌려서 나온 것을 줄인 것이다. 해시(a99ef14 같은 값)는 사람마다 다르게 나온다.

먼저 지도 — 변경은 네 칸을 지나간다

스테이징(staging area, index) — git add 로 "다음 커밋에 넣겠다"고 골라 둔 변경이 머무는 곳. 고친 파일 중 일부만 커밋하고 싶을 때 쓴다.
HEAD — 지금 내가 서 있는 커밋을 가리키는 이름. HEAD~1 은 그 하나 전, HEAD~2 는 둘 전 커밋이다.

준비 — 연습 폴더 만들기

터미널(윈도우면 Git Bash)을 열고 그대로 친다. 이름과 메일은 이 폴더에서만 쓰이게 --global 없이 넣는다.

mkdir undo-practice && cd undo-practice
git init -b main
git config user.name "gangmin"
git config user.email "me@example.com"

echo "# 메모" > notes.md
echo "첫 줄" >> notes.md
git add . && git commit -m "메모 시작"
echo "둘째 줄" >> notes.md
git commit -am "둘째 줄 추가"

커밋 두 개짜리 저장소가 생겼다. 이제 실수를 하나씩 해 본다.

1. 파일을 망쳤다 — git restore

아직 add 도 안 한 변경을 버리고, 마지막 커밋 상태로 돌린다.

echo "망친 줄" >> notes.md
git status --short
 M notes.md

git restore notes.md
git status --short
(아무것도 안 나온다 — 깨끗하다)
cat notes.md
# 메모
첫 줄
둘째 줄

주의: 이렇게 버린 변경은 Git 이 기록한 적이 없어서 되살릴 수 없다. 버리기 전에 git diff 로 무엇이 사라지는지 한 번 본다. 예전 명령 git checkout -- notes.md 도 같은 일을 하지만, 요즘은 뜻이 분명한 restore 를 쓴다.

2. 넣으면 안 되는 파일을 add 했다 — git restore --staged

비밀번호가 든 .env 를 실수로 add 했다고 하자. 커밋 전이라면 스테이징에서만 내리면 된다. 파일 자체는 그대로 남는다.

echo "secret=abc" > .env
git add .env
git status --short
A  .env

git restore --staged .env
git status --short
?? .env

A(추가 예정)가 ??(Git 이 모르는 파일)로 바뀌었다. 다시 실수하지 않게 .gitignore 에 .env 한 줄을 넣어 둔다. 실습이 끝나면 rm .env 로 지운다.

3. 커밋 메시지에 오타 — git commit --amend

echo "셋째 줄" >> notes.md
git commit -am "셋재 줄"
git log --oneline
9db6ea3 셋재 줄
245c062 둘째 줄 추가
aa8cee8 메모 시작

git commit --amend -m "셋째 줄 추가"
git log --oneline
edc9c08 셋째 줄 추가
245c062 둘째 줄 추가
aa8cee8 메모 시작

해시가 9db6ea3 에서 edc9c08 로 바뀐 것을 본다. amend 는 커밋을 "고치는" 게 아니라 새 커밋으로 갈아 끼운다. 빠뜨린 파일이 있으면 git add 파일 후 git commit --amend --no-edit 로 메시지는 그대로 두고 파일만 더할 수 있다. 이미 push 한 커밋에 amend 하면 원격과 기록이 어긋나므로, push 전에만 쓴다.

4. 이미 올린 커밋이 틀렸다 — git revert

"셋째 줄 추가"가 main 에 올라가서 동료들도 받아 갔다고 치자. 이때 기록을 지우면 동료 컴퓨터의 기록과 어긋난다. revert 는 그 커밋의 반대 변경을 담은 새 커밋을 만든다. 기록은 늘어나기만 하니 함께 쓰는 브랜치에서도 안전하다. 

git revert --no-edit HEAD
[main a99ef14] Revert "셋째 줄 추가"
 1 file changed, 1 deletion(-)

git log --oneline
a99ef14 Revert "셋째 줄 추가"
edc9c08 셋째 줄 추가
245c062 둘째 줄 추가
aa8cee8 메모 시작

HEAD 자리에 아무 커밋 해시나 넣으면 그 커밋만 골라 취소한다. GitHub 에서도 합쳐진 PR 화면의 Revert 버튼이 같은 일을 하는 PR 을 만들어 준다.

5. 최근 커밋 몇 개를 없던 일로 — git reset

아직 push 하지 않은 커밋이라면 reset 으로 HEAD 를 뒤로 옮길 수 있다. 옵션 세 개가 헷갈리는데, 차이는 "옮기면서 어디까지 같이 되돌리나" 하나뿐이다.

실험 커밋 세 개를 만들고, 세 옵션을 차례로 써 본다.

for i in 1 2 3; do echo "실험 $i" >> notes.md; git commit -qam "실험 $i"; done

git reset --soft HEAD~1      # 커밋만 취소, 변경은 add 된 채로
git status --short
M  notes.md             ← 왼쪽 M: 스테이징에 있다

git commit -qm "실험 3 (다시)"
git reset HEAD~1             # = --mixed. add 도 취소
git status --short
 M notes.md             ← 오른쪽 M: 파일만 고쳐져 있다

git commit -qam "실험 3 (또)"
git reset --hard HEAD~1      # 파일까지 되돌림
HEAD is now at 6a5b1f2 실험 2
git status --short
(깨끗하다 — "실험 3" 줄이 파일에서도 사라졌다)

쓰임새는 이렇다. soft 는 커밋 여러 개를 하나로 다시 묶고 싶을 때(되돌린 뒤 한 번에 커밋), mixed 는 add 를 다시 고르고 싶을 때, hard 는 정말로 다 버리고 싶을 때다. hard 를 치기 전에는 git status 로 커밋 안 한 변경이 없는지 꼭 본다. 커밋 안 한 변경은 아래 reflog 로도 못 살린다.

6. 하던 걸 잠깐 치워 두기 — git stash

고치는 중에 급한 버그 수정을 먼저 해야 할 때가 있다. 하던 걸 커밋하기엔 덜 됐고, 버리기엔 아깝다. stash 는 변경을 서랍에 넣고 작업 폴더를 깨끗하게 만든다. 

echo "하다 만 작업" >> notes.md
git stash
Saved working directory and index state WIP on main: 6a5b1f2 실험 2
git status --short
(깨끗하다 — 이제 다른 브랜치로 가서 급한 일을 한다)
git stash list
stash@{0}: WIP on main: 6a5b1f2 실험 2

git stash pop                # 서랍에서 꺼내 다시 적용하고, 서랍에서는 지운다
Dropped refs/stash@{0} (07cf51c9…)
git status --short
 M notes.md

새로 만든(아직 Git 이 모르는) 파일은 기본으로는 서랍에 안 들어간다. 같이 넣으려면 git stash -u 를 쓴다. 서랍이 쌓이면 무엇이었는지 잊으니, git stash push -m "로그인 화면 하던 것" 처럼 이름을 붙여 두면 좋다.

덤. 지운 커밋 살리기 — git reflog

reset --hard 로 커밋을 날렸다고 끝이 아니다. Git 은 HEAD 가 움직인 기록을 따로 남긴다(기본 90일). 커밋까지 했던 것이라면 거의 언제나 살릴 수 있다. 

git reset --hard HEAD~2      # 실수로 너무 많이 되돌렸다
git reflog
a99ef14 HEAD@{0}: reset: moving to HEAD~2
6a5b1f2 HEAD@{1}: reset: moving to HEAD
6a5b1f2 HEAD@{2}: reset: moving to HEAD~1
3385926 HEAD@{3}: commit: 실험 3 (또)
6a5b1f2 HEAD@{4}: reset: moving to HEAD~1
ee19ab8 HEAD@{5}: commit: 실험 3 (다시)

git reset --hard 3385926     # "실험 3 (또)" 를 커밋한 순간으로
HEAD is now at 3385926 실험 3 (또)

위에서 reset --hard 로 지웠던 "실험 3 (또)"까지 돌아왔다. 돌아가기 겁나면 git branch rescue 3385926 으로 그 커밋에 이름만 붙여 두고 천천히 살펴봐도 된다. (중간의 moving to HEAD 줄은 stash 가 남긴 것이다.)

상황별로 고르기

상황명령이미 push 했다면?
파일을 망쳤다 (add 전)git restore 파일해당 없음 (커밋 전)
잘못 add 했다git restore --staged 파일해당 없음
마지막 커밋 메시지·파일 실수git commit --amend쓰지 않는다. 고치는 커밋을 하나 더 쌓는다
예전 커밋 하나가 틀렸다git revert 해시그대로 revert — 이게 정답
최근 커밋 몇 개를 없던 일로git reset [--soft|--hard] HEAD~N공용 브랜치면 revert. 내 브랜치면 reset 후 push --force-with-lease
하던 걸 잠깐 치우기git stash / git stash pop해당 없음
reset 으로 커밋을 날렸다git reflog → git reset --hard 해시원격에 남아 있으면 git fetch 로 다시 받는다

외울 규칙은 하나다. 남이 받아 간 기록은 지우지 말고 쌓는다(revert). 나만 가진 기록은 마음대로 고쳐도 된다(amend, reset). 비밀번호나 API 키를 이미 push 했다면 되돌리기로는 부족하다. 기록 어딘가에 남아 있으니, 그 키를 먼저 폐기하고 새로 발급받는다.

reflog — 내 컴퓨터에서 HEAD 가 어디로 움직였는지 적어 둔 일지. 내 저장소에만 있고 push 되지 않는다.
WIP — Work In Progress. "하던 중"이라는 뜻으로, stash 가 자동으로 붙이는 이름이다.
