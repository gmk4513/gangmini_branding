코드 구조 한눈에
— 레이어드 아키텍처와 KISS

이론 레이어드 아키텍처 KISS 모놀리스 MSA DTO 2026.10.28

혼자 만들 때는 코드가 어디 있든 상관없었다. 내가 다 기억하니까. 그런데 팀에서는 다른 사람이 "메모 저장하는 코드 어디 있어요?"라고 물었을 때 폴더 이름만 보고 찾아갈 수 있어야 한다. 그리고 데이터베이스를 바꿨을 때 API 코드까지 줄줄이 고치는 일이 없어야 한다. 그걸 위한 약속이 코드 구조(아키텍처)다.

이 시리즈는 파이썬(FastAPI)으로 만든 작은 메모 API, memo-api를 예로 든다. 메모를 만들고, 읽고, 요약하는 서버다. 기능은 작지만 회사 백엔드에서 쓰는 구조를 그대로 따른다. 이 글은 전체 지도다.

먼저, 한 덩어리냐 여러 덩어리냐

서버를 나누는 방법은 크게 두 가지다. 모든 기능을 하나의 프로그램으로 만드는 모놀리스, 기능마다 따로 도는 작은 서버로 쪼개 네트워크로 서로 부르는 MSA(마이크로서비스).

MSA 가 멋져 보이지만 비용이 크다. 서버가 셋이면 배포도 셋, 모니터링도 셋이고, 메모 하나 만드는 데 네트워크를 몇 번 건너야 한다. 그래서 나온 원칙이 KISS(Keep It Short and Simple) — 가능한 가장 단순한 구조로 시작하라다. 쪼개야 할 분명한 이유가 생기기 전에는 쪼개지 않는다.

쪼갤 만한 이유예
프로그램이 너무 커졌다한 줄 고치는 데 전체를 다시 빌드·배포하느라 반나절이 걸린다. 팀 여럿이 같은 코드를 동시에 건드려 계속 부딪힌다
자원을 따로 써야 한다요약 기능만 GPU 를 쓰고 트래픽이 몰린다. 이 부분만 따로 늘리고 줄이고 싶다
죽어도 따로 죽어야 한다결제가 멈춰도 메모는 써져야 한다

이유가 없다면 모놀리스 하나 + 안을 잘 나눈 구조가 답이다. 이 시리즈가 다루는 게 바로 그 "안을 잘 나누는" 방법이다.

안을 나누는 기본: 세 층

가장 널리 쓰는 방식이 레이어드 아키텍처(층 구조)다. 식당으로 비유하면 이렇다.

  • 표현 층(presentation) — 홀 직원. 손님(외부 요청)의 주문을 받아 주방이 알아듣는 말로 바꾼다. FastAPI 라우터가 여기다.
  • 비즈니스 층(business, service) — 주방장. "제목은 50자까지", "남의 메모는 못 고친다" 같은 규칙을 지키며 실제 일을 한다.
  • 영속 층(persistence, repository) — 창고 담당. 재료(데이터)를 넣고 꺼낸다. 데이터베이스와 말하는 건 여기뿐이다.

DTO · 도메인 · 엔티티 — 같은 메모, 다른 옷

처음엔 셋이 다 "메모"인데 왜 따로 만드나 싶었다. 이유는 각 경계가 바뀌는 이유가 다르기 때문이다. 

# webapp/routers/memo.py — DTO: 바깥과 주고받는 모양 (API 약속)
class CreateMemoRequest(BaseModel):
    title: str
    body: str

class MemoResponse(BaseModel):
    id: int
    title: str
    summary: str

# src/memo/domains.py — 도메인: 서비스가 생각하는 메모 (규칙의 주인공)
@dataclass
class Memo:
    id: int
    user_id: int
    title: str
    body: str
    summary: str = ""

# src/memo/entities.py — 엔티티: DB 테이블의 한 줄
class MemoRow(Base):
    __tablename__ = "memos"
    id = Column(Integer, primary_key=True)
    user_id = Column(Integer, index=True)
    title = Column(String(50))
    body = Column(Text)
    summary = Column(Text)
    created_at = Column(DateTime)
이름누구의 사정을 따르나바뀌는 때
DTOAPI 를 쓰는 앱·프론트엔드화면에 보여 줄 칸이 바뀔 때. body 를 응답에서 빼도 서비스는 모른다
도메인서비스의 규칙"메모에 태그가 생긴다"처럼 일하는 방식이 바뀔 때
엔티티데이터베이스인덱스를 달거나 칼럼 타입을 바꿀 때. created_at 처럼 DB 만 아는 칸도 있다

하나로 합쳐 쓰면 편하지만, DB 칼럼 이름 하나 바꿨는데 API 응답 모양이 같이 바뀌어 앱이 깨지는 일이 생긴다. 옷을 갈아입히는 번거로움이 그 사고를 막는 값이다.

의존은 한 방향으로만

층 구조에서 가장 중요한 약속은 위가 아래를 부르고, 아래는 위를 모른다는 것이다. 라우터는 서비스를 부르지만 서비스는 라우터가 있는지조차 모른다. 서비스는 저장소를 부르지만 저장소는 서비스를 모른다.

덕분에 생기는 일: REST API 를 gRPC 로 바꿔도 서비스는 그대로고(표현 층만 새로), PostgreSQL 을 다른 저장소로 바꿔도 서비스는 그대로다(영속 층만 새로). "바뀌는 곳을 한 층에 가둔다" — 이게 층을 나누는 진짜 이유다.

memo-api 의 폴더 지도

memo-api/
├── src/                 ← 비즈니스 로직 (서버가 없어도 돌아가는 부분)
│   ├── memo/            ← 메모라는 "도메인" 하나 = 모듈 하나
│   │   ├── domains.py       도메인 객체 (Memo)
│   │   ├── entities.py      DB 테이블 모양 (MemoRow)
│   │   ├── repository.py    영속 층: 넣고 꺼내기
│   │   ├── service.py       비즈니스 층: 규칙
│   │   └── container.py     이 모듈의 부품 조립도 (DI)
│   └── common/
│       ├── exceptions.py    NotFound, Forbidden …
│       └── logger.py
├── webapp/              ← 표현 층 (HTTP 를 아는 유일한 곳)
│   ├── main.py              FastAPI 앱, 시작할 때 조립
│   └── routers/memo.py      주소 · DTO
└── tests/

src 와 webapp 을 나눈 이유, 모듈을 도메인으로 나눈 이유는 다음 글에서, 층마다 파일이 무슨 일을 하는지는 그다음 글에서 하나씩 연다.

아키텍처 — 코드를 어떤 덩어리로 나누고, 덩어리끼리 어떤 방향으로 부르게 할지 정한 약속.
모놀리스 — 기능 전체가 프로그램 하나로 빌드·배포되는 구조. 낡은 방식이 아니라 대부분의 서비스가 시작하는 기본값이다.
MSA (Microservice Architecture) — 기능을 독립된 서버 여러 개로 나누고 네트워크로 잇는 구조.
DTO (Data Transfer Object) — 경계를 건너 데이터를 옮기기 위한 상자. 로직 없이 칸만 있다.
도메인 — 서비스가 다루는 대상과 그 규칙. 메모 앱의 도메인은 메모, 사용자 같은 것이다.
엔티티 — 여기서는 DB 테이블 한 줄에 대응하는 객체. (책에 따라 도메인 객체를 엔티티라 부르기도 해서 헷갈리기 쉽다.)

정리

약속한 줄 이유
KISS — 모놀리스로 시작나눌 이유가 생기기 전의 MSA 는 비용만 낸다
세 층으로 나누기바뀌는 이유가 다른 코드를 다른 곳에
경계마다 데이터 모양 바꾸기DB 를 바꿔도 API 가, API 를 바꿔도 DB 가 안 흔들린다
의존은 한 방향아래 층을 갈아 끼울 수 있다
