브랜치와 Pull Request
— 회사에서 매일 하는 흐름

실습 Git GitHub 브랜치 Pull Request gh CLI 2026.10.28

혼자 할 때는 main 에 바로 커밋해도 된다. 지금까지 내 프로젝트들이 다 그랬다. 회사에서는 거의 그러지 않는다. main 은 "언제든 배포해도 되는 상태"로 지키고, 일은 브랜치에서 한 뒤 Pull Request(PR) 로 동료의 확인을 받아 합친다.

이 글은 Git 첫걸음에서 만든 git-practice 저장소에서 이어진다. "소개 페이지 추가"라는 작은 일을 하나 정해서 한 바퀴 돈다.

한 바퀴의 모양

브랜치(branch) — 커밋 줄기의 갈래. 실체는 "어느 커밋을 가리키는 이름표" 하나라서, 만들고 지우는 데 비용이 거의 없다.
Pull Request(PR) — GitHub 기능. "이 브랜치의 변경을 저 브랜치에 합쳐 주세요"라는 요청 페이지. 변경 내용(diff), 댓글, 리뷰, 자동 검사 결과가 한곳에 모인다. GitLab 에서는 Merge Request(MR) 라고 부른다.

① 브랜치 따기

항상 최신 main 에서 딴다. 오래된 main 에서 따면 나중에 충돌이 커진다.

git switch main
git pull                          # 최신으로
git switch -c feat/about-page     # 새 브랜치를 만들고 그리로 이동
Switched to a new branch 'feat/about-page'

switch -c 의 c 는 create. 예전 글에서 자주 보이는 git checkout -b 와 같은 일을 한다. checkout 이 하는 일이 너무 많아서 Git 2.23 부터 switch(브랜치 이동)와 restore(파일 되돌리기)로 나뉘었다.

브랜치 이름 짓기

앞머리뜻예
feat/새 기능feat/about-page
fix/버그 고침fix/ios-voice-autoplay
chore/설정·의존성 같은 잡일chore/enable-r8
docs/문서만docs/readme-setup

팀마다 규칙이 다르니 첫 주에 기존 브랜치 목록(git branch -r)을 보고 따라 한다. 이슈 번호를 붙이는 팀도 많다(fix/123-login-crash).

② 커밋 · ③ push

printf '# 소개\n\n연습 중인 개발자.\n' > about.md
git add about.md
git commit -m "소개 페이지 추가"
[feat/about-page 3e8bf01] 소개 페이지 추가
 1 file changed, 3 insertions(+)
 create mode 100644 about.md

대괄호 안에 지금 브랜치 이름이 찍힌다. main 이 아니라 브랜치에 기록됐다. 이제 GitHub 에 올린다.

git push -u origin feat/about-page
branch 'feat/about-page' set up to track 'origin/feat/about-page'.
To https://github.com/내아이디/git-practice.git
 * [new branch]      feat/about-page -> feat/about-page

브랜치마다 처음 한 번은 -u origin 이름 이 필요하다. 그 뒤로 같은 브랜치에서는 git push 만 친다. 연결 상태는 이렇게 본다. 

git branch -vv
* feat/about-page 3e8bf01 [origin/feat/about-page] 소개 페이지 추가
  main            e6f7baf [origin/main] .gitignore 추가

④ PR 열기

웹에서

  1. push 직후 GitHub 저장소 페이지에 노란 띠 "feat/about-page had recent pushes" 와 Compare & pull request 버튼이 뜬다. 누른다
  2. base: main ← compare: feat/about-page 인지 확인한다. 방향이 반대면 엉뚱한 곳에 합쳐진다
  3. 제목과 설명을 쓴다 (아래 틀)
  4. 오른쪽 Reviewers 에서 리뷰어를 고른다. 아직 덜 됐으면 버튼 옆 ▾ 에서 Create draft pull request

명령줄에서

gh pr create --fill                 # 커밋 메시지로 제목·설명을 채운다
gh pr create --fill --draft         # 초안으로
gh pr create -t "소개 페이지 추가" -b "설명" -r 동료아이디
gh pr create --web                  # 작성 화면을 브라우저로 연다

PR 설명에 쓰는 것

## 무엇을
소개 페이지(about.md)를 추가했습니다.

## 왜
README 에서 자기소개가 길어져서 따로 뺐습니다. (#12)

## 확인한 것
- [x] 로컬에서 마크다운 렌더 확인
- [ ] 모바일 화면 확인 필요

## 리뷰 때 봐 주셨으면 하는 것
문구 톤이 다른 문서와 맞는지

리뷰어는 내 머릿속을 모른다. "왜" 와 "무엇을 확인했나" 가 있으면 리뷰가 빨라진다. #12 처럼 이슈 번호를 쓰면 자동으로 연결되고, Closes #12 라고 쓰면 PR 이 합쳐질 때 그 이슈가 닫힌다.

⑤ 리뷰 받고 고치기

리뷰어가 Files changed 탭에서 줄마다 댓글을 단다. 고칠 게 있으면 같은 브랜치에서 커밋을 더 하고 push 하면 된다. PR 은 브랜치를 보고 있어서 저절로 갱신된다. 새 PR 을 만들 필요가 없다. 

# 리뷰 반영
git add about.md
git commit -m "소개 문구 다듬기 (리뷰 반영)"
git push

내가 리뷰하는 쪽일 때 쓰는 명령도 있다.

gh pr list                     # 열린 PR 목록
gh pr checkout 1               # 1번 PR 의 브랜치를 내 컴퓨터로 받아 직접 돌려 보기
gh pr diff 1                   # 변경 내용
gh pr review 1 --approve       # 승인
gh pr review 1 --request-changes -b "로그인 실패 처리가 빠졌어요"

리뷰 댓글에는 감정 대신 이유를 쓰고, 받을 때는 "왜 이렇게 했는지"로 답한다. 모든 댓글에 답하거나 반영하고 나서 다시 리뷰를 요청하는 게 예의다(PR 오른쪽 Reviewers 옆 ↻).

⑥ 합치기 — merge 버튼의 세 가지

승인과 자동 검사가 통과하면 PR 아래 초록 버튼으로 합친다. 버튼 옆 ▾ 에 세 가지가 있다.

gh pr merge 1 --squash --delete-branch    # squash 로 합치고 브랜치도 지운다
gh pr merge 1 --merge                     # merge commit
gh pr merge 1 --rebase                    # rebase
gh pr merge 1 --squash --auto             # 검사가 다 통과하면 저절로 합쳐지게 예약

⑦ 뒷정리 — main 받아오고 브랜치 지우기

GitHub 에서 합쳐졌어도 내 컴퓨터의 main 은 아직 옛날 그대로다. 받아온다.

git switch main
git pull
Updating e6f7baf..ec7779d
Fast-forward
 about.md | 3 +++
 1 file changed, 3 insertions(+)
 create mode 100644 about.md

Fast-forward 는 "내 main 에 새로 생긴 게 없어서, 이름표만 앞으로 옮겼다"는 뜻이다. 이제 다 쓴 브랜치를 지운다. 

git branch -d feat/about-page                 # 내 컴퓨터에서
git push origin --delete feat/about-page      # GitHub 에서 (merge 할 때 안 지웠다면)
git fetch --prune                             # 원격에서 사라진 브랜치 이름표 정리

여기서 한 번 막힌다. squash 로 합친 브랜치를 -d 로 지우면 이렇게 나올 때가 있다.

error: the branch 'feat/x' is not fully merged
hint: If you are sure you want to delete it, run 'git branch -D feat/x'

squash 는 A·B 를 뭉쳐 새 커밋 S 를 만든다. Git 이 보기엔 내 브랜치의 A·B 가 main 에 없으니 "아직 안 합쳤다"고 판단한다. GitHub 에서 PR 이 Merged 로 보이는 걸 확인했다면 git branch -D(대문자, 강제)로 지워도 된다.

정리

단계명령
① 브랜치git switch main && git pull && git switch -c feat/이름
② 커밋git add … → git diff --staged → git commit -m "…"
③ pushgit push -u origin feat/이름 (처음만 -u)
④ PR웹 Compare & pull request, 또는 gh pr create --fill
⑤ 리뷰같은 브랜치에 커밋 더 하고 git push
⑥ 합치기팀 규칙대로 (흔히 Squash and merge)
⑦ 정리git switch main && git pull → git branch -d (squash 면 -D)

PR 은 크기가 작을수록 빨리 합쳐진다. 리뷰어가 10분 안에 읽을 수 있는 정도(대략 수백 줄 이하)가 좋다. AI 로 한 번에 크게 만든 변경일수록 의미 단위로 나눠서 PR 여러 개로 올린다.
