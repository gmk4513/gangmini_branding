직무 이슈 PR 추정 ADR 2026.10.28

혼자 만들 때는 머릿속 계획이 곧 계획이다. 팀에서는 그게 글이 되어야 한다. 누가 무엇을 하는지, 언제 끝나는지, 왜 이렇게 했는지가 글로 있어야 남이 이어받는다. AI 가 코드를 빨리 써 줄수록 이 차이가 커진다. 코드는 금방 생기는데, 그 코드가 무엇을 위한 것이고 왜 이 모양인지는 사람이 적어야 한다.

일이 흘러가는 길

일을 나누기

좋은 작업 단위는 하루~이틀 안에 끝나고, 끝났는지 확인할 수 있는 크기다. "안드로이드 출시"는 너무 크다. 다이어리 안드로이드 출시를 나눠 보면 이렇다(괄호는 추정의 예). 

안드로이드 출시
├─ Play Console 앱 만들고 등록 정보 채우기      (반나절)
├─ 결제 상품 등록 + RevenueCat 안드로이드 키     (반나절)
├─ 서비스 계정 만들어 EAS 자동 제출 연결         (반나절)
├─ 스토어 그래픽 (아이콘 512, 그래픽 이미지)      (반나절)
└─ 비공개 테스트 → 프로덕션                     (심사 대기 포함 며칠)

나누는 기준은 "이것만 따로 PR 로 올려 리뷰받을 수 있나"다. 나눌 수 없어 보이면 대개 아직 무엇을 할지 덜 정한 것이다.

얼마나 걸리나 — 추정

  • 범위로 말한다. "3일"보다 "2~4일, 결제 심사가 변수". 모르는 부분이 어디인지 같이 말하는 게 숫자보다 중요하다.
  • 모르는 건 먼저 찔러 본다. R8 을 켜면 앱이 깨질지 모를 때, 먼저 로컬 빌드를 한 번 돌려 보면(스파이크) 추정이 확 좁아진다.
  • 늦어질 것 같으면 일찍 말한다. 마감 날 "못 했어요"가 팀에서 가장 비싸다.

이슈 쓰기

버그 이슈는 남이 그대로 따라 하면 똑같이 재현되게 쓴다. 

제목: 아이폰에서 게임 목소리가 안 나온다 (엔진 소리는 나옴)

## 재현
1. 아이폰 사파리로 게임 주소 열기
2. 출발 → 첫 NPC 에게 다가가기

## 기대: 목소리 대사가 나온다
## 실제: 말풍선만 뜨고 소리 없음. 엔진 소리는 난다
## 환경: iOS 사파리 / PC 크롬에서는 정상

이건 실제로 겪은 일이다(감스트 스쿠터). "엔진 소리는 난다"는 한 줄이 원인을 거의 알려 줬다. 엔진은 Web Audio, 목소리는 <audio> 태그였다. 이슈에 되는 것과 안 되는 것을 같이 적으면 범위가 좁혀진다.

리뷰어는 코드를 읽기 전에 설명을 읽는다. 설명이 좋으면 리뷰가 "이게 뭐예요?"가 아니라 "이 판단 괜찮네요 / 여기는 이렇게 하면 어때요"로 바로 간다. AI 가 쓴 코드일수록 왜와 확인 방법 칸을 사람이 직접 채워야 한다. 그게 그 코드의 주인이라는 표시다.

선택지를 장단점으로 말하기

"이게 좋아요"보다 "A 와 B 가 있고, A 는 이게 좋고 저게 나쁘다. 지금 상황에선 A"가 팀을 빨리 움직인다. 상대가 다른 정보를 갖고 있으면 바로 끼어들 수 있기 때문이다. 

대형 화면 경고 (세로 고정)
A. 그대로 둔다      — 비용 0. 경고만 남음. 기한 없음
B. 가로도 지원      — 그림판·줄공책 레이아웃을 다시 짜야 함. 며칠
→ 지금은 A. 태블릿 사용자 비율이 보이면 다시 판단

결정 기록 (ADR)

중요한 선택은 짧은 문서로 남긴다. 업계에서는 ADR(Architecture Decision Record)이라고 부른다. 형식은 단순하다. 감스트 스쿠터에서 한 선택을 이 형식으로 옮기면 이렇다. 

# 0003. 게임 서버를 두지 않는다

상황: 감스트 스쿠터는 혼자 하는 게임. 방문자 대부분이 폰이고 릴스로 한꺼번에 몰린다.
결정: 정적 파일만 Cloudflare Pages 로. 게임 로직은 전부 브라우저에서.
대가: 순위표·방문 집계가 필요하면 다른 서버(bamti-bomb)에 얹어야 한다.
날짜: 2026-10-24

나는 이미 비슷한 걸 하고 있었다. 기록 글마다 "무엇을 왜 골랐나" 표를 두고, 다이어리 저장소에는 HANDOFF.md 에 "기획과 다르게 구현한 것 (의도적)", "바꾸면 안 되는 규칙"을 적어 뒀다. 이게 ADR 의 역할이다. 팀에서는 이걸 저장소의 docs/adr/ 에 번호를 붙여 쌓는다.

이슈(issue) — 할 일·버그·제안을 하나씩 적는 GitHub 의 글. 번호가 붙고, PR 과 이어진다.
스파이크(spike) — 추정을 위해 결과물이 아니라 정보를 얻으려고 짧게 해 보는 작업.
ADR — 설계 결정 하나를 상황·결정·대가로 적은 짧은 문서. 결정을 바꾸면 지우지 않고 새 ADR 로 "0003 을 대체한다"고 쓴다.
