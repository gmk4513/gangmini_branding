직무 팀에서 일하기 코드 리뷰 diff AI 코딩 2026.10.28

팀에서 일하기 시리즈 1번이다. 여섯 가지 중 가장 앞에 둔 이유는 간단하다. 리뷰에서 "이 줄은 왜 있어요?"에 답하지 못하면, 코드가 아무리 잘 돌아가도 신뢰가 깎인다. 나머지 역량은 전부 설명할 수 있는 코드를 전제로 한다.

기준은 하나로 정했다. 올리는 변경의 모든 줄에 대해 "이 줄이 없으면 어떻게 되나"에 답할 수 있어야 한다.

diff 읽는 법

리뷰어는 파일 전체가 아니라 diff, 즉 바뀐 줄만 본다. 그래서 내가 먼저 같은 화면을 봐야 한다. git diff 로 보든 GitHub PR 의 "Files changed" 탭으로 보든 모양은 같다. 

diff --git a/app.json b/app.json
--- a/app.json
+++ b/app.json
@@ -2,7 +2,7 @@
     "name": "학창시절 다이어리",
     "slug": "school-diary",
-    "version": "1.0.0",
+    "version": "1.0.1",
     "scheme": "schooldiary",

마지막 설명이 중요하다. 다이어리 저장소에서 14개 파일 · 3,316줄이 바뀐 것처럼 보였는데, 공백과 줄바꿈을 빼고 보니 진짜 변경은 86줄이었다. 공백을 무시하는 옵션으로 진짜 변경만 골라 볼 수 있다. 

git diff --stat                              # 파일별로 몇 줄 바뀌었나
git diff -w --ignore-cr-at-eol --stat        # 공백·줄바꿈 차이는 빼고
git diff --staged                            # add 해 둔 것(커밋될 것)만

예: R8 을 켠 변경을 한 줄씩

다이어리 앱에서 Play Console 이 "DEX 난독화 3%" 경고를 띄워서, AI 와 같이 R8(코드 줄이기·난독화)을 켰다. 이걸 리뷰에 올린다고 생각하고 줄마다 "없으면?"을 답해 본다. 

  "plugins": [
    "./plugins/withAsciiRootProjectName.js",
+   "./plugins/withGradleMemory.js",
    "expo-router",
    ...
+   [
+     "expo-build-properties",
+     {
+       "android": {
+         "enableMinifyInReleaseBuilds": true,
+         "enableShrinkResourcesInReleaseBuilds": true
+       }
+     }
+   ]
  ],
줄하는 일없으면?
expo-build-propertiesExpo 가 빌드 때마다 새로 만드는 android/ 폴더에 빌드 설정을 넣어 주는 플러그인build.gradle 을 직접 고쳐야 하는데, 다음 빌드에서 폴더가 새로 만들어지며 사라진다
enableMinifyInReleaseBuilds릴리스 빌드에서 R8 을 켠다. 안 쓰는 코드를 지우고 이름을 짧게 바꾼다Play 경고가 그대로 남는다. 2027년 2월 기한
enableShrinkResources…코드가 안 쓰는 그림·레이아웃 파일을 뺀다앱이 조금 더 크다. 경고와는 상관없어서 빼도 되지만, 켜도 손해가 없어 같이 켰다
withGradleMemory.js빌드 도구(Gradle)의 메모리를 4GB 로 늘린다R8 단계에서 "OutOfMemoryError: Metaspace" 로 빌드가 죽었다. 로컬에서 실제로 겪었다
"version": "1.0.1"새 버전 이름스토어에는 올라가지만 사용자가 무엇이 바뀐 버전인지 구분하기 어렵다

이렇게 정리해 보니 리뷰어가 물을 만한 것이 미리 보였다. "R8 을 켜면 앱이 죽을 수도 있지 않나?" 맞다. React Native 는 네이티브 모듈을 이름으로 찾아서, R8 이 그 이름을 바꾸면 깨진다. 그래서 PR 본문에 "릴리스 빌드를 에뮬레이터에 깔아 그림판·DB 저장·서버 호출·결제 가격을 확인했다"를 같이 적어야 한다. 질문이 오기 전에 답을 붙여 두는 것이다.

리뷰 요청 전에 스스로 하는 것

점검표

  • 바뀐 파일 목록이 예상과 맞나. 고치려던 것과 상관없는 파일이 끼어 있으면 빼거나 따로 커밋한다.
  • 모든 줄을 설명할 수 있나. 못 하는 줄이 있으면 아래 질문을 AI 에게 한다.
  • 지울 게 없나. console.log, 주석 처리된 옛 코드, 쓰지 않는 함수.
  • 비밀 값이 없나. API 키, .env, 서비스 계정 JSON 이 diff 에 없는지.
  • 어떻게 확인했나를 적었나. "됐다"가 아니라 "무엇을 해서 무엇을 봤다".

AI 에게 묻는 질문

AI 에게 "설명해 줘"라고만 하면 코드를 그대로 말로 옮긴 답이 온다. 질문을 날카롭게 해야 내가 이해했는지 확인된다.

질문무엇을 알게 되나
이 줄이 없으면 어떻게 돼?그 줄이 막는 문제. 답이 "별일 없다"면 지울 후보다
다른 방법은 뭐가 있었고, 왜 이걸 골랐어?선택의 이유. 리뷰어가 가장 자주 묻는 것
이게 깨지면 어떤 증상으로 나타나?나중에 버그가 났을 때 여기를 의심할 단서
이걸 확인하려면 뭘 해 보면 돼?PR 본문에 적을 검증 방법
동료가 이 PR 을 리뷰한다면 뭘 지적할까?내 눈에 안 보이는 약점. AI 를 리뷰어로 쓰기

그리고 답을 듣고 끝내지 않는다. 내 말로 다시 써 본다. PR 본문이나 커밋 메시지에 내가 쓴 설명이 곧 이해했다는 증거다. 못 쓰겠으면 아직 모르는 것이다.

리뷰어는 이 순서로 읽는다

  1. 제목과 본문. 무엇을 왜 바꿨나. 여기서 이해가 안 되면 코드를 열지도 않고 질문부터 남긴다.
  2. 바뀐 파일 목록과 크기. 설명에 비해 너무 많이 바뀌었으면 의심한다.
  3. 핵심 파일의 diff. 로직이 맞나, 빠진 경우는 없나.
  4. 검증. 테스트가 있나, 어떻게 확인했다고 썼나.

그래서 PR 본문은 이 네 가지에 미리 답하는 모양으로 쓴다. PR 을 실제로 만드는 법은 브랜치와 PR 따라 하기에 있다. 

## 무엇을
Android 릴리스 빌드에서 R8(코드 줄이기·난독화)을 켠다. 버전 1.0.1.

## 왜
Play Console 경고 "DEX 코드 최적화 기준점 미만 — 난독화 3%" (기한 2027년 2월).

## 어떻게 확인했나
- 로컬 릴리스 빌드를 에뮬레이터에 설치
- 그림판 그리기, 일기 저장, 선생님 한마디(서버), 결제 화면 가격 표시 확인
- logcat 에 크래시 없음

## 주의
R8 단계에서 Gradle 메모리가 모자라 withGradleMemory.js 로 4GB 로 올렸다.

PR (Pull Request) — "내 브랜치의 변경을 합쳐 달라"는 요청. 리뷰와 토론이 그 위에서 이뤄진다.
hunk — diff 에서 @@ 로 시작하는 한 덩어리. 바뀐 줄과 그 앞뒤 문맥 몇 줄로 이뤄진다.
R8 — 안드로이드 릴리스 빌드에서 자바·코틀린 코드를 줄이고 이름을 짧게 바꾸는 도구.
