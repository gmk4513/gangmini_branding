직무 테스트 체크리스트 E2E 헤드리스 브라우저 2026.10.28

학창시절 다이어리 안드로이드 빌드에 R8(코드 줄이기·난독화)을 켰다. R8 은 가끔 라이브러리를 조용히 깨뜨린다. 그래서 에뮬레이터에 설치해 크레파스로 그어 보고, 일기를 저장해 보고, 결제 화면 가격이 뜨는지 하나씩 눌러 봤다. 다 정상이었다.

문제는 그 확인이 내 머릿속에만 있다는 것이다. 다음 달에 라이브러리를 올리는 사람(나일 수도 있다)은 무엇을 눌러 봐야 하는지 모른다. 팀에서 "검증"은 확인하는 일이 아니라 확인하는 방법을 남기는 일이다.

손으로 한 확인 vs 남긴 확인

손으로 눌러 봄체크리스트자동 테스트
누가 다시 할 수 있나나만누구나 (사람 손으로)누구나 (명령 한 줄)
얼마나 걸리나매번 몇 분~몇십 분매번 같음처음 만들 때만 오래
빠뜨림자주적다없다 (적힌 것만은)
언제 돌리나생각날 때릴리스 전PR 마다 자동 (CI)

셋 중 하나만 고르는 게 아니다. 처음엔 손으로 해 보고, 두 번째부터는 체크리스트로 적고, 세 번째쯤 "또 이걸 하네" 싶으면 자동화한다. 손으로 한 확인을 버리지 않고 다음 단계로 올리는 것이 요점이다.

테스트 피라미드

자동 테스트는 크기에 따라 세 층으로 나눈다. 아래로 갈수록 빠르고 싸고 많이 쓰고, 위로 갈수록 실제 사용자에 가깝지만 느리고 잘 깨진다.

층다이어리에서 예를 들면도구 (React Native 기준)
단위"설치 8일째면 체험 끝" 같은 날짜 계산 함수Jest
통합일기를 저장하면 DB 에 들어가고, 다시 열면 같은 내용이 나온다Jest + 테스트용 DB
E2E앱을 켜서 그림일기 → 크레파스로 긋기 → 저장 → 도장이 보인다Maestro, Detox

E2E (End-to-End) — 처음부터 끝까지. 실제 앱을 켜고 사람이 하듯 누르고 화면을 확인하는 테스트.
Maestro · Detox — 모바일 앱 E2E 도구. Maestro 는 "이 글자를 눌러라, 이 글자가 보여야 한다"를 YAML 로 적고, Detox 는 자바스크립트 테스트 코드로 쓴다.
CI (지속적 통합) — 코드를 올릴 때마다 서버가 자동으로 빌드하고 테스트를 돌리는 것. GitHub 에서는 Actions 로 한다.

오늘의 확인을 남기면 이렇게 된다

1단계 — 체크리스트로 적는다

손으로 한 걸 그대로 적기만 해도 절반은 된다. 핵심은 "왜 이걸 보나"를 같이 적는 것이다. 이유가 없으면 다음 사람이 "이건 빼도 되겠지" 하고 지운다. 

## 릴리스 전 확인 (R8 을 켠 안드로이드 빌드)
- [ ] 앱이 켜지고 7일 체험 안내가 뜬다        ← DB·글꼴 모듈이 살아 있나
- [ ] 크레파스로 그으면 결이 보인다             ← Skia (네이티브 그리기)
- [ ] 일기 저장 → "참잘했어요" 도장              ← SQLite 저장
- [ ] 선생님 한마디가 달린다                    ← 네트워크 (서버 호출)
- [ ] 결제 화면에 가격 3개가 뜬다               ← RevenueCat + Play 결제 라이브러리
- [ ] logcat 에 FATAL / ClassNotFound 가 없다  ← R8 이 지운 클래스

이 목록은 저장소의 docs/RELEASE_CHECKLIST.md 나 PR 템플릿에 둔다. 사람 머릿속이 아니라 저장소 안에 있어야 남는다.

2단계 — 가장 자주 하는 것부터 자동화

전부 자동화할 필요는 없다. 고르는 기준은 셋이다.

  1. 자주 하는 것 — 릴리스마다 하는 확인
  2. 깨지면 비싼 것 — 결제, 데이터 저장. 사용자 돈과 기록이 걸린다
  3. 사람이 잘 빠뜨리는 것 — 로그에 오류가 있는지 같은, 눈으로 안 보이는 것

다이어리라면 "켜기 → 저장 → 도장 확인"이 첫 E2E 후보다. Maestro 로 쓰면 대략 이런 모양이 된다(예시다. 다이어리에 아직 넣지 않았다). 

# .maestro/save-diary.yaml
appId: com.looth.schooldiary
---
- launchApp
- tapOn: "시작하기"
- tapOn: "그림일기장"
- tapOn: "크레파스 꺼내기"
- swipe: { start: "30%,40%", end: "70%,55%" }
- tapOn: "저장"
- assertVisible: "선생님의 한마디"

헤드리스 브라우저도 검증이다

웹 게임에서는 이미 비슷한 걸 했다. 범퍼카 2026 에서 "판이 너무 길다"를 고칠 때, 게임에 window.__game.sim(초) 라는 손잡이를 남겨 두고 화면 없는 크롬에서 봇끼리 30판을 돌려 평균 경기 시간을 쟀다. 숫자를 바꿀 때마다 다시 쟀다. 이게 바로 "고쳤다"를 느낌이 아니라 숫자로 남기는 방식이다.

AI 와 일할 때 특히 중요한 이유

  • AI 는 "다 됐다"고 말한다. 정말 됐는지는 돌려 봐야 안다. 테스트가 있으면 AI 의 말 대신 결과를 본다.
  • AI 에게 테스트부터 쓰게 할 수 있다. "이 함수의 테스트를 먼저 쓰고, 통과하게 고쳐"라고 하면 고친 범위가 테스트로 남는다.
  • 큰 변경을 겁 없이 맡길 수 있다. 라이브러리 업그레이드, R8 같은 빌드 설정은 테스트가 있어야 "깨진 곳이 없다"를 말할 수 있다.
