커밋 습관
— 리뷰어가 읽을 수 있는 변경

직무 팀에서 일하기 Git .gitattributes .gitignore 2026.10.28

팀에서 일하기 시리즈 2번이다. 회사에 가면 가장 먼저 티가 나는 게 커밋이라고 생각한다. 코드 실력은 몇 주 같이 일해 봐야 보이지만, 커밋 이력은 첫 PR 에서 바로 보인다. 그리고 가장 빨리 고칠 수 있는 습관이기도 하다.

3,316줄이 바뀐 줄 알았는데 86줄이었다

학창시절 다이어리 저장소에서 git status 를 봤더니 커밋 안 된 변경이 14개 파일, 3,316줄이었다. 앱을 스토어에 올리면서 여기저기 고친 것들이 커밋 없이 쌓여 있었다. 그런데 공백·줄바꿈 차이를 빼고 다시 보니 진짜 변경은 86줄이었다. 

git diff --stat | tail -1
 14 files changed, 3316 insertions(+), 3263 deletions(-)

git diff -w --ignore-cr-at-eol --stat | tail -1
 7 files changed, 86 insertions(+), 33 deletions(-)

나머지는 줄바꿈 문자가 바뀐 것이었다. 윈도우는 줄 끝에 CRLF(두 글자)를, 맥·리눅스는 LF(한 글자)를 쓴다. 어떤 도구가 파일을 저장하면서 줄 끝을 바꾸면, 내용은 그대로인데 git 은 모든 줄을 지웠다 다시 쓴 것으로 본다. 팀에서 이게 PR 에 섞이면 리뷰어는 진짜 변경 86줄을 3,000줄 사이에서 찾아야 한다. 사실상 리뷰가 불가능하다.

변경 하나에 커밋 하나

"하나"의 기준은 되돌릴 때 같이 되돌려야 하는 것이다. R8 설정과 그 때문에 필요해진 메모리 설정은 한 커밋이다. R8 과 동의 문구는 서로 상관이 없으니 두 커밋이다. 줄바꿈·들여쓰기 같은 모양만 바꾸는 변경은 언제나 따로 커밋한다. 그래야 리뷰어가 "이 커밋은 모양만 바꿨다"를 믿고 넘어갈 수 있다. 

git add -p                 # 바뀐 덩어리마다 "이번 커밋에 넣을까?" 하나씩 묻는다
git add app.json plugins/  # 파일 단위로 골라 담기
git commit                 # 담은 것만 커밋된다

메시지에는 "무엇을"과 "왜"

코드를 보면 어떻게 바꿨는지는 나온다. 코드에 안 나오는 건 왜다. 메시지는 그걸 남기는 자리다. 

Android: 릴리스 빌드에서 R8 켜기 (1.0.1)

Play Console 경고 "DEX 코드 최적화 기준점 미만 — 난독화 3%"
(기한 2027년 2월). expo-build-properties 로 minify·shrinkResources 를 켰다.
R8 단계에서 Gradle Metaspace 가 모자라 빌드가 죽어서
plugins/withGradleMemory.js 로 4GB 로 올렸다.

확인: 로컬 릴리스 빌드를 에뮬레이터에서 그림판·저장·결제 화면까지 확인.
자리규칙
첫 줄50자 안팎. 무엇을 했나. 앞에 영역을 붙이면 목록에서 찾기 쉽다 (Android:, 서버:)
빈 줄꼭 둔다. 많은 도구가 첫 줄만 제목으로 쓴다

회사에 따라 feat:, fix:, chore: 를 앞에 붙이는 규칙(Conventional Commits)을 쓰기도 한다. 팀에 규칙이 있으면 그걸 따른다. 팀 규칙에 맞추기에서 더 적었다.

줄바꿈은 .gitattributes 로 고정한다

줄바꿈 문제는 조심해서 해결되지 않는다. 저장소에 규칙을 넣어 git 이 알아서 맞추게 해야 한다. 스쿠터 게임을 GitHub 에 처음 올리면서 넣은 파일이다. 

# .gitattributes
# 줄바꿈을 저장소 안에서는 LF 로 통일한다 (윈도우에서 받아도 diff 가 전부 바뀌지 않게)
* text=auto eol=lf
*.bat text eol=crlf

# 바이너리
*.png binary
*.jpg binary
*.glb binary
*.mp3 binary
  • * text=auto eol=lf — 글자 파일은 저장소에 LF 로 넣고, 꺼낼 때도 LF 로. 누가 어떤 OS 에서 저장해도 diff 에 줄바꿈 차이가 안 생긴다.
  • *.bat text eol=crlf — 윈도우 배치 파일은 CRLF 여야 제대로 돈다. 예외.
  • binary — 그림·모델·소리는 글자로 보고 비교하지 말라는 표시. 줄바꿈 변환도 안 한다.

이 파일을 넣은 첫 커밋에서 git 이 "CRLF will be replaced by LF" 경고를 파일마다 띄웠다. 그게 정상이다. 저장소 안의 줄바꿈이 한 번 정리되는 것이고, 그 뒤로는 다시 안 생긴다.

저장소에 넣지 않는 것

비밀 값

한 번 커밋된 비밀 값은 지워도 이력에 남는다. 공개 저장소라면 그 순간 유출된 것으로 보고 키를 바꿔야 한다. 다이어리 앱은 Play 서비스 계정 JSON 과 App Store API 키를 credentials/ 폴더에 두고, 그 폴더를 통째로 .gitignore 에 넣었다. 앱 설정 값은 .env 에 두고 역시 저장소에 넣지 않는다. 

# .gitignore
credentials/
.env

큰 파일

GitHub 는 파일 하나가 100MB 를 넘으면 push 를 거절한다. 스쿠터 게임 폴더에는 릴스 원본 영상이 123MB 였다. 영상은 코드가 아니고, 방송 영상이라 저장소에 둘 이유도 없어서 *.mp4 를 통째로 뺐다. 대신 README 에 "저장소에 없는 것"을 적어 둬서, 받은 사람이 없어진 줄 알고 찾지 않게 했다. 

# .gitignore
*.mp4
*.mov
__pycache__/

브랜치 이름

혼자 할 때는 main 하나에 바로 커밋했다. 팀에서는 일마다 브랜치를 따고, PR 로 main 에 합친다. 이름만 보고 무슨 일인지 알게 짓는다.

모양예
종류/짧은-설명fix/android-r8, feat/meal-photo, chore/gitattributes
이슈 번호를 붙이는 팀fix/123-teacher-timeout

실제로 브랜치를 따고 PR 을 만드는 과정은 브랜치와 PR 따라 하기에 따라 해 볼 수 있게 적었다.

CRLF / LF — 줄 끝을 나타내는 문자. CR(캐리지 리턴) + LF(줄 바꿈) 두 글자를 쓰는 게 윈도우, LF 한 글자가 맥·리눅스.
.gitattributes — 파일 종류마다 git 이 어떻게 다룰지(줄바꿈, 비교 방법) 정하는 파일. 저장소에 같이 들어가서 모든 팀원에게 똑같이 적용된다.
.gitignore — git 이 아예 보지 않을 파일·폴더 목록. 이미 커밋된 파일에는 효과가 없다.

이어서 읽기
