충돌 일부러 만들고 풀기
— merge conflict 실습

실습 Git merge conflict Pull Request 2026.10.28

팀에서 처음 Git 이 무서워지는 순간은 대개 충돌(conflict)이다. 화면에 CONFLICT 가 뜨고 파일 안에 <<<<<<< 가 박힌다. 그런데 충돌은 고장이 아니다. 두 사람이 같은 줄을 다르게 고쳐서, Git 이 어느 쪽이 맞는지 사람에게 묻는 것이다. 한 번 일부러 만들어서 풀어 보면 다음부터는 무섭지 않다.

Git 첫걸음의 git-practice 저장소에서 이어서 한다. 출력은 실제로 돌려서 나온 것이다.

언제 충돌이 나나

1. 충돌 만들기

① main 에 파일 하나를 만든다.

git switch main
printf '# 우리 팀 규칙\n\n점심은 12시에 먹는다.\n' > rules.md
git add rules.md
git commit -m "팀 규칙 추가"

② 브랜치 A 에서 그 줄을 고친다.

git switch -c feat/lunch-1230
# rules.md 의 "12시에" 를 "12시 30분에" 로 고치고
git commit -am "점심 12시 30분으로"

-a 는 "이미 추적 중인 파일의 변경을 add 까지 한 번에"다. 새 파일에는 안 먹는다.

③ main 으로 돌아가 브랜치 B 를 따고, 같은 줄을 다르게 고친다.

git switch main
git switch -c feat/lunch-1130
# 이번엔 "12시에" 를 "11시 30분에" 로
git commit -am "점심 11시 30분으로"

④ main 에 A 를 합친다. 문제없이 된다.

git switch main
git merge feat/lunch-1230
Updating 01f689e..a3b53bd
Fast-forward
 rules.md | 2 +-
 1 file changed, 1 insertion(+), 1 deletion(-)

⑤ 이어서 B 를 합친다. 여기서 부딪힌다.

git merge feat/lunch-1130
Auto-merging rules.md
CONFLICT (content): Merge conflict in rules.md
Automatic merge failed; fix conflicts and then commit the result.

2. 지금 무슨 상태인가 — status 와 충돌 표시

git status
On branch main
You have unmerged paths.
  (fix conflicts and run "git commit")
  (use "git merge --abort" to abort the merge)

Unmerged paths:
  (use "git add <file>..." to mark resolution)
	both modified:   rules.md

both modified — 양쪽이 다 고친 파일이다. Git 은 merge 를 반쯤 한 상태로 멈춰 있고, 할 수 있는 건 두 가지라고 알려 준다. 풀고 commit 하거나, --abort 로 없던 일로 하거나. 파일을 열어 보면: 

# 우리 팀 규칙

<<<<<<< HEAD
점심은 12시 30분에 먹는다.
=======
점심은 11시 30분에 먹는다.
>>>>>>> feat/lunch-1130
표시뜻
<<<<<<< HEAD여기부터 지금 내가 있는 쪽(main, 즉 A 가 합쳐진 상태)
=======경계선
>>>>>>> feat/lunch-1130여기까지 들어오려는 쪽(B)

HEAD — "지금 내가 서 있는 커밋"을 가리키는 이름. 보통은 지금 브랜치의 맨 끝이다.
current / incoming — VS Code 같은 편집기는 HEAD 쪽을 Current change, 들어오는 쪽을 Incoming change 라고 부르고, 그 위에 Accept Current · Accept Incoming · Accept Both 버튼을 띄운다.

3. 겁나면 일단 취소 — merge --abort

git merge --abort
git status --short       # 아무것도 안 나온다
cat rules.md
# 우리 팀 규칙

점심은 12시 30분에 먹는다.

merge 하기 직전으로 정확히 돌아간다. 급하게 다른 일을 해야 하거나, 누구 변경이 맞는지 물어봐야 할 때 쓴다. 충돌 중에 아무 파일이나 지우거나 새로 받는 것보다 훨씬 안전하다.

4. 풀기 — 고르고, 표시 지우고, add, commit

다시 merge 해서 충돌 상태로 만든 뒤 푼다.

git merge feat/lunch-1130     # 다시 충돌

① 파일을 원하는 최종 모습으로 고친다. 한쪽을 고를 수도, 둘을 섞을 수도 있다. 여기서는 섞었다.

# 우리 팀 규칙

점심은 12시에 먹는다. (11시 30분·12시 30분 두 조로 나눈다)

<<<<<<<, =======, >>>>>>> 세 줄은 반드시 지운다. 남은 채로 커밋하면 그 문자가 그대로 코드에 들어가 빌드가 깨진다. 실제로 자주 나는 사고다. 확인은 git diff --check 나 grep -n '<<<<<<<' -r . 로 한다.

② add 로 "다 풀었다"고 알린다.

git add rules.md
git status --short
M  rules.md

③ commit 한다. merge 커밋 메시지는 Git 이 미리 채워 둔다.

git commit --no-edit
[main f47d5b3] Merge branch 'feat/lunch-1130'
git log --oneline --graph -5
*   f47d5b3 Merge branch 'feat/lunch-1130'
|\
| * b3724b1 점심 11시 30분으로
* | a3b53bd 점심 12시 30분으로
|/
* 01f689e 팀 규칙 추가

두 갈래가 다시 하나로 모인 모양이 그대로 보인다. 풀고 나서 꼭 실행해 본다. 문법상 충돌은 풀렸어도, 양쪽 코드를 섞은 결과가 실제로 도는지는 Git 이 모른다.

5. 회사에서 더 흔한 경우 — PR 이 conflicts 로 막혔을 때

실무에서는 main 에 직접 merge 하는 일이 드물다. 대신 내 PR 아래에 이런 문구가 뜬다. "This branch has conflicts that must be resolved". 내가 브랜치에서 일하는 동안 누군가 같은 줄을 고쳐서 main 에 먼저 합친 것이다.

방법 A. GitHub 웹에서 (간단한 충돌)

  1. PR 아래 Resolve conflicts 버튼을 누른다
  2. 웹 편집기에 위와 같은 표시가 나온다. 고치고 표시 세 줄을 지운다
  3. 오른쪽 위 Mark as resolved → Commit merge

충돌이 복잡하거나 파일이 많으면 이 버튼이 안 뜨고 "명령줄에서 풀라"는 안내만 나온다. 그럴 땐 B.

방법 B. 내 컴퓨터에서 (권장)

main 의 최신 내용을 내 브랜치로 가져와 거기서 푼다. 예로 든 feat/lunch-1300 은 "팀 규칙 추가" 시점에서 따서 "12시"를 "1시"로 고친 브랜치다. 그사이 main 에는 위 4번에서 푼 결과가 올라가 있다. 

git switch feat/lunch-1300
git fetch                 # GitHub 의 최신 상태를 받아만 둔다
git merge origin/main     # 최신 main 을 내 브랜치에 합친다
Auto-merging rules.md
CONFLICT (content): Merge conflict in rules.md
Automatic merge failed; fix conflicts and then commit the result.
<<<<<<< HEAD
점심은 1시에 먹는다.
=======
점심은 12시에 먹는다. (11시 30분·12시 30분 두 조로 나눈다)
>>>>>>> origin/main

이번엔 HEAD 가 내 브랜치, 들어오는 쪽이 main 이다. 앞의 실습과 위아래가 바뀌었다. "HEAD = 지금 내가 서 있는 곳"으로 기억하면 헷갈리지 않는다. 풀고, git add, git commit, 그리고 git push 하면 PR 의 충돌 표시가 사라진다.

팀에 따라 merge 대신 git rebase origin/main 으로 따라가기도 한다. 그 차이는 최신 main 따라가기에서 다룬다.

충돌을 줄이는 습관

  • 브랜치를 오래 끌지 않는다. 며칠씩 혼자 들고 있을수록 main 과 멀어진다. 작게 나눠 자주 합친다.
  • 하루 한 번은 main 을 따라간다. git fetch + git merge origin/main(또는 rebase). 작은 충돌을 자주 푸는 게 큰 충돌 한 번보다 쉽다.
  • 상관없는 변경을 섞지 않는다. 기능 고치면서 파일 전체 들여쓰기·줄바꿈을 바꾸면, 그 파일을 만진 모든 사람과 충돌한다. 포매터 일괄 적용은 따로 PR 로.
  • 같은 파일을 크게 고칠 거면 미리 말한다. "오늘 settings 화면 구조 바꿔요" 한 마디가 충돌 해결 한 시간을 아낀다.

셋째가 내 다이어리 앱 저장소에서 실제로 본 일이다. 커밋 안 한 변경이 3,316 줄로 보였는데, 진짜로 바뀐 건 86 줄이었다. 나머지는 윈도우 줄바꿈(CRLF) 차이였다. 혼자라 넘어갔지만, 팀이었다면 그 파일을 만진 모든 사람과 충돌했을 것이다. 저장소에 .gitattributes 로 줄바꿈 규칙을 박아 두는 이유다.

이어서 볼 것

  • 브랜치와 Pull Request — 충돌이 나기 전까지의 흐름
  • 최신 main 따라가기 — merge 와 rebase 의 차이
  • 되돌리기 — 잘못 푼 merge 를 되돌리려면
  • 팀에서 Git 쓰는 습관 — 줄바꿈, 커밋 단위
