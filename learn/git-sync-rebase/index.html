PRACTICE

최신 main 따라가기
— fetch, pull, rebase

실습 Git fetch pull rebase force-with-lease 2026.10.28

혼자 할 때는 main 이 내 손으로만 바뀐다. 팀에서는 내가 로그인 화면을 만드는 사흘 동안 동료들이 main 에 커밋을 열 개쯤 쌓는다. 내 브랜치는 사흘 전 main 에서 갈라져 나왔으니, PR 을 올리기 전에 최신 main 위로 옮겨야 충돌을 내가 먼저 보고 고칠 수 있다.

이 글은 GitHub 없이 내 컴퓨터 안에서 따라 한다. 폴더 하나를 "원격 저장소"로 쓰고, 클론을 두 개 만들어 하나는 나, 하나는 동료 역할을 시킨다. 아래 출력은 Git 2.47 에서 실제로 돌린 것을 줄였다. 해시는 사람마다 다르다.

준비 — 원격 하나, 사람 둘

mkdir sync-practice && cd sync-practice
git init --bare -b main origin.git          # GitHub 역할 (작업 폴더 없는 저장소)

git clone origin.git me                      # 나
cd me
git config user.name "나" && git config user.email me@example.com
echo "# 앱" > README.md
git add . && git commit -m "처음" && git push origin main
cd ..

git clone origin.git mate                    # 동료
cd mate
git config user.name "동료" && git config user.email mate@example.com
cd ..

이제 나는 기능 브랜치에서 일하고, 그동안 동료가 main 에 커밋을 올린다.

# 나: 로그인 기능 브랜치
cd me
git switch -c feature/login
echo "로그인" > login.js && git add . && git commit -m "로그인 화면"
echo "검사" >> login.js && git commit -am "입력 검사"
cd ..

# 동료: main 에 두 커밋을 올림
cd mate
echo "헤더" > header.js && git add . && git commit -m "헤더 고침"
echo "푸터" > footer.js && git add . && git commit -m "푸터 추가"
git push origin main
cd ../me

1. fetch — 받아만 오고, 아무것도 안 바꾼다

git fetch origin
   2c4c9f1..2a8432b  main       -> origin/main

git log --oneline --graph --all
* faa986e 입력 검사
* 3037e1b 로그인 화면
| * 2a8432b 푸터 추가
| * 957d913 헤더 고침
|/
* 2c4c9f1 처음

fetch 는 원격의 새 커밋을 받아 origin/main 이라는 "원격 main 의 사본" 이름표만 옮긴다. 내 main 도, 내 작업 폴더도 그대로다. 그래서 언제 쳐도 안전하다. 그래프를 보면 내 두 커밋과 동료의 두 커밋이 "처음"에서 갈라져 있다. 

git switch main
git status -sb
## main...origin/main [behind 2]

behind 2 — 내 main 이 원격보다 커밋 두 개 뒤처졌다는 뜻이다.

2. pull — fetch 하고 합치기까지

git pull 은 fetch + 합치기다. 합치는 방법이 둘이다. 기본은 merge(합치는 커밋을 하나 새로 만듦), --rebase 를 붙이면 내 커밋을 원격 커밋 뒤로 옮겨 붙인다. 

git pull --rebase origin main
Updating 2c4c9f1..2a8432b
Fast-forward
 footer.js | 1 +
 header.js | 1 +

지금 내 main 에는 내 커밋이 없어서 그냥 앞으로 당겨졌다(Fast-forward). 내 main 에도 내 커밋이 있었다면 어떻게 되는지 보자. 동료가 a.txt 를, 내가 b.txt 를 각자 main 에 커밋한 상황이다. (아래는 실습을 다 마친 뒤 따로 해 본 결과다. 지금 따라 치면 뒤쪽 출력과 해시가 달라지니 읽기만 하고 넘어간다.) 

(동료) git commit … "동료: a" && git push origin main
(나)   git commit … "나: b"

git pull --rebase origin main
Successfully rebased and updated refs/heads/main.
git log --oneline
5a86219 나: b
1a9acf1 동료: a
2a8432b 푸터 추가

내 커밋이 동료 커밋 뒤로 옮겨져 한 줄로 이어졌다. 그냥 pull(merge)이었다면 "Merge branch 'main' of …" 커밋이 하나 끼어들고 그래프가 갈라졌다 합쳐진다. 그런 커밋이 매일 쌓이면 기록 읽기가 힘들어서, 많은 팀이 pull 은 늘 rebase 로 하게 설정해 둔다. 

git config --global pull.rebase true

3. rebase — 내 브랜치를 최신 main 위로

이제 기능 브랜치를 최신 main 위로 옮긴다.

git switch feature/login
git rebase main
Successfully rebased and updated refs/heads/feature/login.

git log --oneline --graph
* 53dfdfd 입력 검사
* 2dac65e 로그인 화면
* 2a8432b 푸터 추가
* 957d913 헤더 고침
* 2c4c9f1 처음

옮기는 도중 동료와 같은 줄을 고친 커밋이 있으면 rebase 가 멈추고 충돌을 알린다. 파일을 고친 뒤 git add 파일 → git rebase --continue 로 이어 가고, 엉망이 됐다 싶으면 git rebase --abort 로 시작 전 상태로 돌아간다. 충돌 고치는 법은 충돌 해결 글에 따로 적었다.

4. 커밋 정리 — rebase -i 로 합치기

PR 을 올리기 전, "오타 고침" 같은 자잘한 커밋을 앞 커밋에 합치고 싶을 때가 있다. 브랜치를 한 번 push 해 둔 상태에서 커밋을 하나 더 만든다. 

git push -u origin feature/login
echo "오타" >> login.js && git commit -am "오타 고침"

git rebase -i main

편집기가 열리고 이런 목록이 보인다. main 이후의 내 커밋이 위에서부터 오래된 순서다.

pick 2dac65e 로그인 화면
pick 53dfdfd 입력 검사
pick bc31470 오타 고침

# Rebase 2a8432b..bc31470 onto 2a8432b (3 commands)
#
# Commands:
# p, pick <commit> = use commit
# r, reword <commit> = use commit, but edit the commit message
# s, squash <commit> = use commit, but meld into previous commit
# f, fixup [-C | -c] <commit> = like "squash" but keep only the previous
#                    commit's log message …
# d, drop <commit> = remove commit

둘째·셋째 줄의 pick 을 fixup(줄여서 f)으로 바꾸고 저장한 뒤 편집기를 닫는다.

pick 2dac65e 로그인 화면
fixup 53dfdfd 입력 검사
fixup bc31470 오타 고침
Successfully rebased and updated refs/heads/feature/login.
git log --oneline
ca22425 로그인 화면
2a8432b 푸터 추가
957d913 헤더 고침

세 커밋이 "로그인 화면" 하나가 됐다. squash 는 메시지까지 모아서 다시 쓰게 하고, fixup 은 앞 커밋 메시지만 남긴다. reword 는 메시지만, drop 은 커밋을 뺀다.

편집기가 낯설다면: 윈도우 Git Bash 의 기본 편집기는 Vim 일 수 있다. i 로 고치기 시작, Esc 후 :wq 로 저장하고 나간다. VS Code 를 쓰려면 git config --global core.editor "code --wait". 이 명령은 대화형이라 직접 터미널에서 친다. GitHub 의 "Squash and merge" 버튼을 쓰는 팀이라면 이 정리를 PR 을 합칠 때 GitHub 가 대신 해 준다.

5. 다시 push — 거절당하고, 안전하게 덮어쓰기

git push origin feature/login
 ! [rejected]        feature/login -> feature/login (non-fast-forward)
error: failed to push some refs to '…/origin.git'
hint: Updates were rejected because the tip of your current branch is behind
hint: its remote counterpart.

rebase 로 해시가 바뀌어서, 원격의 feature/login 과 내 것이 다른 기록이 됐다. Git 은 원격 커밋을 잃지 않으려고 거절한다. 여기서 hint 대로 git pull 을 하면 옛 커밋과 새 커밋이 뒤섞이니 하지 않는다. 내 브랜치이고 덮어쓰는 게 맞으니 강제로 push 한다. 다만 --force 대신 --force-with-lease 를 쓴다. 

git push --force-with-lease origin feature/login
 + 53dfdfd...ca22425 feature/login -> feature/login (forced update)

lease 가 막아 주는 것

--force-with-lease 는 "내가 마지막으로 본 원격 상태 그대로일 때만 덮어써라"는 조건부 강제 push 다. 그 사이 동료가 같은 브랜치에 커밋을 올렸다면 거절한다. 직접 확인해 보자. 

(동료) git fetch && git switch feature/login
(동료) echo "동료 수정" >> login.js && git commit -am "동료: 문구 수정" && git push

(나)   git commit --amend -m "로그인 화면 (입력 검사 포함)"
(나)   git push --force-with-lease origin feature/login
 ! [rejected]        feature/login -> feature/login (stale info)
error: failed to push some refs to '…/origin.git'

stale info — 내가 아는 원격 정보가 낡았다는 뜻이다. 그냥 --force 였다면 동료의 "문구 수정" 커밋이 소리 없이 사라졌다. 이럴 땐 git fetch 로 동료 커밋을 받아 내 브랜치에 합친 뒤 다시 push 한다.

황금 규칙 — 남과 같이 쓰는 커밋은 rebase 하지 않는다

rebase 는 커밋을 새로 만든다. 그래서 main 처럼 여러 사람이 받아 간 브랜치를 rebase 하고 강제 push 하면, 동료들의 기록이 원격과 통째로 어긋나고 각자 엉킨 기록을 풀어야 한다.

브랜치rebase · 강제 push
나 혼자 쓰는 기능 브랜치해도 된다. push 는 --force-with-lease
동료와 같이 커밋하는 브랜치미리 말하고 한다. 아니면 merge 로
main · develop 같은 공용 브랜치하지 않는다. 대부분 저장소 설정으로 아예 막혀 있다

정리 — 아침마다 치는 순서

git switch main
git pull                       # pull.rebase=true 라면 rebase 로 받아 온다
git switch feature/login
git rebase main                # 충돌 나면 고치고 git rebase --continue
git push --force-with-lease    # 이미 push 해 둔 브랜치라면
명령하는 일내 파일이 바뀌나
git fetch원격 커밋을 받아 origin/… 만 옮김안 바뀐다
git pullfetch + merge바뀐다 (합치기 커밋이 생길 수 있음)
git pull --rebasefetch + 내 커밋을 원격 뒤로바뀐다 (기록이 한 줄)
git rebase main내 브랜치를 main 끝으로 옮김바뀐다 (내 커밋 해시가 새로)
git rebase -i커밋 합치기·고치기·빼기바뀐다
push --force-with-lease원격이 내가 본 그대로일 때만 덮어씀원격이 바뀐다

origin/main — 마지막으로 fetch 했을 때 원격 main 이 어디 있었는지 적어 둔 이름표. 실시간이 아니라 fetch 할 때만 움직인다.
fast-forward — 내 쪽에 새 커밋이 없어서, 합칠 것 없이 이름표만 앞으로 당기면 되는 경우.
bare 저장소 — 작업 폴더 없이 기록만 있는 저장소. GitHub 의 저장소가 이런 모양이라 실습에서 원격 대신 썼다.
