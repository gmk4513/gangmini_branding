실습 Git 리팩터링 브랜치 전략 FastAPI DI 2026.10.28

취업 준비 공부 메모에 이렇게 적어 뒀었다. "main(운영), dev(개발). 브랜치 따서 DI 구조로 정리 → 공부해 보기." 이 글은 그 메모를 그대로 실행한 기록이다. 78줄짜리 한 파일 메모 API 에서 시작해, 계층과 DI 구조로 바꾸고, 그 과정을 회사에서 하듯 브랜치 → 작은 커밋 → PR → 출시 순서로 밟는다.

명령과 출력은 내 컴퓨터에서 실제로 돌린 것이다. GitHub 대신 같은 컴퓨터 안의 빈 저장소(remote.git)를 원격으로 썼다. 명령은 GitHub 일 때와 똑같다.

전체 그림

리팩터링 — 바깥에서 보이는 동작은 그대로 두고 안쪽 구조만 바꾸는 것. 기능 추가가 아니다. 그래서 "동작이 그대로인가"를 매 단계 확인할 방법이 먼저 필요하다.

0. 출발점 — 한 파일짜리 API

app.py 하나에 전역 DB 연결, 라우트, SQL, 규칙, 로그 형식이 다 들어 있다. 잘 돌아가지만 이런 문제가 있다. 

# app.py (78줄 중 일부)
db = sqlite3.connect("memo.db", check_same_thread=False)  # ① 전역 연결 — 바꿔 끼울 수 없다

@app.post("/memos", status_code=201)
def create_memo(m: MemoIn, x_user: str = Header()):
    if not m.title.strip():                                 # ② 규칙이 라우트 안에
        raise HTTPException(400, "제목이 비었습니다")
    ...
    cur = db.execute("INSERT INTO memo ...", ...)           # ③ SQL 이 라우트 안에
    print(json.dumps({"level": "INFO", "msg": "메모를 만들었다", ...}))   # ④ 로그 형식이 비즈니스 코드 안에

@app.patch("/memos/{memo_id}")
def rename_memo(...):
    ...
    if not m.title.strip():                                 # ② 같은 규칙을 또 쓴다
        raise HTTPException(400, "제목이 비었습니다")

@app.get("/me")
def me(x_user: str = Header()):
    count = db.execute("SELECT COUNT(*) FROM memo WHERE owner = ?", ...)  # ⑤ 다른 기능이 memo 테이블을 직접

먼저, 동작이 그대로인지 확인하는 장치

구조를 바꾸다 보면 어딘가 깨진다. 그래서 바꾸기 전에 바깥에서 본 동작을 확인하는 짧은 스크립트(smoke.py)부터 만들었다. API 를 실제로 불러 상태 코드와 결과를 본다. 구조가 바뀌어도 API 는 같아야 하니, 이 스크립트는 처음부터 끝까지 그대로 쓴다. 

# smoke.py (요약)

smoke 테스트 — "전원을 켰을 때 연기가 안 나는지"만 보는 가장 기본적인 확인. 꼼꼼하진 않지만 크게 깨진 건 바로 잡는다. 꼼꼼한 테스트는 마지막 커밋에서 따로 쓴다.

2. 작업 브랜치 따기

작업은 늘 dev 에서 딴다. main 에서 따면 아직 출시 안 된 dev 의 변경과 엇갈린다.

$ git switch dev

Already on 'dev'
$ git switch -c refactor/layered-di

브랜치 이름 앞의 refactor/ 는 "기능 추가가 아니라 구조 정리"라는 표시다. 팀마다 feat/, fix/, refactor/ 같은 접두어를 정해 쓴다.

3. 다섯 번에 나눠 바꾸기

한 번에 전부 바꾸면 smoke 가 깨졌을 때 어디서 깨졌는지 모른다. 리뷰어도 수백 줄짜리 변경을 한 번에 읽어야 한다. 그래서 한 커밋에 한 가지 이유로 나눴다. 각 커밋 뒤에 smoke 를 돌려 통과할 때만 커밋했다.

커밋바꾼 것해결한 문제
① 저장소SQL 을 src/memo/repository.py 로③ SQL 이 라우트 안에
② 도메인·서비스규칙은 Memo, 흐름은 MemoService② 같은 규칙 중복, ⑤ 다른 기능의 테이블 직접 접근
③ 라우터·DTOHTTP 를 webapp/ 으로, 요청·응답 모양 분리표현 계층 분리
④ 컨테이너조립을 container.py 로, 로그 형식은 webapp 으로① 전역 연결, ④ 로그 형식
⑤ 테스트서비스·API 테스트, 가짜 저장소바뀐 구조가 주는 이득 확인

① 저장소 분리 — SQL 을 한 곳으로

가장 안전한 첫걸음이다. 라우트 안의 SQL 을 SqliteMemoRepository 메서드로 옮기고, 라우트는 그 메서드를 부르게만 바꾼다. 이 단계에서는 아직 dict 를 돌려준다. 한 번에 하나만 바꾼다. 

# 바뀌기 전
row = db.execute("SELECT id, owner, title, body, created_at FROM memo WHERE id = ?", (memo_id,)).fetchone()
# 바뀐 뒤
m = repo.find_memo(memo_id)

② 도메인과 서비스 — 규칙과 흐름 나누기

"제목은 비면 안 된다", "내 메모만"을 Memo 도메인으로 옮겨 한 번만 쓰게 하고, 일의 순서는 MemoService 로 옮겼다. 예외도 HTTPException 대신 HTTP 를 모르는 NotFound·PermissionDenied·InvalidInput 으로 바꿨다. 저장소는 이제 dict 대신 Memo 를 돌려준다(엔티티 MemoRow 가 변환). /me 는 memo 테이블을 직접 세지 않고 service.count_memos 를 부른다.

③ 라우터와 DTO — HTTP 는 webapp 으로

app.py 를 지우고 webapp/routers/memo.py(라우트 + DTO)와 webapp/main.py(앱 조립)로 옮겼다. 응답은 MemoResponse 로만 나가서 owner 가 빠진다. 도메인 예외를 404·403·400 으로 바꾸는 일도 여기서 한 번에 한다. 조립은 아직 손으로 한다. 

# webapp/main.py (③ 시점)
def create_app(db_path: str = "memo.db") -> FastAPI:
    conn = sqlite3.connect(db_path, check_same_thread=False)
    app = FastAPI(title="memo-api")
    app.state.memo_service = MemoService(SqliteMemoRepository(conn))   # 손으로 조립
    ...

GitHub 이라면 여기서 PR 을 연다. 중요한 건 받는 쪽(base)을 main 이 아니라 dev 로 고르는 것이다. 웹에서는 "base: dev ← compare: refactor/layered-di", 명령으로는 이렇다. 

gh pr create --base dev --title "refactor: 계층 + DI 구조로 정리" --body "동작은 그대로(smoke 통과), 구조만 바꿈. 커밋 5개로 나눠 두었으니 하나씩 보면 됩니다."

PR 설명에는 "무엇을, 왜, 어떻게 확인했나"를 적는다. 리팩터링 PR 은 특히 "동작은 그대로"라는 근거(smoke·테스트 결과)가 리뷰어를 안심시킨다. PR 작성법은 브랜치와 Pull Request에 따로 있다.

리뷰가 끝나면 PR 화면의 Merge 버튼을 누른다. 로컬에서는 같은 일을 이렇게 흉내 냈다.

$ git switch dev
$ git merge --no-ff refactor/layered-di -m "Merge pull request #1 from refactor/layered-di"
$ git push origin dev
   0d8353f..7e9ca67  dev -> dev

5. 출시 — dev 를 main 으로

dev 에 모인 변경을 확인한 뒤(실무라면 dev 서버에서 한 번 더 돌려 본다) main 에 합치고 새 버전 태그를 붙인다. 태그는 "운영에 나간 정확한 상태"에 붙이는 이름표라, 문제가 생기면 v0.1.0 으로 바로 되돌릴 수 있다.

해 보고 남은 것

한 것이유
바꾸기 전에 smoke 부터리팩터링은 "동작 그대로"가 약속이다. 확인 장치 없이 시작하면 약속을 지켰는지 모른다
dev 에서 브랜치main 은 운영 그대로 둔다. 실험은 브랜치에서
한 커밋에 이유 하나깨지면 어느 커밋인지 바로 안다. 리뷰어가 하나씩 읽을 수 있다
커밋마다 smoke중간 상태도 늘 돌아가게. 어느 커밋으로 돌아가도 쓸 수 있다
PR 은 dev 로, 출시는 main 으로 + 태그출시 단위가 분명해지고, 되돌릴 자리가 생긴다

처음 메모에는 "DI 구조로 정리"가 한 줄이었다. 막상 해 보니 구조를 바꾸는 코드보다 바꾸는 순서가 더 중요했다. SQL 을 먼저 모으고, 규칙을 옮기고, HTTP 를 떼고, 마지막에 조립을 모은다. 각 단계가 작아서 무섭지 않았고, 어느 단계에서 멈춰도 코드는 돌아가는 상태였다.

이어서 읽기

  • main · dev 브랜치 전략 — 왜 두 줄기로 나누나
  • 레이어드 아키텍처 따라 만들기 — 바꾼 뒤의 구조 설명
  • 의존성 주입(DI) — 컨테이너와 수명, override
  • 코드 구조와 설계 — 전체 지도
  • 테스트와 CI/CD — 이 smoke 와 테스트를 PR 마다 자동으로
  • 브랜치와 Pull Request
  • 검증을 남기는 능력
