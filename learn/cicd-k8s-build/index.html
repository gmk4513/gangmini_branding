PRACTICE · CI/CD 11/13

쿠버네티스 안에서 이미지 빌드
— 젠킨스 에이전트 파드와 Kaniko

실습 Jenkins Helm Kubernetes plugin Kaniko Docker Hub 2026.11.10

9편에서는 젠킨스 컨테이너가 호스트의 도커 소켓을 빌려(DooD) docker build 를 했다. 회사가 쿠버네티스로 옮겨 가면 젠킨스도 쿠버네티스 안에 들어간다. 그런데 거기서는 이 방법이 막힌다. 요즘 쿠버네티스 노드에는 도커 데몬이 없기 때문이다(컨테이너는 containerd 가 돌린다). 빌려 쓸 소켓 자체가 없다.

그래서 쿠버네티스에서는 두 가지를 바꾼다. 빌드를 젠킨스 컨트롤러가 아니라 빌드마다 새로 뜨는 에이전트 파드에서 하고, 이미지는 도커 데몬 없이 이미지를 만드는 도구 Kaniko 로 만든다.

이번 단계에서 할 것

  1. 헬름으로 젠킨스를 10편의 kind 클러스터에 설치하기
  2. Docker Hub 로그인 정보를 쿠버네티스 Secret 으로 넣기
  3. Jenkinsfile.k8s — 에이전트 파드에서 pytest → Kaniko 로 빌드·푸시
  4. 빌드하는 동안 파드가 생겼다 사라지는 걸 직접 보기

끝나면: 젠킨스 잡 cicd-hello-k8s 가 초록이고, Docker Hub 에 <빌드번호>-<커밋> 태그가 새로 생겨 있다.

어떻게 도나

에이전트(agent) — 젠킨스에서 실제로 빌드를 실행하는 쪽. 4편에서는 컨트롤러가 직접 했고(실무에선 권하지 않는다), 여기서는 쿠버네티스 파드가 에이전트가 된다.
Kubernetes plugin — 젠킨스가 빌드할 때마다 쿠버네티스에 파드를 만들어 달라고 해서 에이전트로 쓰고, 끝나면 지우게 해 주는 플러그인.
jnlp 컨테이너 — 에이전트 파드에 항상 들어가는 컨테이너. 젠킨스 컨트롤러와 연결을 맺고, 코드(git)를 받는다. 이름은 옛 연결 방식(Java Network Launch Protocol)에서 왔다.
containerd — 컨테이너를 실제로 돌리는 프로그램(컨테이너 런타임). 쿠버네티스 1.24 부터 도커 대신 이것을 직접 쓰는 게 표준이 됐다. 도커 엔진도 속에서는 containerd 를 쓴다.

왜 Kaniko 인가 — 쿠버네티스에서 이미지 만드는 방법 비교

방법쿠버네티스에서문제
DooD (소켓 빌려 쓰기)노드에 도커 데몬이 없어서 안 된다있다 해도 노드 전체 권한을 빌드에 넘기는 셈
DinD (도커 안에 도커)privileged 파드로 가능privileged 는 노드를 탈취할 수 있는 권한. 공용 클러스터에선 대개 금지
Kaniko평범한 컨테이너 하나로 된다데몬 없이 Dockerfile 을 한 줄씩 직접 실행해 레이어를 만들고 바로 레지스트리에 올린다
BuildKit(rootless), Buildah된다Kaniko 의 대안. 설정이 조금 더 든다

알아 둘 것: Kaniko 의 원래 저장소(구글의 GoogleContainerTools/kaniko)는 2025년에 보관(archive) 처리되어 더 이상 새 기능이 나오지 않는다. 공개 이미지는 지금도 받을 수 있어 실습에는 문제없고, 구조를 익히기에 가장 단순해서 여기서 쓴다. 실무에서 새로 고른다면 BuildKit·Buildah 나 다른 곳이 이어 관리하는 Kaniko 포크도 같이 검토한다.

privileged — 컨테이너에 호스트 장치와 커널 기능을 거의 다 열어 주는 옵션. 컨테이너 격리를 사실상 없앤다.
레이어(layer) — 이미지를 이루는 층. Dockerfile 의 명령 한 줄(RUN, COPY)이 대략 층 하나가 된다. Kaniko 는 한 줄 실행할 때마다 바뀐 파일을 찍어(스냅샷) 층으로 만든다.

1. 준비 확인

kubectl config current-context      # kind-cicd 여야 한다
kubectl get nodes                   # Ready
helm version --short                # 2편에서 설치

젠킨스 컨트롤러는 메모리를 1~2GB 쓴다. 10편 끝에서 말한 대로 9편의 도커 젠킨스는 꺼 두는 게 좋다.

헬름(Helm) — 쿠버네티스용 패키지 관리자. 우분투의 apt 처럼 helm install 한 줄로 젠킨스에 필요한 YAML 수십 개(StatefulSet, Service, 권한, 설정)를 한꺼번에 깐다. 이 YAML 묶음을 차트(chart), 설치된 하나를 릴리스(release), 설정을 바꾸는 파일을 values 파일이라고 한다.

2. 헬름으로 젠킨스 설치

mkdir -p ~/cicd/k8s-jenkins && cd ~/cicd/k8s-jenkins

설정 파일 jenkins-values.yaml 을 만든다. 차트의 기본값은 대부분 그대로 두고 필요한 것만 덮어쓴다.

# jenkins-values.yaml
controller:
  # port-forward 로 들어올 주소. 젠킨스가 링크를 만들 때 쓴다
  jenkinsUrl: http://localhost:8095
  # 차트가 기본으로 까는 플러그인(kubernetes, workflow-aggregator, git,
  # configuration-as-code)에 더해서 깔 것
  additionalPlugins:
    - junit
    - pipeline-stage-view
persistence:
  size: 8Gi
helm repo add jenkins https://charts.jenkins.io
helm repo update
kubectl create namespace jenkins
helm install jenkins jenkins/jenkins -n jenkins -f jenkins-values.yaml

플러그인을 받으며 뜨느라 2~5분 걸린다. 지켜본다.

kubectl -n jenkins get pods -w
NAME        READY   STATUS     RESTARTS   AGE
jenkins-0   0/2     Init:0/1   0          20s     ← 플러그인 설치 중
jenkins-0   0/2     PodInitializing   0   2m
jenkins-0   1/2     Running    0          2m20s
jenkins-0   2/2     Running    0          3m

2/2 는 젠킨스 본체와, 설정이 바뀌면 다시 읽게 해 주는 보조 컨테이너(config-reload) 두 개다. 관리자 비밀번호는 차트가 무작위로 만들어 Secret 에 넣어 두었다. 

kubectl -n jenkins get secret jenkins -o jsonpath="{.data.jenkins-admin-password}" | base64 -d; echo
kubectl -n jenkins port-forward svc/jenkins 8095:8080

이 터미널은 열어 둔다. 브라우저에서 http://localhost:8095, 아이디 admin, 비밀번호는 위에서 본 값. 4편과 달리 설치 마법사가 없다. 차트가 설정 코드(JCasC)로 미리 끝내 놓았기 때문이다.

StatefulSet — 이름과 저장 공간이 고정된 파드를 만드는 오브젝트. 젠킨스는 설정·빌드 기록을 디스크에 두므로 Deployment 대신 이걸 쓴다. 그래서 파드 이름이 무작위가 아니라 jenkins-0 이다.
PVC(PersistentVolumeClaim) — "디스크 8GB 주세요" 라는 요청. 파드가 다시 떠도 같은 디스크가 붙어서 젠킨스 설정이 남는다. kind 는 노드 안의 폴더를 디스크로 내준다.
Secret — 비밀번호·토큰을 담는 쿠버네티스 오브젝트. 값은 base64 로 적혀 있을 뿐 암호화된 게 아니다. 그래서 base64 -d 로 바로 풀린다. 권한 관리가 핵심이다.
JCasC(Jenkins Configuration as Code) — 젠킨스 설정을 화면 클릭 대신 YAML 로 적는 플러그인. 차트가 이걸로 관리자 계정과 쿠버네티스 연결을 미리 넣어 둔다.

3. 쿠버네티스 연결 확인

Manage Jenkins → Clouds 에 kubernetes 라는 항목이 이미 있다. 눌러 보면 쿠버네티스 주소와 네임스페이스 jenkins, 젠킨스 주소(http://jenkins.jenkins.svc.cluster.local:8080)가 차 있다. 에이전트 파드가 이 주소로 컨트롤러를 찾아온다. Test Connection 을 눌러 Connected to Kubernetes 가 나오면 된다.

이름.네임스페이스.svc.cluster.local — 클러스터 안에서 Service 를 부르는 주소(DNS 이름). 클러스터 안에서만 통한다. 같은 네임스페이스면 jenkins 처럼 이름만 써도 된다.
서비스 어카운트(ServiceAccount) — 파드가 쿠버네티스 API 를 부를 때 쓰는 신분증. 차트가 젠킨스에 "jenkins 네임스페이스에 파드를 만들고 지울 권한"만 준 계정을 만들어 붙였다.

4. Docker Hub 로그인 정보를 Secret 으로

Kaniko 는 docker login 을 하지 않는다. 대신 /kaniko/.docker/config.json 파일에서 로그인 정보를 읽는다. 그 파일을 쿠버네티스 Secret 으로 만들어 두고 Kaniko 컨테이너에 끼워 준다. 토큰은 2편에서 만든 Docker Hub Access Token(Read & Write)을 쓴다. 

kubectl -n jenkins create secret docker-registry dockerhub-cred \
  --docker-server=https://index.docker.io/v1/ \
  --docker-username=<도커허브아이디> \
  --docker-password=<도커허브 Access Token>
secret/dockerhub-cred created

명령에 토큰을 직접 치면 셸 기록(~/.bash_history)에 남는다. 연습이 끝나면 Docker Hub 에서 토큰을 지우거나, 명령 앞에 공백을 하나 넣어 기록에 안 남게 한다(우분투 bash 기본 설정에서 동작).

docker-registry 형 Secret — 레지스트리 로그인 정보를 도커의 config.json 모양 그대로 담는 Secret. 키 이름이 .dockerconfigjson 이다. 비공개 이미지를 받을 때(imagePullSecrets)도 같은 형식을 쓴다.

5. Jenkinsfile.k8s 쓰기

cicd-hello 저장소에 새 파일 Jenkinsfile.k8s 를 만든다. 6편·9편의 Jenkinsfile 은 그대로 둔다(젠킨스 잡마다 읽을 파일을 따로 지정한다). <도커허브아이디> 는 내 것으로 바꾼다. 

// Jenkinsfile.k8s — 쿠버네티스 에이전트 파드에서 테스트하고 Kaniko 로 빌드·푸시
pipeline {
  agent {
    kubernetes {
      // 이 빌드를 위해 띄울 파드. jnlp 컨테이너는 플러그인이 알아서 더한다
      yaml '''
apiVersion: v1
kind: Pod
spec:
  containers:
    - name: python
      image: python:3.12-slim
      command: ["sleep"]
      args: ["infinity"]
    - name: kaniko
      image: gcr.io/kaniko-project/executor:debug
      command: ["/busybox/cat"]
      tty: true
      volumeMounts:
        - name: docker-config
          mountPath: /kaniko/.docker
  volumes:
    - name: docker-config
      secret:
        secretName: dockerhub-cred
        items:
          - key: .dockerconfigjson
            path: config.json
'''
    }
  }

  environment {
    IMAGE = '<도커허브아이디>/cicd-hello'
  }

  options {
    timeout(time: 20, unit: 'MINUTES')
    buildDiscarder(logRotator(numToKeepStr: '20'))
  }

  triggers {
    pollSCM('H/2 * * * *')
  }

  stages {
    stage('Tag') {
      steps {
        script {
          def shortSha = sh(script: 'git rev-parse --short=7 HEAD', returnStdout: true).trim()
          env.IMAGE_TAG = "${env.BUILD_NUMBER}-${shortSha}"
        }
        echo "이번 이미지: ${env.IMAGE}:${env.IMAGE_TAG}"
      }
    }

    stage('Test') {
      steps {
        container('python') {
          sh '''
            python -m venv /tmp/venv
            . /tmp/venv/bin/activate
            pip install -q -r requirements-dev.txt
            python -m pytest -q --junitxml=test-results.xml
          '''
        }
      }
      post {
        always { junit 'test-results.xml' }
      }
    }

    stage('Build & Push') {
      steps {
        container(name: 'kaniko', shell: '/busybox/sh') {
          sh '''#!/busybox/sh
            /kaniko/executor \
              --context="$WORKSPACE" \
              --dockerfile="$WORKSPACE/Dockerfile" \
              --build-arg "APP_VERSION=$IMAGE_TAG" \
              --destination="$IMAGE:$IMAGE_TAG" \
              --skip-unused-stages
          '''
        }
      }
    }
  }

  post {
    success { echo "푸시 완료: ${env.IMAGE}:${env.IMAGE_TAG}" }
    failure { echo '실패한 단계의 로그를 위에서 확인하세요' }
  }
}
부분뜻
agent { kubernetes { yaml … } }"이 모양의 파드를 띄워서 거기서 빌드해라." 6편의 agent any 자리다
command: ["sleep"] / ["/busybox/cat"]컨테이너가 바로 끝나 버리지 않고 기다리게 하는 장치. 젠킨스가 그 안에 들어가 명령을 친다
executor:debugKaniko 이미지 중 셸(busybox)이 들어 있는 판. 젠킨스의 sh 를 쓰려면 셸이 있어야 한다
volumes: … dockerhub-cred4번의 Secret 을 /kaniko/.docker/config.json 파일로 끼워 넣는다
container('python') { … }이 블록의 명령은 python 컨테이너 안에서. 블록 밖의 sh(Tag 단계)는 jnlp 컨테이너에서 돈다
/tmp/venv가상환경을 작업 폴더 밖에 만든다. 작업 폴더에 만들면 Kaniko 빌드 재료에 섞인다
shell: '/busybox/sh', #!/busybox/shKaniko 이미지에는 /bin/sh 가 없다. 셸 위치를 알려 준다
--context, --dockerfile빌드 재료 폴더와 Dockerfile. docker build . 의 . 자리
--destination빌드가 끝나면 바로 이 이름으로 레지스트리에 올린다. 로컬에 이미지를 남기지 않는다
--skip-unused-stagesDockerfile 의 test 단계는 건너뛴다. 테스트는 이미 python 컨테이너에서 했으니까. 빼면 Kaniko 가 test 단계도 빌드한다(그것도 한 번 더 검사하는 셈이라 나쁘진 않다)
git add Jenkinsfile.k8s
git commit -m "쿠버네티스 에이전트 + Kaniko 빌드 파이프라인"
git push

6. 잡 만들고 돌리기

  1. New Item → 이름 cicd-hello-k8s → Pipeline → OK
  2. Pipeline 칸: Definition 을 Pipeline script from SCM, SCM Git, Repository URL https://github.com/<내아이디>/cicd-hello.git
  3. Branch Specifier */main, Script Path 를 Jenkinsfile.k8s 로 바꾼다 (이걸 안 바꾸면 6편의 Jenkinsfile 을 읽는다)
  4. Save → Build Now

빌드를 누르자마자 다른 터미널에서 파드를 지켜본다. 이게 이 글에서 가장 볼만한 장면이다.

pod "try-hello" deleted

7. 일부러 실패시켜 보기

app.py 의 인사말(9편을 따라 했다면 "Hello, Docker CI/CD!")을 "Hi" 로 바꿔 push 한다. 테스트는 그대로 둔다. 2분 안에(Poll SCM) 빌드가 돌고 Test 에서 빨갛게 멈춘다. Build & Push 는 실행되지 않으므로 Docker Hub 에 깨진 이미지가 올라가지 않는다. 테스트 결과 화면(Test Result)에서 어느 테스트가 왜 실패했는지 본다. 확인했으면 되돌려 push 한다.

더 해 볼 것 — 캐시

에이전트 파드는 매번 새것이라 pip 설치 같은 층을 매번 다시 만든다. Kaniko 에 --cache=true --cache-repo=<도커허브아이디>/cicd-hello-cache 를 더하면 만든 층을 레지스트리에 저장해 두고 다음 빌드에서 재사용한다. 두 번째 빌드 로그에 Using caching version of cmd 가 보이면 캐시가 먹은 것이다.
