PRACTICE · CI/CD 10/13

쿠버네티스 최소 기초
— kind 에 앱 손으로 배포하기

실습 Kubernetes kind kubectl Deployment 롤링 업데이트 2026.11.10

9편까지는 서버 한 대에서 docker run 으로 컨테이너를 띄웠다. 서버가 한 대면 이걸로 충분하다. 그런데 서버가 열 대가 되면 "이 컨테이너는 어느 서버에 띄우지?", "서버 하나가 죽으면 거기 있던 컨테이너는 누가 다시 띄우지?", "새 버전으로 바꾸는 동안 서비스가 끊기면?" 같은 질문이 생긴다. 이걸 대신 해 주는 것이 쿠버네티스(Kubernetes)다.

11~13편은 쿠버네티스 위에서 CI/CD 를 한다. 그 전에 이 글에서 쿠버네티스를 딱 필요한 만큼만 손으로 만져 본다. 여기서 손으로 하는 일(YAML 을 고쳐서 kubectl apply)을 13편에서는 ArgoCD 가 대신 하게 된다.

이번 단계에서 할 것

  1. kind 로 내 컴퓨터에 쿠버네티스 클러스터 하나 만들기
  2. cicd-hello 를 Deployment·Service YAML 로 배포하고 접속하기
  3. 파드를 지워 보고(자가 치유), 늘려 보고(스케일), 새 버전으로 바꿔 보고(롤링 업데이트), 되돌려 보기

끝나면: curl localhost:8200/health 가 쿠버네티스 안의 파드에서 답하고, kubectl rollout undo 로 이전 버전으로 돌아갈 수 있다.

쿠버네티스 한눈에

클러스터(cluster) — 쿠버네티스가 관리하는 컴퓨터(노드)들의 묶음. 실무에서는 서버 수십 대, 이 실습에서는 도커 컨테이너 한 개다.
노드(node) — 클러스터에 속한 컴퓨터 한 대. 컨테이너가 실제로 도는 곳.
컨트롤 플레인(control plane) — 클러스터의 두뇌. 명령을 받는 API 서버, 상태를 적어 두는 저장소 etcd, 파드를 어느 노드에 둘지 정하는 스케줄러, 원하는 상태와 현재 상태를 계속 비교하는 컨트롤러로 이뤄진다.
kubectl — 쿠버네티스에 명령하는 CLI. "큐브 컨트롤" 또는 "큐브 씨티엘"이라고 읽는다. 결국 API 서버에 HTTP 요청을 보내는 프로그램이다.
kind — Kubernetes IN Docker. 도커 컨테이너를 노드로 삼아 쿠버네티스를 내 컴퓨터에 몇십 초 만에 띄우는 도구. 연습·테스트용이다.

꼭 알아야 할 오브젝트 넷

이름한 줄 뜻비유
Pod (파드)컨테이너를 띄우는 가장 작은 단위. 보통 컨테이너 하나 = 파드 하나. IP 를 하나 받는다컨테이너를 담은 그릇
Deployment"이 이미지로 파드를 N 개 유지해라" 라는 주문서. 파드가 죽으면 새로 만들고, 이미지가 바뀌면 하나씩 갈아 끼운다현장 반장
Service파드 여러 개 앞에 서는 고정 주소. 파드는 죽고 살면서 IP 가 바뀌지만 Service 이름은 그대로다대표 전화번호
Namespace클러스터 안을 나누는 폴더. 이름이 같아도 네임스페이스가 다르면 다른 것층(floor)

ReplicaSet — Deployment 가 실제로 파드 개수를 맞추려고 만드는 중간 오브젝트. 직접 만질 일은 거의 없지만 kubectl get all 에 보이니 이름만 알아 둔다. 버전이 바뀔 때마다 새 ReplicaSet 이 생기고, 되돌리기는 이전 ReplicaSet 을 다시 키우는 것이다.
매니페스트(manifest) — 오브젝트를 적은 YAML 파일. "명세서"라는 뜻. 12·13편에서 이 파일들을 Git 저장소에 넣는다.

1. 준비 확인

2편에서 깐 도구가 있는지 우분투 터미널에서 확인한다. Docker Desktop 이 켜져 있어야 한다.

docker version --format '{{.Server.Version}}'
kind version
kubectl version --client

세 줄 모두 버전이 나오면 된다. 쿠버네티스는 메모리를 꽤 먹는다. 11편(젠킨스)과 12편(ArgoCD)까지 같은 클러스터에 올리므로 Docker Desktop 의 Settings → Resources(WSL2 백엔드면 .wslconfig 의 memory)에서 메모리를 6GB 이상 잡아 두는 게 좋다.

2. 클러스터 만들기

kind create cluster --name cicd
Creating cluster "cicd" ...
 ✓ Ensuring node image (kindest/node:v1.xx.x) 🖼
 ✓ Preparing nodes 📦
 ✓ Writing configuration 📜
 ✓ Starting control-plane 🕹️
 ✓ Installing CNI 🔌
 ✓ Installing StorageClass 💾
Set kubectl context to "kind-cicd"

처음엔 노드 이미지(수백 MB)를 받느라 1~3분 걸린다. 마지막 줄이 중요하다. kind 가 kubectl 의 대상(컨텍스트)을 방금 만든 클러스터로 바꿔 놓았다. 

kubectl get nodes
NAME                 STATUS   ROLES           AGE   VERSION
cicd-control-plane   Ready    control-plane   40s   v1.xx.x
docker ps --format '{{.Names}}'     # 노드의 정체는 도커 컨테이너다
cicd-control-plane

컨텍스트(context) — kubectl 이 "지금 어느 클러스터에, 누구로" 명령할지 적어 둔 설정. ~/.kube/config 파일에 들어 있다. 회사에서 클러스터가 여러 개면 kubectl config get-contexts 로 보고 kubectl config use-context 이름 으로 바꾼다. 엉뚱한 클러스터(운영!)에 명령하는 사고가 여기서 난다.

3. 띄울 이미지 정하기

파드는 이미지를 레지스트리에서 받아서 띄운다. 두 가지 중 하나를 고른다.

(가) 9편에서 Docker Hub 에 올린 이미지를 쓴다 — 권장

Docker Hub 의 내 저장소 <도커허브아이디>/cicd-hello → Tags 에서 태그 하나를 고른다(예: 12-a1b2c3d). Docker Hub 무료 저장소는 기본이 공개라 쿠버네티스가 로그인 없이 받을 수 있다.

(나) 9편을 건너뛰었다면 — 내 컴퓨터에서 만들어 kind 에 넣는다

cd ~/cicd/cicd-hello
docker build --build-arg APP_VERSION=local-1 -t cicd-hello:local-1 .
kind load docker-image cicd-hello:local-1 --name cicd

kind 노드는 내 컴퓨터의 도커 이미지 목록을 모른다. kind load 가 이미지를 노드 안으로 복사해 준다. 이 경우 아래 YAML 의 image: 를 cicd-hello:local-1 로 쓴다.

4. 매니페스트 쓰기

실습 폴더에 k8s 폴더를 만들고 파일 셋을 쓴다. 12편에서 이 폴더를 그대로 Git 저장소로 옮긴다.

mkdir -p ~/cicd/k8s-practice/k8s
cd ~/cicd/k8s-practice
# k8s/namespace.yaml
apiVersion: v1
kind: Namespace
metadata:
  name: cicd-hello
# k8s/deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: cicd-hello
  namespace: cicd-hello
spec:
  replicas: 2
  selector:
    matchLabels:
      app: cicd-hello
  template:
    metadata:
      labels:
        app: cicd-hello
    spec:
      containers:
        - name: app
          image: <도커허브아이디>/cicd-hello:12-a1b2c3d   # ← 3번에서 고른 것
          ports:
            - containerPort: 8000
          readinessProbe:
            httpGet:
              path: /health
              port: 8000
            initialDelaySeconds: 2
            periodSeconds: 5
          livenessProbe:
            httpGet:
              path: /health
              port: 8000
            initialDelaySeconds: 5
            periodSeconds: 10
          resources:
            requests:
              cpu: 50m
              memory: 64Mi
            limits:
              cpu: 250m
              memory: 128Mi
# k8s/service.yaml
apiVersion: v1
kind: Service
metadata:
  name: cicd-hello
  namespace: cicd-hello
spec:
  selector:
    app: cicd-hello
  ports:
    - port: 80
      targetPort: 8000
줄뜻
apiVersion, kind무슨 종류의 오브젝트인가. Deployment 는 apps/v1, Service·Namespace 는 v1
metadata.name이름. 같은 네임스페이스 안에서 겹치면 안 된다
replicas: 2파드를 항상 두 개 유지
selector / labels"app: cicd-hello 라벨이 붙은 파드가 내 것" 이라는 약속. Deployment 와 Service 가 파드를 찾는 방법이다. 셋이 같은 글자여야 한다
template파드를 찍어 낼 틀. 이미지가 여기 있다
readinessProbe"이 파드에 손님을 보내도 되나" 검사. /health 가 200 을 줘야 Service 가 요청을 보낸다
livenessProbe"살아 있나" 검사. 계속 실패하면 컨테이너를 재시작한다
resourcesrequests 는 자리 잡을 때 보장받는 양, limits 는 넘으면 안 되는 상한. 50m = CPU 0.05 개, 64Mi = 64MB 정도
port: 80 / targetPort: 8000Service 는 80 으로 받아서 파드의 8000 으로 넘긴다

라벨(label) — 오브젝트에 붙이는 이름표(키: 값). 쿠버네티스는 이름이 아니라 라벨로 서로를 찾는다.
프로브(probe) — 쿠버네티스가 주기적으로 컨테이너를 찔러 보는 검사. 그래서 앱에 /health 같은 주소를 만들어 둔다(3편에서 만든 이유가 여기 있다).

5. 배포하고 접속하기

kubectl apply -f k8s/
namespace/cicd-hello created
deployment.apps/cicd-hello created
service/cicd-hello created

폴더를 통째로 주면 안의 YAML 을 다 적용한다. 파드가 뜨는 걸 지켜본다(-w = 바뀔 때마다 새 줄, 멈추려면 Ctrl+C).

kubectl -n cicd-hello get pods -w
NAME                          READY   STATUS              RESTARTS   AGE
cicd-hello-6d9f7c8b5d-4xk2p   0/1     ContainerCreating   0          3s
cicd-hello-6d9f7c8b5d-9mjzt   0/1     ContainerCreating   0          3s
cicd-hello-6d9f7c8b5d-4xk2p   1/1     Running             0          12s
cicd-hello-6d9f7c8b5d-9mjzt   1/1     Running             0          13s

둘 다 1/1 Running 이면 된다. 파드 이름 뒤의 무작위 글자는 ReplicaSet 과 파드마다 붙는 것이라 사람마다 다르다. Service 는 클러스터 안의 주소라 내 컴퓨터에서 바로 못 들어간다. 연습할 땐 port-forward 로 구멍을 하나 뚫는다. 

kubectl -n cicd-hello port-forward svc/cicd-hello 8200:80

이 터미널은 열어 둔 채로, 새 우분투 터미널을 하나 더 열어서:

curl localhost:8200/
curl localhost:8200/health
Hello, Docker CI/CD! version=12-a1b2c3d
{"status":"ok","version":"12-a1b2c3d"}

port-forward — 내 컴퓨터의 포트(8200)를 클러스터 안의 Service·파드 포트로 잠깐 이어 주는 터널. 명령을 끄면 끊긴다. 연습·디버깅용이고, 실제 서비스는 Ingress 나 LoadBalancer 로 바깥에 연다.
Ingress — 도메인·경로별로 바깥 요청을 Service 에 나눠 주는 입구 설정. 이 시리즈에서는 쓰지 않는다.

인사말은 9편 5단계에서 바꾼 문구다. 그 단계를 건너뛰었거나 (나) 방식이면 Hello, CI/CD! 로 나온다.

상태 보는 명령 넷

kubectl -n cicd-hello get all                  # 한 번에 훑기
kubectl -n cicd-hello describe pod <파드이름>    # 자세히 + 맨 아래 Events (문제는 대개 여기 있다)
kubectl -n cicd-hello logs deploy/cicd-hello    # 앱 로그 (파드 중 하나)
kubectl -n cicd-hello get pods -o wide         # 파드 IP·노드까지

6. 일부러 망가뜨려 보기 — 자가 치유

파드 하나를 지운다. 이름은 get pods 에서 복사한다.

kubectl -n cicd-hello delete pod <파드이름 하나>
kubectl -n cicd-hello get pods
NAME                          READY   STATUS    RESTARTS   AGE
cicd-hello-6d9f7c8b5d-9mjzt   1/1     Running   0          5m
cicd-hello-6d9f7c8b5d-r7wq2   1/1     Running   0          4s     ← 새로 생김

지웠는데 몇 초 만에 다른 이름의 파드가 생겼다. Deployment 가 "2개여야 하는데 1개네" 하고 채운 것이다. 서버 한 대의 docker run 에는 없던 능력이다.

선언형(declarative) — 결과 상태를 적고 방법은 시스템에 맡기는 방식. 반대는 명령형(imperative): "컨테이너 하나 띄워, 하나 더 띄워" 처럼 할 일을 하나씩 시키는 방식.
조정 루프(reconciliation loop) — 원하는 상태와 현재 상태를 계속 비교해 차이를 메우는 반복. 쿠버네티스 컨트롤러와 ArgoCD 의 핵심 동작이다.

7. 늘리기 — 스케일

kubectl -n cicd-hello scale deploy/cicd-hello --replicas=4
kubectl -n cicd-hello get pods

네 개가 된다. 그런데 이건 명령으로 바꾼 것이라 k8s/deployment.yaml 에는 여전히 replicas: 2 라고 적혀 있다. 누가 나중에 kubectl apply -f k8s/ 를 다시 하면 2개로 돌아간다. 파일과 클러스터가 어긋난 상태 — 이걸 드리프트(drift)라고 부르고, 12편에서 ArgoCD 가 잡아내는 장면을 본다. 지금은 파일대로 되돌려 둔다. 

kubectl apply -f k8s/
deployment.apps/cicd-hello configured

8. 새 버전으로 바꾸기 — 롤링 업데이트

Docker Hub 에 태그가 둘 이상 있으면 다른 태그를 고른다(9편에서 두 번 이상 빌드했다면 있다). (나)를 골랐다면 APP_VERSION=local-2 로 하나 더 만들어 kind load 한다. 그리고 deployment.yaml 의 image: 줄 태그를 바꿔 다시 적용한다. 

# k8s/deployment.yaml 의 image 태그를 새 것으로 고친 뒤
kubectl apply -f k8s/
kubectl -n cicd-hello rollout status deploy/cicd-hello
Waiting for deployment "cicd-hello" rollout to finish: 1 out of 2 new replicas have been updated...
Waiting for deployment "cicd-hello" rollout to finish: 1 old replicas are pending termination...
deployment "cicd-hello" successfully rolled out

새 파드를 하나 띄워 readiness 검사가 통과하면 옛 파드를 하나 내리고, 다시 하나 띄우고… 를 반복한다. 그래서 바꾸는 동안에도 항상 파드가 떠 있다. port-forward 를 다시 켜고(Deployment 가 바뀌면 끊길 수 있다) curl localhost:8200/ 로 버전이 바뀐 걸 확인한다.

롤링 업데이트(rolling update) — 옛 버전을 한꺼번에 끄지 않고 새 버전과 하나씩 바꿔 끼우는 배포 방식. Deployment 의 기본값이다.
무중단 배포 — 배포하는 동안 사용자가 끊김을 못 느끼게 하는 것. readinessProbe 가 있어야 "준비 안 된 새 파드"로 요청이 가지 않는다.

9. 되돌리기 — rollout undo

kubectl -n cicd-hello rollout history deploy/cicd-hello
REVISION  CHANGE-CAUSE
1         <none>
2         <none>

kubectl -n cicd-hello rollout undo deploy/cicd-hello
kubectl -n cicd-hello rollout status deploy/cicd-hello

이전 ReplicaSet 을 다시 키워서 1분도 안 걸려 옛 버전으로 돌아간다. 이미지를 다시 빌드하지 않는다는 게 핵심이다. 다만 이것도 7번처럼 파일과 어긋난다(파일은 새 태그, 클러스터는 옛 태그). GitOps 에서는 되돌리기도 Git 에서 한다(13편).

다음 단계로 가기 전 정리

  • 클러스터는 지우지 않는다. 11~13편에서 계속 쓴다.
  • 손으로 배포한 앱은 지운다. 12편에서 ArgoCD 가 처음부터 다시 배포하게 하려는 것이다: kubectl delete namespace cicd-hello
  • ~/cicd/k8s-practice/k8s/ 의 YAML 세 개는 남겨 둔다. 12편에서 매니페스트 저장소로 옮긴다.
  • 9편의 도커 젠킨스(8090)·앱 컨테이너(8100)는 메모리가 빠듯하면 꺼 둔다: 젠킨스 폴더에서 docker compose stop, docker stop cicd-hello
