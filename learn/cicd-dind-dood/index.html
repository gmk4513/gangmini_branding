THEORY · CI/CD 07/13

DinD 와 DooD
— 컨테이너 안에서 도커를 쓰는 두 방법

이론 Docker DinD DooD docker.sock 보안 2026.11.10

4~6번에서는 젠킨스를 우분투에 직접 깔았다. 이제부터는 젠킨스도 컨테이너로 띄우고, 그 젠킨스가 앱을 도커 이미지로 만들어 배포하게 할 것이다. 그런데 여기서 문제가 하나 생긴다. 젠킨스가 컨테이너 안에 갇혀 있는데, 그 안에서 docker build 를 어떻게 치나?

답은 두 가지다. 컨테이너 안에 도커를 하나 더 띄우거나(DinD), 바깥에 이미 있는 도커를 빌려 쓰거나(DooD). 이 글은 두 방법을 직접 띄워 차이를 눈으로 보고, 다음 글(8번)에서 어느 쪽을 쓸지 정한다.

이번 단계에서 할 것

  1. 도커가 어떻게 생겼는지 다시 보기 — 클라이언트, 데몬, 소켓
  2. DinD 를 띄워 보고, 안에서 보이는 것 확인
  3. DooD 를 띄워 보고, 안에서 보이는 것 확인
  4. DooD 의 볼륨 경로 함정 직접 겪어 보기
  5. 보안 문제와 비교표 정리

끝나면 — "DinD 안에서는 바깥 컨테이너가 안 보이고, DooD 안에서는 보인다"를 내 터미널에서 확인했고, 왜 그런지 그림으로 설명할 수 있다.

먼저 — 도커는 두 프로그램이다

우리가 치는 docker 명령은 사실 심부름꾼이다. 진짜 일(이미지 만들기, 컨테이너 띄우기)은 뒤에서 늘 돌고 있는 도커 데몬이 한다. 둘은 소켓이라는 파일 하나(/var/run/docker.sock)로 말을 주고받는다.

이미지(image) — 앱과 앱이 돌 환경(파이썬, 패키지)을 통째로 얼려 둔 꾸러미. 붕어빵 틀.
컨테이너(container) — 이미지를 실제로 띄운 것. 틀에서 찍어 낸 붕어빵. 한 이미지로 여러 개를 띄울 수 있다.
레지스트리(registry) — 이미지를 올려 두고 받아 가는 창고. Docker Hub 가 가장 흔하다.
데몬(daemon) — 화면 없이 뒤에서 계속 돌며 부탁을 기다리는 프로그램. 도커 데몬의 이름은 dockerd.
소켓(socket) — 같은 컴퓨터 안의 두 프로그램이 말을 주고받는 통로. 리눅스에서는 파일처럼 생겼다(/var/run/docker.sock). 이 파일에 쓸 수 있으면 데몬에게 무엇이든 시킬 수 있다.

왜 이게 문제가 되나

젠킨스를 컨테이너로 띄우면 젠킨스는 자기 컨테이너 안만 볼 수 있다. 그 안에는 도커 데몬이 없다. 그래서 파이프라인에서 docker build 를 치면 이렇게 끝난다. 

docker: command not found               # 도커 클라이언트조차 없을 때
Cannot connect to the Docker daemon at unix:///var/run/docker.sock.
Is the docker daemon running?                # 클라이언트는 있는데 붙을 데몬이 없을 때

클라이언트는 이미지에 깔면 된다(8번에서 한다). 남는 질문은 "어느 데몬에 붙나"다. 그 답이 DinD 와 DooD 다.

DinD (Docker in Docker) — 컨테이너 안에 도커 데몬을 하나 더 띄운다. 안쪽 도커는 바깥과 완전히 따로 논다.
DooD (Docker outside of Docker) — 컨테이너 안에는 클라이언트만 두고, 바깥(호스트) 데몬의 소켓을 컨테이너 안으로 연결해 빌려 쓴다. "Docker-out-of-Docker", 또는 그냥 "소켓 마운트 방식"이라고도 부른다.
호스트(host) — 컨테이너를 띄워 준 바깥 컴퓨터. 이 실습에서는 Docker Desktop 이 띄운 리눅스, 실서버라면 그 서버.

그림으로 — 두 방법의 차이

1. 준비 — 비교용 컨테이너 하나 띄우기

우분투 터미널에서 친다. "바깥에 무엇이 떠 있는지"를 알아보기 쉽게, 3번 글에서 만든 cicd-hello 를 이미지로 만들어 하나 띄워 둔다. 이미지는 저장소 폴더에서 만든다. 

cd ~/cicd/cicd-hello
docker build -t cicd-hello:local .
docker run -d --name hello-outside -p 8100:8000 cicd-hello:local
docker ps --format 'table {{.Names}}\t{{.Image}}'
NAMES           IMAGE
hello-outside   cicd-hello:local

지금 바깥(호스트 데몬)에는 컨테이너가 하나 있다. 이걸 기준으로 DinD 와 DooD 안에서 무엇이 보이는지 본다.

2. DinD — 안에 데몬을 하나 더

도커 회사가 DinD 용 이미지(docker:dind)를 직접 낸다. 안에 데몬을 돌리려면 컨테이너에 거의 모든 권한을 줘야 해서 --privileged 가 필요하다. 

docker run -d --name dind --privileged docker:dind
sleep 10                                     # 안쪽 데몬이 뜰 때까지
docker exec dind docker ps                   # dind 안에서 docker ps
docker exec dind docker images

머리줄만 있고 내용이 없다 (Docker Desktop 29.6.1 에서 실제로 받은 출력).

CONTAINER ID   IMAGE     COMMAND   CREATED   STATUS    PORTS     NAMES
IMAGE   ID             DISK USAGE   CONTENT SIZE   EXTRA

둘 다 비어 있다. 바깥에 hello-outside 도, cicd-hello:local 이미지도 있는데 안에서는 안 보인다. 안쪽 데몬은 갓 태어난 별개의 도커이기 때문이다. 그래서 DinD 안에서 빌드하면 python:3.12-slim 같은 바탕 이미지를 처음부터 다시 받는다. 컨테이너를 지우면 그 캐시도 같이 사라진다.

--privileged 를 빼면 어떻게 되는지도 본다. 

docker run -d --name dind-noprv docker:dind
sleep 5
docker ps -a --filter name=dind-noprv --format '{{.Status}}'
docker logs dind-noprv 2>&1 | tail -3

실제로 받은 출력이다. 에러 문구는 도커 버전마다 조금씩 다를 수 있다.

Exited (1) 7 seconds ago
Could not mount /sys/kernel/security.
AppArmor detection and --privileged mode might break.
mount: permission denied (are you root?)

데몬을 띄우려면 커널 기능을 직접 만져야 하는데, 보통 컨테이너에는 그 권한이 없다. 그래서 DinD 는 --privileged 없이는 안 된다. 이게 DinD 의 가장 큰 약점이다(아래 보안 절).

--privileged — 컨테이너에 호스트 커널의 거의 모든 기능과 장치 접근을 열어 주는 옵션. 컨테이너가 "격리된 상자"가 아니게 된다.
TLS 2376 — docker:dind 는 다른 컨테이너가 네트워크로 붙을 수 있게 2376 포트를 TLS(암호화 연결)로 연다. 젠킨스 컨테이너를 따로 두고 DOCKER_HOST=tcp://dind:2376 로 붙게 하는 구성이 젠킨스 공식 문서의 DinD 예시다. 인증서는 볼륨으로 나눠 갖는다. 

docker rm -f dind dind-noprv                 # 정리

3. DooD — 바깥 소켓을 빌려 쓰기

이번엔 데몬 없이 클라이언트만 든 이미지(docker:cli)를 띄우고, 바깥 소켓 파일을 -v 로 연결한다. 

docker run --rm \
  -v /var/run/docker.sock:/var/run/docker.sock \
  docker:cli docker ps --format 'table {{.Names}}\t{{.Image}}'

이렇게 나온다. 첫 줄 이름은 도커가 무작위로 붙인다(직접 돌렸을 땐 jovial_einstein).

NAMES             IMAGE
jovial_einstein   docker:cli          ← 방금 띄운 자기 자신
hello-outside     cicd-hello:local

바깥 컨테이너가 보인다. 심지어 자기 자신도 목록에 있다. 안에서 친 docker 가 바깥 데몬에게 그대로 전달되기 때문이다. (같은 실험을 8번 글의 젠킨스 이미지로 해 봤을 때도, 컨테이너 안의 docker ps 에 바깥에서 띄운 앱 컨테이너가 그대로 보였다.) 이 컨테이너 안에서 docker run 을 하면 새 컨테이너는 이 컨테이너 안이 아니라 옆에 생긴다(형제 컨테이너). 캐시도 바깥 것을 그대로 쓰니 빌드가 빠르다.

마운트(mount) — 바깥의 파일이나 폴더를 컨테이너 안의 어떤 경로에 "붙여 보이게" 하는 것. -v 바깥경로:안경로.
형제 컨테이너(sibling container) — DooD 에서 컨테이너 안의 명령으로 만든 컨테이너. 같은 데몬이 만들었으니 부모·자식이 아니라 나란히 선 형제다.

젠킨스 사용자라면 — 권한 거부

docker:cli 는 root 로 돌아서 바로 됐다. 젠킨스 이미지는 jenkins(uid 1000) 사용자로 돈다. 그대로 소켓만 붙이면 이렇게 된다. 

permission denied while trying to connect to the docker API at unix:///var/run/docker.sock

소켓 파일은 아무나 쓸 수 없게 그룹 권한이 걸려 있다. 컨테이너 안에서 소켓을 보면 주인과 그룹 번호가 나온다. 

docker run --rm -v /var/run/docker.sock:/var/run/docker.sock alpine \
  stat -c '%A %u %g' /var/run/docker.sock
srw-rw---- 0 0        # Docker Desktop: 주인 root(0), 그룹 root(0)
srw-rw---- 0 999      # 리눅스 Docker Engine 예: 그룹이 docker(번호는 서버마다 다름)

그룹이 읽고 쓸 수 있으니(rw- 가운데 칸), 젠킨스 사용자를 그 그룹 번호에 넣어 주면 된다. docker run --group-add 0 … 처럼. 8번 글에서 compose 파일에 이걸 넣는다. Docker Desktop(29.6.1)에서 직접 해 보니, --group-add 없이는 위 permission denied 가 나고 --group-add 0 을 주면 docker ps 가 됐다.

4. DooD 의 함정 — 볼륨 경로는 바깥 기준이다

DooD 를 쓰다 거의 모두 한 번은 걸리는 문제다. 컨테이너 안에서 -v $PWD:/app 처럼 현재 폴더를 붙이면, 그 경로를 해석하는 건 바깥 데몬이다. 바깥에는 그 경로가 없거나, 다른 내용이 있다. 

# 컨테이너 안에 /work/hello.txt 를 만들고, 그 폴더를 새 컨테이너에 붙여 본다
docker run --rm -v /var/run/docker.sock:/var/run/docker.sock docker:cli sh -c '
  mkdir -p /work && echo "안에서 만든 파일" > /work/hello.txt
  ls /work
  echo "--- 형제 컨테이너에서 본 /work:"
  docker run --rm -v /work:/data alpine ls -la /data
'
hello.txt
--- 형제 컨테이너에서 본 /work:
total 4
drwxr-xr-x    2 root     root            40 Nov 10 08:48 .
drwxr-xr-x    1 root     root          4096 Nov 10 08:48 ..

비어 있다. 바깥 데몬은 "호스트의 /work"를 붙였고, 그건 (없어서) 새로 만든 빈 폴더다. 우리가 만든 파일은 docker:cli 컨테이너 안에만 있다.

젠킨스로 치면, 젠킨스 작업 폴더(/var/jenkins_home/workspace/…)를 -v 로 다른 컨테이너에 넘기려 할 때 이렇게 된다. 피하는 법은 두 가지다.

  • 파일을 -v 로 넘기지 않는다. docker build . 는 괜찮다. 클라이언트가 폴더 내용을 묶어서(빌드 컨텍스트) 데몬에게 보내기 때문이다. 그래서 테스트도 -v 로 코드를 붙여 돌리는 대신 docker build --target test 로 한다(9번 글).
  • 꼭 붙여야 하면 젠킨스 홈을 바깥과 같은 경로로 마운트한다(예: 바깥 /var/jenkins_home ↔ 안 /var/jenkins_home). 이름 있는 볼륨을 쓸 땐 --volumes-from 도 방법이다.

빌드 컨텍스트(build context) — docker build . 의 마지막 .. 이 폴더 내용을 통째로 묶어 데몬에게 보낸다. 그래서 DooD 에서도 빌드는 잘 된다. .dockerignore 에 적은 건 빠진다.

5. 보안 — 둘 다 "사실상 root"

  • DooD: 소켓에 쓸 수 있다 = 호스트의 root. 소켓으로 docker run -v /:/host --privileged … 를 시키면 호스트 디스크 전체를 열 수 있다. 젠킨스에 소켓을 줬다는 건, 젠킨스에서 파이프라인을 고칠 수 있는 사람 모두에게 서버 열쇠를 준 것과 같다. 그래서 젠킨스 로그인·권한 관리가 중요해진다.
  • DinD: --privileged 자체가 위험. 격리가 거의 풀린 컨테이너라 안에서 호스트로 빠져나갈 길이 많다. 대신 안쪽 도커가 바깥 컨테이너를 건드릴 수는 없다.
  • 완전히 안전하게 하려면 빌드 전용 서버(젠킨스 에이전트)를 따로 두거나, 데몬 없이 이미지를 만드는 도구(Kaniko, BuildKit rootless, Buildah)를 쓴다. 11번 글에서 쿠버네티스와 Kaniko 로 이어진다.

root — 리눅스에서 모든 것을 할 수 있는 관리자 계정. uid 0.
에이전트(agent) — 젠킨스가 빌드를 맡기는 일꾼 컴퓨터. 젠킨스 본체(컨트롤러)는 지시만 하고, 위험한 빌드는 에이전트에서 돌리는 게 원칙이다.

한 장 비교

DinDDooD
데몬컨테이너 안에 하나 더호스트 것 하나를 같이 씀
필요한 것--privileged소켓 마운트 + 그룹 권한
바깥 컨테이너가 보이나안 보임 (격리)다 보임, 지울 수도 있음
이미지 캐시따로. 컨테이너 지우면 사라짐 → 빌드 느림호스트 캐시 공유 → 빠름
만든 컨테이너 위치안쪽호스트에 형제로
-v 경로안쪽 기준호스트 기준 (함정)
보안privileged 라 위험소켓 = 호스트 root
쓰는 곳매번 깨끗한 도커가 필요한 CI, 도커 자체를 테스트할 때혼자·작은 팀의 젠킨스 서버, 빌드한 이미지를 바로 같은 서버에 띄울 때

이 시리즈는 DooD 로 간다. 이유는 두 가지다. 빌드한 이미지를 같은 서버에 바로 띄우는 것(9번의 배포)이 목표인데, DinD 로 하면 앱이 안쪽 데몬에 떠서 바깥에서 접속하기 번거롭다. 그리고 캐시를 공유하니 빌드가 빠르다. 대신 보안 약점을 알고 쓴다.

쿠버네티스에서는 — 둘 다 곤란하다

쿠버네티스 노드에는 보통 도커 데몬이 없다(1.24 부터 쿠버네티스는 도커 대신 containerd 같은 런타임을 직접 쓴다). 그래서 DooD 로 빌릴 소켓이 없다. DinD 는 되긴 하지만 파드에 privileged 를 줘야 해서, 많은 클러스터가 정책으로 막는다. 그래서 쿠버네티스 안에서는 데몬 없이 이미지를 만드는 도구(Kaniko 등)를 쓴다. 11번 글의 주제다.

컨테이너 런타임 — 컨테이너를 실제로 띄우는 프로그램. 도커도 내부적으로 containerd 를 쓴다. 쿠버네티스는 도커를 거치지 않고 containerd 를 바로 부른다.
Kaniko — 데몬 없이 Dockerfile 을 읽어 이미지를 만들고 레지스트리에 올리는 도구. 일반 권한 컨테이너에서 돈다.

정리하기

docker rm -f hello-outside                   # 비교용 컨테이너 지우기
docker ps -a                                  # 남은 것 확인

permission denied … docker.sock컨테이너 사용자가 소켓 그룹에 없다소켓 그룹 번호를 재서 --group-add
dind 컨테이너가 바로 꺼짐--privileged 빠짐붙인다 (그리고 위험을 안다)
-v 로 붙인 폴더가 비어 있음DooD 에서 경로를 호스트 기준으로 해석-v 대신 docker build 로 보내거나 같은 경로로 마운트
DinD 빌드가 매번 느림안쪽 캐시가 비어 있음안쪽 /var/lib/docker 를 볼륨으로 남기거나 DooD 로
우분투에서 docker 가 없다고 나옴Docker Desktop 의 WSL integration 이 꺼짐Docker Desktop → Settings → Resources → WSL integration → Ubuntu 켜기

이 글의 용어 정리
클라이언트 / 데몬 — 명령을 받아 전달하는 쪽 / 실제로 일하는 쪽.
docker.sock — 둘이 말하는 통로. 여기에 쓸 수 있으면 도커 전체를 쓸 수 있다.
DinD — 안에 데몬을 하나 더. 격리되지만 privileged 와 느린 캐시.
DooD — 바깥 데몬 빌려 쓰기. 빠르고 간단하지만 소켓이 곧 root, -v 는 바깥 경로.
형제 컨테이너 — DooD 안에서 만든 컨테이너가 호스트에 나란히 생기는 것.
