PRACTICE

운영 브랜치와 개발 브랜치
— main 과 dev 로 일하기

실습 Git 브랜치 전략 Git Flow 태그 hotfix 2026.10.28

브랜치와 Pull Request 에서는 브랜치가 main 하나였다. 일을 브랜치에서 하고, PR 로 main 에 합친다. 그런데 회사 저장소를 열어 보면 main 옆에 dev(또는 develop)가 하나 더 있는 경우가 많다. 내 공부 메모에도 이렇게 적혀 있다. "main(운영), dev(개발)". 왜 둘로 나누는지, 하루하루 어떻게 오가는지를 내 컴퓨터 안에서 한 바퀴 돌려 본다.

한 줄로 줄이면 이렇다. main 은 "지금 손님이 쓰고 있는 것", dev 는 "다음에 손님에게 나갈 것"이다.

왜 둘로 나누나

혼자 만든 사이트는 main 에 합치는 순간 바로 배포돼도 괜찮았다. 망가지면 내가 고치면 된다. 손님이 있는 서비스는 다르다. 기능 다섯 개가 동시에 만들어지고 있고, 그중 둘은 아직 덜 됐는데, 이미 나간 버전에서 급한 버그가 터진다. 이때 "지금 운영 중인 코드가 정확히 무엇인가"를 바로 알 수 있어야 한다.

브랜치뜻어디에 배포되나누가 합치나
main운영. 지금 손님이 쓰는 코드와 똑같다운영 서버 (실제 서비스)릴리스 때만. 보통 책임자가
dev개발. 다음 릴리스에 들어갈 것들을 모으는 곳개발 서버 (팀만 들어가는 주소)기능 PR 이 리뷰를 통과하면
feature/*기능 하나. 며칠 살다가 지워진다없음 (내 컴퓨터)나
hotfix/*운영 중 급한 버그 하나main 에 합쳐 바로 운영으로급한 사람이, 리뷰는 빠르게

dev 가 "완충지대"다. 새 기능은 먼저 dev 에 모여 개발 서버에서 팀이 직접 눌러 본다. 문제가 있으면 운영에 나가기 전에 거기서 잡힌다. 그리고 main 은 릴리스할 때만 움직이니, main 의 기록이 곧 "언제 무엇을 배포했나"의 기록이 된다.

운영(production) — 실제 사용자가 쓰는 환경. 줄여서 prod 라고 많이 부른다.
개발 서버 · 스테이징(staging) — 운영과 비슷하게 꾸린, 팀만 들어가는 환경. 회사마다 dev / stage / qa 처럼 여러 단계를 두기도 한다.
릴리스(release) — 모아 둔 변경을 묶어 운영에 내보내는 일, 또는 그렇게 나간 한 묶음.

한 바퀴의 모양

  1. 기능은 dev 에서 딴다. feature/memo-search 처럼 이름을 붙이고, 끝나면 dev 를 대상으로 PR 을 연다.
  2. dev 는 개발 서버로 자동 배포된다. 팀이 거기서 직접 눌러 보고 확인한다(QA).
  3. 모였으면 릴리스. dev → main PR 을 하나 열어 합친다. 이게 "이번 배포에 무엇이 나가나"의 목록이 된다.
  4. 태그를 단다. main 의 그 커밋에 v0.1.0 같은 버전 이름표를 붙인다. 운영 배포는 보통 이 태그를 기준으로 한다.
  5. 급한 불은 hotfix. 운영에서 버그가 나면 dev 가 아니라 main 에서 따서 고치고, main 에 합쳐 v0.1.1 로 내보낸 뒤, 같은 수정을 dev 에도 합친다. 안 그러면 다음 릴리스 때 버그가 되살아난다.

따라 하기 — 내 컴퓨터 안에서 한 바퀴

GitHub 없이도 연습할 수 있다. 내 컴퓨터에 "원격 저장소 역할"을 할 빈 저장소(bare)를 하나 만들고, 거기서 받아 와서 일한다. 아래 출력은 Git 2.47 에서 실제로 돌린 결과다(같은 경고 몇 줄은 지웠다). 연습용 앱 이름은 memo-api 로 했다.

1. 연습용 원격과 main 준비

$ mkdir gitprac3 && cd gitprac3
$ git init --bare remote.git          # 원격 역할. 작업 폴더가 없는 저장소
$ git clone remote.git memo-api
warning: You appear to have cloned an empty repository.
$ cd memo-api
$ git config user.name "me"; git config user.email "me@example.com"   # 이 저장소에서만
$ git switch -c main
$ echo "# memo-api" > README.md
$ git add . && git commit -m "처음 커밋"
$ git push -u origin main

2. dev 를 만들어 올리기

$ git switch -c dev
Switched to a new branch 'dev'
$ git push -u origin dev
 * [new branch]      dev -> dev

처음 한 번만 하는 일이다. 이 뒤로 기능 브랜치는 전부 dev 에서 딴다.

3. 기능 브랜치에서 일하고 dev 에 합치기

$ git switch -c feature/memo-search       # 지금 dev 위에 있으니 dev 에서 딴다
$ echo "def search(q): ..." > search.py
$ git add . && git commit -m "메모 검색 기능"
$ git push -u origin feature/memo-search
 * [new branch]      feature/memo-search -> feature/memo-search

# (GitHub 이었다면 여기서 base: dev 로 PR 을 열고 리뷰를 받는다. 여기서는 직접 합친다)
$ git switch dev
$ git merge --no-ff feature/memo-search -m "Merge feature/memo-search into dev"
Merge made by the 'ort' strategy.
 search.py | 1 +
 1 file changed, 1 insertion(+)
$ git push

--no-ff 는 "앞으로 감기(fast-forward)로 끝낼 수 있어도 합치기 커밋을 꼭 만들어라"라는 뜻이다. 그래야 dev 의 기록에 "여기서 기능 하나가 들어왔다"는 매듭이 남는다. GitHub 의 "Create a merge commit" 버튼이 이것과 같다.

4. 릴리스 — dev 를 main 에 합치고 태그

$ git switch main
$ git merge --no-ff dev -m "Release v0.1.0"
Merge made by the 'ort' strategy.
 search.py | 1 +
$ git tag -a v0.1.0 -m "첫 배포"
$ git push
$ git push origin v0.1.0
 * [new tag]         v0.1.0 -> v0.1.0

-a 를 붙인 태그(annotated tag)는 누가 언제 왜 달았는지가 같이 저장된다. 배포용 태그는 이걸 쓴다. 

$ git show v0.1.0 --no-patch
tag v0.1.0
Tagger: me <me@example.com>
Date:   Wed Oct 28 16:59:31 2026 +0900

첫 배포

5. 운영에서 버그 — hotfix

$ git switch -c hotfix/login-500 main     # dev 가 아니라 main 에서 딴다
$ echo "fix" > fix.txt
$ git add . && git commit -m "로그인 500 에러 수정"

$ git switch main
$ git merge --no-ff hotfix/login-500 -m "Merge hotfix/login-500"
$ git tag -a v0.1.1 -m "핫픽스"

$ git switch dev                          # 잊으면 다음 릴리스에 버그가 돌아온다
$ git merge --no-ff hotfix/login-500 -m "Merge hotfix/login-500 into dev"
$ git push origin main dev v0.1.1

왜 dev 에서 따지 않을까. dev 에는 아직 손님에게 안 나간 기능이 섞여 있다. 거기서 고쳐 main 에 합치면 덜 된 기능까지 같이 운영으로 나간다. 운영에 있는 것(main)에서 따야 "버그 수정 하나만" 나간다.

6. 그림으로 확인

$ git log --oneline --graph --all
*   53cbd22 (HEAD -> dev, origin/dev) Merge hotfix/login-500 into dev
|\
| | *   56f1393 (tag: v0.1.1, origin/main, main) Merge hotfix/login-500
| | |\
| | |/
| |/|
| * | e0c4b40 (hotfix/login-500) 로그인 500 에러 수정
| |/
| *   e26a861 (tag: v0.1.0) Release v0.1.0
| |\
| |/
|/|
* |   0aaff82 Merge feature/memo-search into dev
|\ \
| |/
|/|
| * 1de28e2 (origin/feature/memo-search, feature/memo-search) 메모 검색 기능
|/
* 5562457 처음 커밋

처음 보면 실이 엉킨 것 같다. 읽는 법은 하나다. 위가 최신, 별표(*)가 커밋, 괄호 안이 그 커밋을 가리키는 이름표. tag: v0.1.0, tag: v0.1.1 이 붙은 줄이 운영에 나간 순간이고, 둘 다 main 쪽 줄기에 있다.

7. 다음 릴리스에 무엇이 나가나

$ git log --oneline main..dev     # dev 에는 있고 main 에는 없는 것
53cbd22 Merge hotfix/login-500 into dev
$ git log --oneline dev..main     # main 에는 있고 dev 에는 없는 것
56f1393 Merge hotfix/login-500

A..B 는 "B 에는 있고 A 에는 없는 커밋"이다. 릴리스 PR 을 열기 전에 main..dev 를 보면 이번에 나갈 목록이 나온다. 여기서는 hotfix 를 양쪽에 따로 합쳐서 합치기 커밋 하나씩만 다르고, 파일 내용은 같다. 다음 릴리스 때 dev 를 main 에 합치면 이 차이도 정리된다.

8. 다 쓴 브랜치 지우기

$ git branch -d feature/memo-search hotfix/login-500
Deleted branch feature/memo-search (was 1de28e2).
Deleted branch hotfix/login-500 (was e0c4b40).
$ git push origin --delete feature/memo-search
 - [deleted]         feature/memo-search

bare 저장소 — 작업 폴더 없이 Git 기록만 담은 저장소. GitHub 의 저장소도 서버 쪽에서는 이런 모양이다.
fast-forward — 합칠 쪽에 새 커밋이 없으면, 합치기 커밋을 만들지 않고 이름표만 앞으로 옮기는 것.
태그(tag) — 특정 커밋에 붙이는, 움직이지 않는 이름표. 브랜치는 커밋할 때마다 앞으로 가지만 태그는 그 자리에 있다.

GitHub 에서는

  • 기본 브랜치를 dev 로. Settings → General → Default branch 를 dev 로 바꾸면 새 PR 의 기본 대상(base)이 dev 가 된다. 실수로 main 에 기능 PR 을 여는 일이 줄어든다.
  • PR 을 열 때 base 를 본다. PR 화면 위쪽 base: dev ← compare: feature/memo-search 가 맞는지 확인한다. 릴리스 PR 만 base: main ← compare: dev 다.
  • 두 브랜치 모두 보호. main 과 dev 에 직접 push 를 막고, PR 과 리뷰, 자동 검사 통과를 요구한다(협업 기능 실습). main 은 승인자를 더 엄격하게 두는 곳이 많다.
  • 태그로 배포. 릴리스 PR 을 합친 뒤 Releases → Draft a new release 에서 v0.1.0 태그를 만들면, 바뀐 것 목록(릴리스 노트)도 같이 남는다. 이 태그가 생길 때 운영 배포가 돌게 해 두는 경우가 많다(테스트와 CI/CD).

다른 방식들과 비교

main + dev 는 "Git Flow" 라는 방식을 가볍게 한 것이다. 이게 유일한 정답은 아니다. 자주 보는 셋을 놓고 보면 이렇다.

방식브랜치잘 맞는 곳대가
Git Flowmain · develop · feature · release · hotfix정해진 날에 버전을 묶어 내보내는 제품 (앱, 설치형 소프트웨어)브랜치가 많고, 오래 사는 브랜치끼리 맞추는 일이 생긴다
main + dev (이 글)main · dev · feature · hotfix개발 서버에서 한 번 확인하고 내보내는 웹 서비스, 작은 팀dev 와 main 이 벌어지지 않게 릴리스를 자주 해야 한다
GitHub Flowmain · 짧은 기능 브랜치합치면 바로 배포해도 되는 서비스. 자동 검사가 든든할 때"아직 내보내면 안 되는 기능"을 숨길 다른 수단이 필요하다
트렁크 기반main 하나에 하루 안에 합침배포가 아주 잦은 큰 팀. 기능 스위치(feature flag)를 쓰는 곳테스트 자동화와 기능 스위치 없이는 위험하다

처음 들어간 팀에서 할 일은 방식을 고르는 게 아니라, 그 팀이 무엇을 쓰는지 알아보는 것이다. 저장소의 기본 브랜치, 보호 규칙, 최근 PR 들의 base 를 보면 대개 바로 보인다. 혼자 하는 내 프로젝트는 지금처럼 main 하나(GitHub Flow)로 충분하다. 손님이 있는 서비스를 여럿이 만들게 되면 그때 dev 를 둔다.

정리

상황어디서 따나어디로 합치나
새 기능devdev (PR)
릴리스—dev → main, 그리고 태그
운영 급한 버그mainmain (태그) → dev 에도

main 은 손님이 보는 것과 늘 같아야 하고, dev 는 다음 배포의 대기실이다. 이 두 문장만 기억하면 나머지 규칙은 거기서 나온다. 다음은 이 흐름 위에서 코드를 어떻게 나눠 두는지(코드 구조), 그리고 dev·main 에 합칠 때 무엇이 자동으로 도는지(테스트와 CI/CD)다.

이어서 읽기

  • 브랜치와 Pull Request — main 하나로 도는 기본 흐름
  • 충돌 일부러 만들고 풀기 — dev 와 main 이 벌어지면 만나는 것
  • GitHub 협업 기능 실습 — 브랜치 보호와 리뷰
  • GitHub Actions 첫걸음 — PR 마다 자동 검사
  • 테스트와 CI/CD — dev·main 에 합칠 때 도는 것들
  • 코드 구조 큰 그림 · 의존성 주입
