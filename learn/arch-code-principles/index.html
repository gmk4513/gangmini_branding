이론 SLAP 이름 규칙 예외 처리 OpenAPI 코드 생성 2026.10.28

앞 글들이 "코드를 어느 폴더·층에 둘까"였다면, 이 글은 함수 하나를 어떻게 써야 남이 읽기 쉬운가다. 코드는 쓰는 시간보다 읽히는 시간이 훨씬 길다. 리뷰어가 읽고, 몇 달 뒤의 내가 읽고, AI 가 읽는다. 네 가지 원칙을 memo-api 예시로 본다. 예시 코드는 모두 직접 돌려 본 것이다.

1. SLAP — 한 함수 안의 줄들은 같은 높이로

SLAP(Single Level of Abstraction Principle)은 "한 함수 안의 줄들은 추상화 수준이 같아야 한다"는 원칙이다. 책의 목차를 떠올리면 쉽다. 목차에 "1장 시작하기 · 2장 설치 · 3장 pip install 을 치고 엔터를 누른다"가 섞여 있으면 이상하다. 3장만 갑자기 너무 자세하다.

섞여 있는 함수

def create_memo_with_summary(self, user_id, title, body):
    if not title.strip():                       # 검사 (세부)
        raise InvalidInput("제목이 비었다")
    if len(title) > 50:
        raise InvalidInput("제목은 50자까지")
    summary = body[:20]                          # 요약 (아주 세부)
    row = MemoRow(user_id=user_id, title=title.strip(), body=body, summary=summary)
    self.session.add(row)                        # DB (가장 세부)
    self.session.commit()
    return Memo(id=row.id, user_id=user_id, title=row.title, body=body, summary=summary)

"메모를 요약해서 만든다"는 한 문장짜리 일인데, 읽으려면 글자 수 검사, 문자열 자르기, DB 세션까지 다 머리에 올려야 한다.

높이를 맞춘 함수

class MemoService:
    # 고수준: 무엇을 하는지만
    def create_memo_with_summary(self, user_id: int, title: str, body: str) -> Memo:
        validate_title(title)
        memo = self._build_memo(user_id, title, body)
        return self.repository.create(memo)

    # 중간 수준: 어떻게 조립하는지
    def _build_memo(self, user_id: int, title: str, body: str) -> Memo:
        summary = summarize(body)
        return Memo(id=0, user_id=user_id, title=title.strip(), body=body, summary=summary)

이제 맨 위 함수는 세 줄짜리 목차다. 검사하고, 만들고, 저장한다. 더 궁금한 사람만 한 칸 아래로 내려가면 된다.

2. 동형원리 — 같은 일은 같은 모양으로

동형원리(Isomorphism)는 함수 이름, 매개변수 순서, 돌려주는 값의 규칙을 프로젝트 전체에서 통일하자는 원칙이다. 한 저장소의 규칙을 익히면 다른 저장소는 안 열어 봐도 쓸 수 있게 된다.

이름돌려주는 것없을 때
get_xxx / get도메인 객체 하나예외(NotFound)를 던진다
find_xxx / findOptional[도메인] 또는 list[도메인]None 이나 빈 리스트
…_by_yyyby 뒤가 조건find_all_by_user(user_id) = "user_id 가 같은 것 전부"
class MemoRepository:
    def get(self, memo_id: int) -> Memo:                       # 없으면 예외
        memo = self._rows.get(memo_id)
        if memo is None:
            raise NotFound(f"memo {memo_id}")
        return memo

    def find(self, memo_id: int) -> Optional[Memo]:            # 없으면 None
        return self._rows.get(memo_id)

    def find_all_by_user(self, user_id: int) -> list[Memo]:    # by 뒤가 조건
        return [m for m in self._rows.values() if m.user_id == user_id]
>>> repo.find(99)
None
>>> repo.get(99)

이렇게 정해 두면 이름만 보고 "get 이니까 None 검사는 안 해도 되겠구나", "find 니까 None 을 처리해야겠구나"를 안다. 매개변수 순서도 맞춘다. memo-api 에서는 누가(user_id) → 무엇을(memo_id) → 어떻게(내용) 순서로 통일했다: update_title(user_id, memo_id, title).

3. 선형원리 — 위에서 아래로 한 줄로 읽히게

선형원리는 처리 흐름이 가능한 한 직선이어야 한다는 원칙이다. if 와 반복문이 겹겹이 쌓이면 읽는 사람은 "지금 몇 번째 조건 안에 있지?"를 계속 세야 한다.

전: 중첩된 if

def update_title(repository, user_id, memo_id, title):
    memo = repository.find(memo_id)
    if memo is not None:
        if memo.user_id == user_id:
            if title.strip():
                if len(title) <= 50:
                    memo.title = title.strip()
                    return memo
                else:
                    return "제목은 50자까지"
            else:
                return "제목이 비었다"
        else:
            return "남의 메모"
    else:
        return "메모가 없다"

후: 검사는 validate 안에서 raise

def validate_owner(memo: Memo, user_id: int) -> None:
    if memo.user_id != user_id:
        raise Forbidden("남의 메모")

def validate_title(title: str) -> None:
    if not title.strip():
        raise InvalidInput("제목이 비었다")
    if len(title) > 50:
        raise InvalidInput("제목은 50자까지")

class MemoService:
    def update_title(self, user_id: int, memo_id: int, title: str) -> Memo:
        memo = self.repository.get(memo_id)      # 없으면 여기서 NotFound
        validate_owner(memo, user_id)
        validate_title(title)
        memo.title = title.strip()
        return memo

성공하는 길(happy path)이 들여쓰기 없이 한 줄로 내려간다. 실패는 각 검사 안에서 예외로 빠져나가고, 예외를 HTTP 상태 코드(404 · 403 · 422)로 바꾸는 일은 표현 층(webapp)이 한 곳에서 맡는다. 서비스는 HTTP 를 모른 채로 남는다.

4. 생성원칙 — 반복되는 코드는 생성기에게

생성원칙(Rule of Generation)은 "코드를 작성하는 코드를 작성하라"다. 사람은 똑같은 걸 백 번 손으로 옮겨 적는 데 약하다. 한 번은 꼭 틀린다.

대표적인 예가 API 클라이언트다. 프론트엔드는 서버의 주소마다 요청 함수와 응답 타입을 만들어야 한다. 서버가 바뀔 때마다 손으로 맞추면 언젠가 어긋난다. FastAPI 는 라우터와 DTO 를 보고 API 명세(/openapi.json)를 저절로 만들어 준다. 이 명세를 읽어서 TypeScript 함수와 타입을 뽑아 주는 도구(openapi-typescript, orval 등)가 있다.

나는 아직 이 도구들을 내 프로젝트에 써 보지 않았다. 다만 생각해 보면 비슷한 일을 이미 하고 있었다. 스토어 스크린샷이나 인스타 카드처럼 똑같은 작업을 여러 번 해야 할 때 손으로 만들지 않고 파이썬 스크립트로 뽑았다. 같은 원칙이다. 반복은 사람이 아니라 생성기가 한다.

추상화 수준 — "무엇을" 하는지에 가까울수록 높고, "어떻게" 하는지에 가까울수록 낮다. "메모를 만든다"는 높고, "INSERT 문을 보낸다"는 낮다.
happy path — 아무 문제 없이 성공하는 흐름. 선형원리는 이 길을 들여쓰기 없이 곧게 두자는 것이다.
OpenAPI — HTTP API 의 주소, 입력, 출력을 기계가 읽을 수 있게 적는 표준 형식(JSON/YAML).
코드 생성기 — 명세나 스키마를 읽어 코드를 대신 써 주는 도구. 만든 결과는 손으로 고치지 않고, 원본을 고친 뒤 다시 생성한다.
