젠킨스 대시보드로
— 빌드·배포 확인하기

실습 Jenkins Freestyle Poll SCM systemd JUnit 2026.11.10

앞 글에서 젠킨스를 깔았다. 이제 일을 시킨다. 이번 글의 목표는 CI/CD 한 바퀴를 가장 단순한 모양으로 끝까지 돌려 보는 것이다. GitHub 에 커밋이 올라오면 → 젠킨스가 알아채서 → 코드를 받아 테스트하고 → 통과하면 같은 서버에 배포한다.

화면에서 칸을 채워 만드는 Freestyle 잡으로 한다. 회사에서는 다음 글의 Jenkinsfile 방식을 더 많이 쓰지만, 젠킨스가 무엇을 어떤 순서로 하는지는 화면으로 한 번 보는 게 가장 빨리 잡힌다.

이번 단계에서 할 것

  1. 서버에 배포 자리 만들기 (systemd 서비스 cicd-hello, 포트 8000)
  2. Freestyle 잡 cicd-hello-freestyle 만들기 — 저장소 연결, 테스트, 결과 게시, 배포
  3. Build Now 로 돌리고 콘솔 출력·빌드 기록·환경 변수 읽기
  4. 일부러 테스트를 깨뜨려서 배포가 막히는 것 보기
  5. 커밋하면 저절로 돌게 (Poll SCM), 실서버라면 웹훅

끝나면: GitHub 에서 app.py 를 고쳐 커밋하고 2~3분 기다리면, curl localhost:8000/ 의 version= 숫자가 새 빌드 번호로 바뀐다.

한 바퀴의 모양

Freestyle 프로젝트 — 젠킨스에서 가장 오래된 잡 종류. 웹 화면의 칸(저장소, 트리거, 빌드 단계, 빌드 후 조치)을 채워서 만든다. 설정은 젠킨스 안에만 저장된다.
빌드(build) — 여기서는 "잡을 한 번 돌린 것" 전체를 말한다. 컴파일이 없는 파이썬이라도 테스트·배포까지 한 번 돈 걸 빌드라고 부른다.

1. 서버에 배포 자리 만들기 (한 번만)

배포할 곳을 먼저 만든다. 회사로 치면 "운영 서버에 앱이 사는 폴더와 서비스"를 관리자가 미리 꾸려 두는 단계다. 우분투 터미널에서 한다.

1-1. 필요한 패키지

sudo apt install -y python3-venv curl

우분투의 파이썬은 가상환경 기능(venv)이 따로 떨어져 있어서 깔아 줘야 한다. 젠킨스 빌드에서도, 배포 자리에서도 쓴다.

1-2. 앱 폴더와 가상환경

sudo mkdir -p /opt/cicd-hello
sudo chown jenkins:jenkins /opt/cicd-hello
sudo -u jenkins python3 -m venv /opt/cicd-hello/venv
echo "APP_VERSION=manual" | sudo -u jenkins tee /opt/cicd-hello/version.env

폴더 주인을 jenkins 사용자로 바꾸는 게 핵심이다. 젠킨스 빌드는 jenkins 사용자로 돌기 때문에, 주인이 아니면 파일을 복사할 수 없다.

/opt — 리눅스에서 따로 설치하는 프로그램을 두는 관례적인 자리.
sudo -u jenkins — 관리자 권한으로 "jenkins 사용자인 척" 명령을 실행. 만들어지는 파일의 주인이 jenkins 가 된다.
가상환경(venv) — 프로젝트마다 따로 쓰는 파이썬 패키지 상자. 서버 전체 파이썬을 더럽히지 않는다. 자세히는 실습 환경 준비.

1-3. systemd 서비스 파일

sudo nano /etc/systemd/system/cicd-hello.service
[Unit]
Description=cicd-hello (CI/CD 실습 앱)
After=network.target

[Service]
User=jenkins
WorkingDirectory=/opt/cicd-hello
EnvironmentFile=/opt/cicd-hello/version.env
ExecStart=/opt/cicd-hello/venv/bin/python app.py
Restart=always

[Install]
WantedBy=multi-user.target

저장(Ctrl+O, Enter)하고 나간다(Ctrl+X). 그리고 systemd 에 알린다.

sudo systemctl daemon-reload
sudo systemctl enable cicd-hello

아직 start 는 안 한다. app.py 가 없어서 켜자마자 죽는다. 첫 배포는 젠킨스가 한다.

줄뜻
User=jenkins앱을 jenkins 사용자로 돌린다. root 로 돌리면 앱이 뚫렸을 때 서버 전체가 넘어간다
EnvironmentFile=이 파일의 이름=값 줄을 환경 변수로 읽는다. 젠킨스가 여기에 빌드 번호를 적는다 → 앱의 APP_VERSION
ExecStart=실행할 명령. 가상환경 안의 파이썬으로 app.py 를 돌린다 (포트 8000)
Restart=always앱이 죽으면 다시 살린다
WantedBy=multi-user.targetenable 하면 서버가 켜질 때 같이 켜진다

서비스 파일(unit file) — systemd 에게 "이 프로그램을 이렇게 돌려라"를 적어 주는 설정 파일. /etc/systemd/system/ 에 둔다.
daemon-reload — 서비스 파일을 새로 만들거나 고친 뒤 systemd 가 다시 읽게 하는 명령.

1-4. jenkins 에게 재시작 권한 하나만 주기

서비스를 재시작하려면 관리자 권한(sudo)이 필요하다. 그렇다고 jenkins 에게 sudo 전체를 주면 빌드 스크립트 한 줄로 서버 전체를 바꿀 수 있다. 그래서 딱 이 명령 하나만, 비밀번호 없이 허락한다. 

sudo visudo -f /etc/sudoers.d/jenkins-cicd-hello
jenkins ALL=(root) NOPASSWD: /usr/bin/systemctl restart cicd-hello

저장하고 나오면 visudo 가 문법을 검사한다. 틀렸으면 저장 전에 알려 준다. 제대로 됐는지 jenkins 사용자로 직접 해 본다.

sudo -u jenkins sudo -n systemctl restart cicd-hello; echo "결과: $?"
sudo -u jenkins sudo -n systemctl stop cicd-hello;    echo "결과: $?"
결과: 0                         ← restart 는 허락됨 (app.py 가 아직 없어 곧 죽지만 명령 자체는 통과)
sudo: a password is required
결과: 1                         ← stop 은 허락 안 됨. 의도한 대로

sudoers — 누가 어떤 명령을 sudo 로 실행할 수 있는지 적은 규칙 파일. 직접 편집하다 문법을 틀리면 sudo 자체가 막히므로 반드시 visudo 로 고친다.
NOPASSWD — 그 명령은 비밀번호를 묻지 않는다. 젠킨스는 비밀번호를 칠 수 없으니 필요하다. 대신 명령을 하나로 좁혀 둔다(최소 권한 원칙).
sudo -n — 비밀번호를 물어야 하면 기다리지 말고 바로 실패하라는 뜻. 빌드가 멈춰 서는 걸 막는다.

2. Freestyle 잡 만들기

대시보드 왼쪽 + New Item → 이름 cicd-hello-freestyle → Freestyle project → OK. 설정 화면이 길게 나온다. 위에서부터 채운다.

2-1. General

  • Description: cicd-hello 테스트 후 8000 포트로 배포
  • Discard old builds 체크 → Max # of builds to keep: 20. 빌드 기록이 끝없이 쌓여 디스크를 채우는 걸 막는다

2-2. Source Code Management

  • Git 선택
  • Repository URL: https://github.com/<내아이디>/cicd-hello.git
  • Credentials: - none -. 공개 저장소라 받기만 할 때는 필요 없다. 비공개라면 앞 글에서 만든 github-token 을 고른다
  • Branch Specifier: */main (기본값은 */master 라서 꼭 바꾼다)

2-3. Triggers — 일단 비워 둔다

저절로 도는 건 5번 단계에서 켠다. 처음에는 손으로 돌려 본다.

2-4. Environment

  • Add timestamps to the Console Output 체크 (로그 줄마다 시각이 붙어 어디서 오래 걸렸는지 보인다)

2-5. Build Steps — 테스트

Add build step → Execute shell 을 고르고 넣는다.

echo "=== 빌드 #$BUILD_NUMBER / 커밋 $GIT_COMMIT ==="

python3 -m venv venv
venv/bin/pip install -q -r requirements-dev.txt
venv/bin/python -m pytest -q --junitxml=test-results.xml

평소처럼 . venv/bin/activate 로 가상환경을 켜도 되지만, 젠킨스 로그에 activate 스크립트 속 명령이 스무 줄 넘게 찍혀 정작 중요한 줄이 묻힌다(아래 -x 때문). 그래서 가상환경 안의 pip, python 을 경로로 직접 부른다. 결과는 같다.

젠킨스는 이 칸을 sh -xe 로 실행한다. -x 는 실행하는 줄을 + 를 붙여 로그에 찍고, -e 는 한 줄이라도 실패하면 거기서 멈추고 빌드를 실패로 만든다. pytest 는 테스트가 하나라도 깨지면 실패 코드로 끝나니, 그대로 빌드 실패가 된다.

--junitxml 은 테스트 결과를 젠킨스가 읽는 XML 형식으로도 남기라는 옵션이다. 아래 빌드 후 조치에서 이 파일을 읽는다.

2-6. Build Steps — 배포

Add build step → Execute shell 을 하나 더 추가한다. 테스트 칸 아래에 있어야 한다.

# 1) 코드 복사 → 2) 패키지 맞추기 → 3) 버전 기록 → 4) 재시작
cp app.py requirements.txt /opt/cicd-hello/
/opt/cicd-hello/venv/bin/pip install -q -r /opt/cicd-hello/requirements.txt
echo "APP_VERSION=$BUILD_NUMBER" > /opt/cicd-hello/version.env
sudo -n systemctl restart cicd-hello

# 5) 확인: 10초 안에 /health 가 대답하면 성공
for i in $(seq 1 10); do
  if curl -fsS http://localhost:8000/health; then
    echo; echo "배포 확인 완료"; exit 0
  fi
  sleep 1
done
echo "배포 확인 실패: 8000 포트가 대답하지 않음"
exit 1

마지막 확인을 빼먹기 쉽다. restart 는 "재시작을 시켰다"까지만 성공이고, 앱이 정말 떴는지는 모른다. 문법 오류가 있는 app.py 라도 restart 명령 자체는 성공한다. 그래서 밖에서 한 번 불러 보고 대답이 없으면 빌드를 실패로 만든다.

헬스 체크(health check) — "살아 있니?"라고 묻는 가벼운 주소(/health)를 불러 앱이 정상인지 보는 것. 배포 뒤, 그리고 운영 중 감시에 쓴다.
curl -fsS — -f 는 HTTP 에러(404·500)면 실패로 끝나기, -s 는 진행 표시 숨기기, -S 는 그래도 에러 메시지는 보이기.

2-7. Post-build Actions — 테스트 결과 게시

  • Add post-build action → Publish JUnit test result report
  • Test report XMLs: test-results.xml

Save.

빌드 후 조치(post-build action) — 빌드 단계가 끝난 뒤 성공·실패와 상관없이 하는 일. 테스트 결과 게시, 알림 보내기, 결과물 보관 등.
JUnit XML — 원래 Java 테스트 도구 JUnit 의 결과 형식인데, 거의 모든 언어의 테스트 도구가 이 형식으로 내보낼 수 있어서 CI 도구들의 공용어가 됐다.

콘솔 출력 읽는 순서

잡 화면에서 볼 것

위치보이는 것
Builds 목록빌드 번호와 상태 아이콘. 초록 체크 = 성공, 빨간 X = 실패, 노란 느낌표 = 불안정(빌드는 끝났지만 테스트 일부 실패 등), 회색 = 중단·아직 안 함
날씨 아이콘 (대시보드)최근 빌드 다섯 개 중 성공 비율. 해 = 다 성공, 먹구름·번개 = 대부분 실패
Test Result / 추세 그래프JUnit 결과. 몇 개 통과·실패, 어떤 테스트가 언제부터 깨졌나
Workspace워크스페이스 폴더를 브라우저로 둘러보기. test-results.xml, venv/ 가 보인다
Changes (빌드 안)이 빌드에 새로 들어온 커밋 목록

UNSTABLE(불안정) — 빌드 명령은 성공했지만 결과물에 문제가 있다는 중간 상태. 주로 "테스트 결과 파일에 실패가 있음"일 때. 이 잡은 pytest 가 실패하면 셸 단계부터 실패라서 보통 FAILURE 가 된다.
빌드 번호 — 잡마다 1 부터 하나씩 오르는 번호. 지워도 재사용하지 않는다. 그래서 "몇 번 빌드가 운영에 나갔나"의 이름표로 쓴다. 이 실습에서는 앱의 version= 이 된다.

4. 젠킨스가 넣어 주는 환경 변수

빌드 스크립트 안에서 $BUILD_NUMBER, $GIT_COMMIT 을 따로 정의하지 않고 썼다. 젠킨스가 빌드마다 넣어 주는 값이다. 자주 쓰는 것만 추린다.

변수예쓰임
BUILD_NUMBER7버전·이미지 태그
JOB_NAMEcicd-hello-freestyle알림 메시지
WORKSPACE/var/lib/jenkins/workspace/cicd-hello-freestyle파일 경로
GIT_COMMIT1a2b3c4d… (40자)"어느 코드로 만들었나" 기록
GIT_BRANCHorigin/main브랜치마다 다르게 할 때
BUILD_URLhttp://localhost:8080/job/…/7/알림에 링크 달기. 앞 글 3-4 의 Jenkins URL 로 만들어진다. 그 칸이 비어 있으면 값이 없다(파이프라인에서는 null 로 찍힌다)

전체 목록은 http://localhost:8080/env-vars.html 에서 볼 수 있다. 빌드 스크립트에 env | sort 를 한 줄 넣어 콘솔에서 직접 봐도 된다.

GitHub 에서 다시 Hello, CI/CD! 로 되돌려 커밋하고, 다시 돌려서 초록으로 만든다.

6. 커밋하면 저절로 — Poll SCM 과 웹훅

지금은 Build Now 를 눌러야 돈다. 커밋만 하면 알아서 돌게 바꾼다. 방법은 두 가지다.

방식어떻게언제 쓰나
Poll SCM젠킨스가 정해진 주기마다 GitHub 에 "새 커밋 있어?"라고 물어본다젠킨스가 사내망·내 PC 안에 있어 밖에서 못 들어올 때 (이 실습)
웹훅GitHub 가 커밋 즉시 젠킨스 주소로 "새 커밋 왔어"를 보낸다젠킨스 주소가 인터넷에서 열려 있을 때. 회사 서버 대부분

6-1. Poll SCM 켜기

잡 → Configure → Triggers → Poll SCM 체크 → Schedule:

H/2 * * * *

Save. 이제 GitHub 에서 app.py 의 문구를 살짝 바꿔(예: Hello, CI/CD! 뒤에 :) 추가 — 테스트는 "포함"만 보니 통과한다) 커밋하고 2분 남짓 기다린다. Builds 에 새 번호가 생기고, 빌드 화면에 Started by an SCM change 라고 적힌다. 잡 화면의 Git Polling Log 에서 젠킨스가 언제 물어봤는지 보인다.

SCM(Source Code Management) — 소스 코드 관리 도구. 여기서는 Git 이다. Poll SCM 은 "코드 저장소를 주기적으로 들여다보기".
크론(cron) 표현식 — 분 시 일 월 요일 다섯 칸으로 주기를 적는 리눅스 표기. */2 는 "2마다". 젠킨스는 여기에 H 를 더했다. H/2 는 "2분마다, 다만 시작 분은 잡 이름에 따라 흩어서" — 잡 100개가 같은 순간에 GitHub 를 두드리지 않게 하는 장치다.

6-2. 실서버라면 — GitHub 웹훅

폴링은 2분 늦고, 잡이 많으면 GitHub 에 쓸데없는 질문이 쌓인다. 젠킨스 주소가 밖에서 열려 있다면 웹훅이 낫다. 순서만 적어 둔다(내 PC 의 localhost 는 GitHub 가 찾아올 수 없어 이 실습에서는 안 된다).

  1. 젠킨스: GitHub 플러그인이 있는지 확인(추천 플러그인에 보통 같이 깔린다). 잡 Triggers 에서 GitHub hook trigger for GITScm polling 체크
  2. GitHub 저장소: Settings → Webhooks → Add webhook
  3. Payload URL: https://jenkins.회사.com/github-webhook/ (끝의 / 까지), Content type: application/json, 이벤트: Just the push event
  4. 저장 후 Recent Deliveries 에 초록 체크가 뜨면 연결된 것

내 PC 의 젠킨스로 웹훅을 꼭 받아 보고 싶다면 smee.io·ngrok 같은 "터널" 서비스로 바깥 주소를 잠깐 빌리는 방법이 있다. 다만 내 젠킨스를 인터넷에 여는 일이니, 7-1 의 보안 설정을 확인한 뒤에만 쓴다.

웹훅(webhook) — "일이 생기면 이 주소로 알려 줘"라고 등록해 두는 방식. 내가 계속 묻는 폴링과 반대로, 상대가 먼저 알려 준다.
/github-webhook/ — GitHub 플러그인이 웹훅을 받으려고 젠킨스에 열어 두는 주소.

7. 왜 nohup 이 아니라 systemd 인가

처음 배포 스크립트를 짜면 흔히 이렇게 쓴다. nohup python app.py & — 앱을 뒤에 띄워 두고 빌드를 끝내는 방식이다. 젠킨스에서는 빌드가 끝나는 순간 앱이 같이 죽는다.

젠킨스에는 ProcessTreeKiller 라는 장치가 있다. 빌드가 끝나면 그 빌드가 띄운 프로세스를 전부 찾아 정리한다. 빌드가 남긴 찌꺼기 프로세스가 서버에 쌓이는 걸 막으려는 것이다. 빌드에서 띄운 프로세스에는 젠킨스가 표시(BUILD_ID·JENKINS_NODE_COOKIE 환경 변수)를 달아 두기 때문에, 뒤로 숨겨도 찾아낸다.

systemd 로 띄우면 앱은 빌드의 자식이 아니라 systemd 의 자식이다. 빌드는 "다시 띄워 줘"라고 부탁만 하고 끝난다. 덤으로 죽으면 다시 살리기, 서버 재부팅 때 자동 시작, journalctl -u cicd-hello 로 로그 보기가 따라온다. 표시 변수를 바꿔서 정리를 피하는 요령도 인터넷에 돌지만, 그건 문제를 숨기는 것이다. 서버에서 계속 돌아야 하는 건 서비스로 등록한다.

프로세스(process) — 실행 중인 프로그램 하나. 프로세스가 띄운 프로세스를 자식이라 부르고, 부모-자식이 나무 모양(process tree)을 이룬다.
nohup … & — 터미널을 닫아도 안 죽게(nohup) 뒤에서(&) 실행. 터미널에는 통하지만 젠킨스의 정리 장치는 못 피한다.

8. 빌드 파라미터 — 돌릴 때 값 받기

가끔은 "테스트만 돌리고 배포는 하지 마"가 필요하다. 잡에 파라미터를 달면 돌릴 때마다 값을 고를 수 있다.

  1. Configure → General → This project is parameterized → Add Parameter → Boolean Parameter
  2. Name: DEPLOY, Default: 체크(true), Description: 테스트 통과 후 배포할지
  3. 배포 칸 맨 위에 두 줄 추가:
if [ "$DEPLOY" != "true" ]; then echo "DEPLOY=false → 배포 건너뜀"; exit 0; fi

저장하면 Build Now 가 Build with Parameters 로 바뀐다. 체크를 끄고 돌리면 테스트만 하고 끝난다. 폴링으로 저절로 돈 빌드는 기본값(true)을 쓴다. 파라미터 값은 셸에서 같은 이름의 환경 변수로 들어온다. 종류는 Boolean 말고도 String(글자), Choice(목록에서 고르기) 등이 있다.

Freestyle 의 한계 — 다음 글로

잘 돌지만 불편한 점이 보인다. 설정이 젠킨스 화면 안에만 있어서 누가 언제 무엇을 바꿨는지 기록이 없다. 같은 잡을 다른 저장소에 쓰려면 화면을 다시 하나하나 채워야 한다. 젠킨스 서버가 날아가면 설정도 같이 사라진다. 단계가 늘어나면 "어디까지 돌았나"를 콘솔 한 줄 한 줄로 찾아야 한다. 다음 글에서 이 설정 전체를 Jenkinsfile 이라는 코드 파일로 옮겨 저장소에 같이 넣는다.

다음 단계로 가기 전 정리

  • cicd-hello 서비스(8000)와 이 잡은 그대로 둔다. 다음 글의 파이프라인이 같은 자리에 배포한다.
  • 다만 이 잡의 Poll SCM 은 꺼 둔다(Configure → Triggers 체크 해제). 다음 글의 파이프라인도 같은 저장소를 지켜보게 되는데, 둘 다 켜 두면 커밋 한 번에 배포가 두 번 일어난다.
