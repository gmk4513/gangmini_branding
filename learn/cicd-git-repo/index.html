버전 관리와 Git
— 실습 앱 저장소 만들고 관리하기

실습 Git GitHub SVN 태그 PAT 2026.11.10

CI/CD 파이프라인은 전부 Git 저장소에서 출발한다. 젠킨스는 저장소에서 코드를 받아 빌드하고, ArgoCD 는 저장소에 적힌 대로 배포한다. "커밋 하나가 운영까지 간다"는 말의 커밋이 여기서 생긴다. 그래서 파이프라인보다 먼저 저장소를 제대로 만든다.

이 글에서는 버전 관리 도구가 어떻게 바뀌어 왔는지 짧게 보고, 시리즈 내내 쓸 실습 앱 cicd-hello 를 직접 만들어 테스트한 뒤 GitHub 에 올린다. Git 명령 하나하나는 Git 첫걸음에 자세히 있으니, 여기서는 CI/CD 에 필요한 만큼만 쓴다.

이번 단계에서 할 것

  • 실습 앱 파일 8개 만들기 → 가상환경에서 pytest, 도커로 테스트·실행
  • Git 저장소로 만들고 GitHub 공개 저장소 cicd-hello 에 올리기
  • README, 태그 v0.1.0, main 보호 규칙(Ruleset), 브랜치 → PR → 합치기 한 바퀴
  • 젠킨스가 쓸 GitHub 토큰(fine-grained PAT) 만들기

끝나면: https://github.com/<내아이디>/cicd-hello 에 앱 파일과 태그 v0.1.0 이 있고, main 에 직접 push 하면 거절된다. 토큰 하나를 안전한 곳에 적어 두었다.

버전 관리 도구는 어떻게 바뀌었나

보고서_최종.hwp, 보고서_최종_진짜.hwp, 보고서_최종_진짜_수정.hwp. 파일 이름으로 버전을 관리하면 이렇게 된다. 무엇이 바뀌었는지, 누가 바꿨는지, 어제 걸로 돌아가려면 어느 파일인지 모른다. 버전 관리 시스템(VCS)은 이걸 도구가 대신 기록하게 한다.

중앙집중형 (SVN)분산형 (Git)
기록이 있는 곳중앙 서버 한 곳모든 사람의 컴퓨터 + GitHub
커밋서버에 바로 올라간다 (네트워크 필수)내 컴퓨터에 먼저 쌓고, 나중에 push
브랜치폴더를 통째로 복사하는 방식이라 무겁다이름표 하나 붙이는 것이라 가볍다. 하루에도 여러 개 만든다
권한 관리폴더별로 세밀하게 막기 쉽다저장소 단위. 대신 PR·보호 규칙으로 관리
지금오래된 회사·게임 회사(큰 바이너리 파일) 일부에 남아 있다사실상 표준. GitHub·GitLab·Bitbucket 이 모두 Git

CI/CD 와 Git 이 잘 맞는 이유는 브랜치가 가볍기 때문이다. 기능마다 브랜치를 따고, PR 을 올리면 CI 가 그 브랜치를 검사하고, 합치면 CD 가 배포한다. 이 흐름 전체가 "브랜치를 싸게 만들 수 있다"는 전제 위에 있다.

버전 관리 시스템(VCS, Version Control System) — 파일이 언제·누가·왜 바뀌었는지 기록하고, 아무 때로나 되돌아갈 수 있게 해 주는 도구.
SVN (Subversion) — 2000년대에 많이 쓴 중앙집중형 버전 관리 도구. 커밋할 때마다 중앙 서버에 바로 올린다.
브랜치(branch) — 기록의 갈래. main 은 그대로 두고 옆 갈래에서 새 기능을 만들다가, 다 되면 합친다(merge).

Git 은 세 칸 + 원격 하나

스테이징(staging area) — 다음 커밋에 넣을 변경을 골라 두는 대기실. git add 로 올린다.
원격(remote) · origin — 내 저장소와 짝을 이루는 다른 곳의 저장소. 보통 GitHub 이고, 기본 이름이 origin.
clone — 원격 저장소를 통째로(전체 기록까지) 내 컴퓨터로 복사하는 것. 젠킨스도 빌드할 때마다 이걸(또는 fetch 를) 한다.

1. 실습 앱 파일 만들기

시리즈 내내 쓰는 앱이다. 주소 / 를 부르면 버전을 붙여 인사하고, /health 는 살아 있는지 알려 준다. 버전은 환경 변수 APP_VERSION 에서 읽는다. 나중에 젠킨스가 여기에 빌드 번호를 넣어서, 화면만 보고 "몇 번째 빌드가 배포됐나"를 알 수 있게 한다.

우분투 터미널에서 폴더를 만들고 들어간다.

mkdir -p ~/cicd/cicd-hello
cd ~/cicd/cicd-hello

파일은 아래 명령을 블록째 복사해 붙여 넣으면 만들어진다. cat > 파일 <<'EOF' 부터 EOF 까지가 파일 내용이다. VS Code 가 편하면 code . 으로 폴더를 열고 같은 이름의 파일을 만들어 내용을 붙여 넣어도 된다.

히어독(heredoc) — cat > app.py <<'EOF' … EOF 는 "EOF 라는 줄이 나올 때까지의 글을 app.py 에 써라"라는 셸 문법. 편집기 없이 터미널만으로 파일을 만들 때 쓴다. 'EOF' 처럼 따옴표로 감싸면 안의 $ 같은 글자를 셸이 건드리지 않는다.

app.py — 앱 본체

cat > app.py <<'EOF'
import os
from flask import Flask, jsonify

app = Flask(__name__)
VERSION = os.getenv("APP_VERSION", "dev")


@app.get("/")
def index():
    return f"Hello, CI/CD! version={VERSION}\n"


@app.get("/health")
def health():
    return jsonify(status="ok", version=VERSION)


if __name__ == "__main__":
    app.run(host="0.0.0.0", port=8000)
EOF
  • os.getenv("APP_VERSION", "dev") — 환경 변수가 없으면 dev. 내 컴퓨터에서 그냥 돌리면 version=dev 로 보인다.
  • host="0.0.0.0" — 이 컴퓨터의 모든 네트워크 입구에서 받는다. 127.0.0.1(기본값)로 두면 컨테이너 밖에서 접속이 안 된다. 도커에서 자주 걸리는 함정이라 처음부터 이렇게 둔다.
  • port=8000 — 앱은 언제나 8000 번에서 받는다. 밖에서 몇 번으로 열지는 배포 방식마다 정한다.

test_app.py — 자동 테스트 두 개

cat > test_app.py <<'EOF'
from app import app


def test_index():
    res = app.test_client().get("/")
    assert res.status_code == 200
    assert b"Hello, CI/CD!" in res.data


def test_health():
    res = app.test_client().get("/health")
    assert res.get_json()["status"] == "ok"
EOF

서버를 띄우지 않고 Flask 의 test_client() 로 요청을 흉내 낸다. 파이프라인의 "테스트" 단계가 돌리는 게 이 파일이다. 이 두 줄짜리 확인이 있어야 "인사말을 실수로 지운 커밋"이 운영에 나가기 전에 멈춘다.

requirements.txt · requirements-dev.txt — 필요한 패키지

cat > requirements.txt <<'EOF'
flask==3.1.2
EOF

cat > requirements-dev.txt <<'EOF'
-r requirements.txt
pytest==8.4.2
EOF

운영에 필요한 것(flask)과 개발·테스트에만 필요한 것(pytest)을 나눈다. 운영 이미지에 테스트 도구를 넣지 않으려는 것이다. -r requirements.txt 는 "저 파일 내용도 같이 설치"라는 뜻. 버전을 == 로 박아 두어야 오늘 빌드와 한 달 뒤 빌드가 같은 패키지를 쓴다.

Dockerfile — 이미지 만드는 순서

cat > Dockerfile <<'EOF'
# 1) 공통 바탕: 파이썬 + 앱 실행에 필요한 패키지
FROM python:3.12-slim AS base
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY app.py .

# 2) 테스트 단계: 테스트 도구를 더 깔고 pytest 를 돌린다. 실패하면 빌드가 멈춘다
FROM base AS test
COPY requirements-dev.txt test_app.py ./
RUN pip install --no-cache-dir -r requirements-dev.txt && python -m pytest -q

# 3) 최종 이미지: 테스트 도구 없이 앱만
FROM base AS final
ARG APP_VERSION=dev
ENV APP_VERSION=${APP_VERSION}
EXPOSE 8000
CMD ["python", "app.py"]
EOF

FROM ... AS 이름 이 세 번 나오는 멀티 스테이지 Dockerfile 이다. 테스트 단계는 base 위에 pytest 를 깔고 테스트를 돌린다. 최종 단계는 base 에서 바로 갈라져 나오므로 pytest 가 들어가지 않는다. 지금은 "이런 파일이 있다" 정도로 보고, 자세한 건 7~9편에서 다룬다.

Dockerfile — 이미지를 만드는 요리법. 한 줄이 한 단계다. FROM(무엇에서 시작), COPY(파일 넣기), RUN(명령 실행), CMD(컨테이너가 켜질 때 실행할 것).
멀티 스테이지 빌드 — Dockerfile 하나에 여러 단계(FROM ... AS)를 두고, 필요한 단계 결과만 최종 이미지에 남기는 방식. 테스트 도구나 컴파일러를 최종 이미지에서 빼서 작고 안전하게 만든다.
ARG / ENV — ARG 는 빌드할 때만 쓰는 값(--build-arg 로 넘김), ENV 는 컨테이너 안에서 계속 보이는 환경 변수. 여기선 빌드 때 받은 버전을 환경 변수로 옮긴다.

.dockerignore · .gitignore — 넣지 말 것

cat > .dockerignore <<'EOF'
.git
__pycache__
.pytest_cache
venv
EOF

cat > .gitignore <<'EOF'
venv/
__pycache__/
.pytest_cache/
EOF
  • .gitignore — Git 이 무시할 것. 가상환경(venv/)은 수천 개 파일이고 컴퓨터마다 다르니 저장소에 넣지 않는다. 대신 requirements.txt 를 넣어 누구든 같은 걸 설치하게 한다.
  • .dockerignore — 이미지를 만들 때 도커에게 넘기지 않을 것. .git 폴더까지 넘기면 빌드가 느려진다.
ls -A
.dockerignore  .gitignore  Dockerfile  app.py  requirements-dev.txt  requirements.txt  test_app.py

Jenkinsfile 은 6편에서 더한다. 지금은 7개면 된다.

2. 내 컴퓨터에서 테스트하고 띄워 보기

파이프라인에 맡기기 전에 사람이 한 번 돌려 본다. 파이프라인은 사람이 하던 일을 그대로 옮기는 것이라, 손으로 안 되는 건 자동으로도 안 된다. 프로젝트 전용 가상환경을 만들고 그 안에 설치한다. 

python3 -m venv venv
source venv/bin/activate
pip install -r requirements-dev.txt
python -m pytest -q
..                                                                       [100%]
2 passed in 0.10s

(우분투 24.04 컨테이너에서 이 글의 명령 그대로 돌려 나온 출력이다. 이 뒤의 curl 결과도 같다.) 점 두 개가 테스트 두 개다. 2 passed 면 성공. 프롬프트 앞에 (venv) 가 붙어 있으면 가상환경이 켜진 것이다. python3 -m venv 에서 ensurepip is not available 이 나오면 sudo apt install -y python3-venv 를 하고 다시 한다(2편에서 깔았다면 괜찮다).

앱을 띄우고, 우분투 터미널을 하나 더 열어서 불러 본다.

# 첫 번째 터미널
APP_VERSION=local python app.py

# 두 번째 터미널
curl localhost:8000/
curl localhost:8000/health
Hello, CI/CD! version=local
{"status":"ok","version":"local"}

윈도우 브라우저에서 http://localhost:8000 을 열어도 같은 글이 보인다. 확인했으면 첫 번째 터미널에서 Ctrl+C 로 끄고 deactivate 로 가상환경을 나온다.

가상환경(venv) — 프로젝트 폴더 안에 만든 그 프로젝트 전용 파이썬 + 패키지 묶음. source venv/bin/activate 로 켜면 python·pip 가 그걸 가리킨다. 우분투 24.04 는 시스템 파이썬에 pip install 을 막아 두어서(externally-managed 에러) 가상환경이 사실상 필수다.
환경 변수 — 프로그램 밖에서 넣어 주는 설정 값. APP_VERSION=local python app.py 처럼 명령 앞에 쓰면 그 명령에만 적용된다.
curl — 터미널에서 주소를 불러 응답을 찍어 주는 도구. 브라우저의 아주 단순한 버전.

3. 도커로도 확인

나중에 파이프라인이 할 일을 미리 손으로 해 본다. 먼저 테스트 단계까지만 만든다.

docker build --target test -t cicd-hello:test .
...
#11 8.623 2 passed in 0.08s
...

로그 중간에 2 passed 가 보이면 이미지 안에서도 테스트가 통과한 것이다. 이제 최종 이미지를 만들고 띄운다. --build-arg 로 버전을 넘긴다. 

docker build --build-arg APP_VERSION=0.1.0 -t cicd-hello:0.1.0 .
docker run -d --name hello-try -p 8000:8000 cicd-hello:0.1.0
curl localhost:8000/
curl localhost:8000/health
Hello, CI/CD! version=0.1.0
{"status":"ok","version":"0.1.0"}

(위 두 출력은 같은 Dockerfile 로 실제로 빌드·실행해서 나온 것이다. 버전 값만 이 글에 맞게 바꿔 적었다.) 확인했으면 지운다. 8000 번은 5편에서 다시 쓴다. 

docker rm -f hello-try
  • -t cicd-hello:0.1.0 — 이미지에 이름(cicd-hello)과 태그(0.1.0)를 붙인다.
  • -p 8000:8000 — "내 컴퓨터의 8000 번으로 오는 걸 컨테이너의 8000 번으로". 앞이 바깥, 뒤가 안쪽이다.
  • 주의: docker build . 만 하면 테스트 단계는 건너뛴다. 요즘 도커의 빌드 엔진(BuildKit)은 최종 단계에 필요 없는 단계를 아예 실행하지 않기 때문이다. 그래서 파이프라인에서는 --target test 를 먼저 따로 돌린다.

태그(이미지) — 이미지 이름 뒤 : 다음에 붙는 버전 이름. 안 붙이면 latest. 9편부터는 빌드번호-커밋해시(예: 12-a1b2c3d)를 붙여 어느 커밋으로 만든 이미지인지 알 수 있게 한다.
포트 매핑(-p) — 컨테이너는 자기만의 네트워크를 가져서, 밖에서 들어오려면 "바깥 번호:안쪽 번호" 로 문을 이어 줘야 한다.
BuildKit — 도커의 현재 기본 빌드 엔진. 필요한 단계만, 가능하면 동시에 빌드한다.

venv/ 와 __pycache__/ 가 목록에 없다. .gitignore 가 일한 것이다. 만약 venv/ 가 보이면 .gitignore 철자를 확인한다. 이제 담아서 기록한다. 

git add .
git commit -m "cicd-hello: 인사·헬스 체크 API, 테스트, Dockerfile"
git log --oneline
[main (root-commit) 3f2c1ab] cicd-hello: 인사·헬스 체크 API, 테스트, Dockerfile
 7 files changed, 59 insertions(+)
...

(해시 3f2c1ab 는 사람마다 다르다.) 커밋 메시지는 "무엇을 왜"가 보이게 쓴다. 나중에 젠킨스 빌드 화면에 이 메시지가 그대로 뜬다.

5. GitHub 에 올리기

2편에서 로그인해 둔 gh 로, 지금 폴더를 공개 저장소로 만들고 바로 올린다.

gh repo create cicd-hello --public --source . --push
✓ Created repository <내아이디>/cicd-hello on GitHub
  https://github.com/<내아이디>/cicd-hello
✓ Added remote https://github.com/<내아이디>/cicd-hello.git
✓ Pushed commits to https://github.com/<내아이디>/cicd-hello.git
  • --public — 공개 저장소. 젠킨스·ArgoCD 가 비밀번호 없이 받아 갈 수 있어 실습이 단순해진다. 회사 코드는 당연히 비공개(--private)이고, 그때는 받아 갈 때도 토큰이 필요하다.
  • --source . — 지금 폴더를 그 저장소로 연결, --push — 바로 올리기.
  • gh 없이 하려면: github.com 에서 New repository → 이름 cicd-hello, Public, README 추가 안 함 → 화면에 나오는 git remote add origin ... 과 git push -u origin main 두 줄을 친다.

브라우저에서 https://github.com/<내아이디>/cicd-hello 를 열어 파일 7개가 보이면 된다.

6. README 하나

저장소 첫 화면에 보이는 설명서다. 남(그리고 한 달 뒤의 나)이 이 저장소가 뭔지, 어떻게 돌리는지 알 수 있게.

cat > README.md <<'EOF'
# cicd-hello

CI/CD 실습용 작은 Flask 앱.

- `GET /` → `Hello, CI/CD! version=<APP_VERSION>`
- `GET /health` → `{"status": "ok", "version": "..."}`

## 로컬에서 돌리기

    python3 -m venv venv && source venv/bin/activate
    pip install -r requirements-dev.txt
    python -m pytest -q
    APP_VERSION=local python app.py   # http://localhost:8000

## 도커

    docker build --target test .                       # 테스트
    docker build --build-arg APP_VERSION=1 -t cicd-hello .
    docker run -p 8000:8000 cicd-hello
EOF

git add README.md
git commit -m "README: 돌리는 법"
git push

7. 태그 v0.1.0 — "이 커밋이 첫 릴리스"

커밋 해시는 기계용 이름이라 외울 수 없다. 태그는 특정 커밋에 사람이 읽는 이름을 붙인다. 회사에서는 "운영에 나간 버전"마다 붙여 둔다. 나중에 "v0.1.0 때 코드 좀 보자"가 한 줄로 된다. 

git tag -a v0.1.0 -m "첫 릴리스: 인사·헬스 체크"
git push origin v0.1.0
git tag -n
v0.1.0          첫 릴리스: 인사·헬스 체크

git push 만으로는 태그가 올라가지 않는다. 태그는 따로 push 한다. GitHub 저장소 화면 오른쪽의 Releases / Tags 에 v0.1.0 이 보이면 된다.

Git 태그 — 커밋 하나에 붙이는 움직이지 않는 이름표. 브랜치는 새 커밋을 따라 움직이지만 태그는 그 자리에 고정된다. -a 를 붙이면 만든 사람·날짜·메시지가 함께 남는 "주석 태그"가 된다.
시맨틱 버저닝(SemVer) — 주.부.수(예: 1.4.2) 규칙. 호환이 깨지면 주 번호, 기능 추가는 부 번호, 버그 수정은 수 번호를 올린다. 0.x 는 "아직 정식 전"이라는 뜻.

8. 저장소 관리 — main 을 보호하기

CI/CD 를 붙이면 main 에 들어간 것 = 곧 배포되는 것이 된다. 그래서 main 에는 아무나, 아무렇게나 못 넣게 막는다. GitHub 의 Ruleset 으로 규칙을 건다.

  1. 저장소 → Settings → Rules → Rulesets → New ruleset → New branch ruleset
  2. Ruleset Name: protect-main, Enforcement status: Active
  3. Target branches → Add target → Include default branch (main)
  4. Rules 에서 켤 것:
    • Restrict deletions — main 브랜치 삭제 금지 (기본 켜짐)
    • Block force pushes — 기록 덮어쓰기 금지 (기본 켜짐)
    • Require a pull request before merging — main 에 직접 push 금지, PR 로만. 혼자 실습이니 Required approvals 는 0
  5. Create

막혔는지 확인한다. main 에서 바로 커밋해 push 해 본다.

echo "" >> README.md
git commit -am "main 직접 push 시험"
git push
remote: error: GH013: Repository rule violations found for refs/heads/main.
remote: - Changes must be made through a pull request.
 ! [remote rejected] main -> main (push declined due to repository rule violations)

대략 이런 거절이 나오면 규칙이 일한 것이다. 시험한 커밋은 되돌려 둔다.

git reset --hard origin/main

나중에 6편에서 PR 마다 젠킨스 검사를 돌리게 되면, 이 Ruleset 에 Require status checks to pass 를 더해 "검사가 초록이어야만 합칠 수 있게" 할 수 있다. (공개 저장소에서는 무료로 된다. 비공개 저장소는 무료 플랜에서 Ruleset 이 제한될 수 있다.)

Ruleset (브랜치 보호 규칙) — 특정 브랜치에 "PR 없이 못 넣음", "강제 push 금지" 같은 규칙을 거는 GitHub 기능. 예전 이름은 Branch protection rules 이고 지금도 같이 있다.
force push — git push --force. 원격의 기록을 내 것으로 덮어쓴다. 남의 커밋이 사라질 수 있어 main 에는 막아 둔다.
git reset --hard origin/main — 내 브랜치를 GitHub 의 main 과 똑같이 맞추고, push 안 한 커밋과 고친 내용을 버린다. 되돌릴 수 없으니 버려도 되는 것만 있을 때 쓴다.

9. 브랜치 → PR → 합치기, 한 바퀴

이제 main 에 넣는 길은 PR 하나다. 회사에서 하루에도 몇 번씩 도는 흐름을 짧게 한 번 해 본다. 자세한 설명은 브랜치와 Pull Request에 있다. 

git switch -c docs/health-example
cat >> README.md <<'EOF'

## 확인

    curl localhost:8000/health
EOF
git commit -am "README: 헬스 체크 확인 예시"
git push -u origin docs/health-example

gh pr create --fill            # 커밋 메시지로 PR 제목·본문 채우기
gh pr merge --squash --delete-branch

git switch main
git pull
  • git switch -c 이름 — 새 브랜치를 만들고 그리로 옮긴다. 이름은 종류/내용 으로 짓는 게 흔하다(feature/, fix/, docs/).
  • gh pr merge --squash — PR 의 커밋들을 하나로 합쳐 main 에 넣는다. --delete-branch 는 다 쓴 브랜치를 지운다.
  • 웹에서 해도 같다: push 후 저장소 화면의 Compare & pull request → Create pull request → Squash and merge.

git log --oneline 에 커밋이 세 개(앱, README, 헬스 체크 예시) 보이면 된다.

PR (Pull Request) — "내 브랜치를 main 에 합쳐 주세요"라는 요청. 변경 내용(diff)을 보여 주고, 리뷰와 자동 검사(CI)가 여기에 붙는다.
squash merge — 브랜치의 커밋 여러 개를 하나로 눌러 담아 합치는 방식. main 의 기록이 "PR 하나 = 커밋 하나"로 깔끔해진다.

10. 젠킨스가 쓸 토큰 만들기 (fine-grained PAT)

공개 저장소는 받아 가는 데 인증이 필요 없다. 하지만 13편에서 젠킨스가 매니페스트 저장소에 push 를 하고, 회사에서는 저장소가 비공개라 받는 데도 인증이 필요하다. 이때 내 GitHub 비밀번호를 줄 수는 없으니 권한을 좁힌 토큰을 만든다. 원칙은 필요한 저장소에만, 필요한 권한만, 기한을 정해서.

  1. GitHub 오른쪽 위 프로필 → Settings → Developer settings → Personal access tokens → Fine-grained tokens → Generate new token
  2. Token name: jenkins-cicd, Expiration: 실습 기간에 맞게(예: 30일 또는 90일)
  3. Repository access: Only select repositories → cicd-hello 를 고른다
    (cicd-hello-manifests 는 12편에서 만든다. 만든 뒤 이 토큰을 Edit 해서 저장소를 하나 더 고르면 된다. 토큰 값은 그대로다.)
  4. Permissions → Repository permissions → Contents: Read and write (Metadata: Read-only 는 저절로 붙는다). 다른 건 건드리지 않는다.
  5. Generate token → github_pat_... 로 시작하는 값이 한 번만 보인다. 복사해서 안전한 곳에 적어 둔다.

토큰으로 저장소에 접근되는지만 확인한다. 명령에 토큰을 바로 쓰면 셸 기록(history)에 남으니, 화면에 안 보이게 입력받아 쓴다.

read -s -p "토큰 붙여 넣기: " TOKEN; echo
git ls-remote https://<내아이디>:$TOKEN@github.com/<내아이디>/cicd-hello.git | head -3
unset TOKEN
8d1e4f0...        HEAD
8d1e4f0...        refs/heads/main
5b7c2a9...        refs/tags/v0.1.0

목록이 나오면 된다. 이 토큰은 젠킨스에 github-token 이라는 이름의 자격 증명으로 넣는다(4편 이후). 토큰을 코드·Jenkinsfile·채팅에 붙여 넣지 않는다. 새어 나갔다고 생각되면 같은 화면에서 바로 Delete 하고 새로 만든다.

PAT (Personal Access Token) — GitHub 비밀번호 대신 프로그램에 주는 토큰. classic 토큰은 내 모든 저장소에 권한이 가서 위험하고, fine-grained 토큰은 저장소와 권한을 하나씩 고를 수 있다. 새로 만들 땐 fine-grained 를 쓴다.
최소 권한 원칙 — 프로그램에는 일하는 데 꼭 필요한 권한만 준다. 토큰이 새도 피해가 그 범위 안에서 끝난다.
git ls-remote — 원격 저장소의 브랜치·태그 목록만 묻는 명령. 받지 않고 접속·인증만 확인할 때 쓴다.

정리 — 지금 있는 것

~/cicd/cicd-hello/          ↔  github.com/<내아이디>/cicd-hello (공개)
├── app.py                     main: 커밋 3개, 태그 v0.1.0
├── test_app.py                Ruleset: PR 로만 main 에
├── requirements.txt
├── requirements-dev.txt    토큰: jenkins-cicd (Contents read/write, cicd-hello 만)
├── Dockerfile
├── .dockerignore
├── .gitignore
├── README.md
└── venv/  ← Git 에는 안 올라감

다음 편부터는 이 저장소를 사람 대신 젠킨스가 받아서 테스트하고 배포한다. 도커로 띄웠던 hello-try 컨테이너는 지웠는지 확인한다(docker ps 에 없어야 한다). 이미지 cicd-hello:test, cicd-hello:0.1.0 은 남겨 둬도 된다.

용어 정리

버전 관리 시스템(VCS) — 파일 변경의 기록과 되돌리기를 맡는 도구. 중앙집중형(SVN)과 분산형(Git)이 있다.
저장소 · 커밋 · 브랜치 · 태그 — 기록을 쌓는 곳 · 기록 하나 · 기록의 갈래 · 커밋에 붙인 고정 이름표.
원격(origin) — GitHub 쪽 저장소. 파이프라인의 기준.
가상환경(venv) — 프로젝트 전용 파이썬 패키지 묶음. 저장소엔 안 올리고 requirements.txt 만 올린다.
멀티 스테이지 Dockerfile — 테스트 단계와 최종 단계를 한 파일에 나눠 둔 요리법.
Ruleset — main 같은 브랜치에 거는 GitHub 보호 규칙.
PR — 브랜치를 합쳐 달라는 요청. 리뷰와 CI 가 붙는 자리.
fine-grained PAT — 저장소·권한·기한을 좁힌 GitHub 토큰. 젠킨스에 준다.
