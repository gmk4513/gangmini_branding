ES 모듈과 클래식 스크립트
— type="module" 한 줄의 차이

이론 JavaScript 브라우저 CORS import map 2026.10.15

범퍼카 2026을 만들면서, 게임 파일을 더블클릭하면 안 열리고 작은 서버를 띄워야만 열리는 일을 겪었다. 이유는 게임 코드가 ES 모듈이라서였다. 그 전에 만든 비프리 게임은 클래식 스크립트라 더블클릭으로도 열렸다. 같은 자바스크립트인데 무엇이 다른지 정리한다.

한 줄로 줄이면 이렇다. 클래식 스크립트는 모든 파일이 방 하나를 같이 쓰고, ES 모듈은 파일마다 자기 방이 있고 필요한 것만 문으로 주고받는다.

먼저, 자바스크립트

자바스크립트(JavaScript, JS)는 웹페이지를 움직이게 하는 프로그래밍 언어다. 웹페이지는 보통 세 가지로 만든다. HTML 이 뼈대, CSS 가 모양, 자바스크립트가 동작이다.

가장 작은 예는 이렇다. 버튼을 누르면 글자가 바뀐다. 

<button id="b">눌러 보기</button>
<script>
  document.getElementById("b").addEventListener("click", () => {
    document.getElementById("b").textContent = "눌렀다!";
  });
</script>

HTML 이 만든 버튼을 자바스크립트가 찾아서(getElementById), "눌리면 이걸 해라"를 걸어 두고(addEventListener), 글자를 바꾼다. 범퍼카도 결국 이걸 아주 많이 한 것이다. 화면 대신 캔버스에 그리고, 클릭 대신 방향키를 받을 뿐이다.

어디서 돌아가나 — 엔진

자바스크립트는 미리 기계어로 바꿔 두지 않는다. 글자 그대로의 코드 파일을 보내면, 받는 쪽의 엔진이 읽으면서 실행한다. 그래서 빌드 없이 파일만 올려도 돌아간다. 처음엔 브라우저 안에서만 돌았지만, 지금은 엔진만 있으면 어디서든 돈다.

알아 두면 덜 헷갈리는 것

  • 자바(Java)와는 관계없다. 1995년 넷스케이프 브라우저에 넣으려고 만들었고, 당시 인기 있던 자바의 이름을 빌렸을 뿐 전혀 다른 언어다.
  • 표준 이름은 ECMAScript 다. 언어 규칙은 ECMA 라는 표준 단체가 정하고, 해마다 새 판이 나온다. 그중 2015년 판(ES2015, ES6 라고도 부른다)이 가장 크게 바뀐 판이고, 이 글의 주제인 import / export도 그때 들어왔다.
  • 변수에 타입을 적지 않는다. 같은 변수에 숫자를 넣었다가 글자를 넣어도 된다. 편하지만 실수를 늦게 발견한다. 그래서 실무에서는 타입을 적는 TypeScript로 쓰고 자바스크립트로 바꿔서 내보내는 경우가 많다.

엔진 — 자바스크립트 코드를 읽고 실행하는 프로그램. 크롬·엣지·Node.js 는 V8, 사파리는 JavaScriptCore, 파이어폭스는 SpiderMonkey 를 쓴다.
DOM — 브라우저가 HTML 을 읽어 만든 "화면 요소들의 나무". 자바스크립트는 이 나무를 통해 버튼을 찾고 글자를 바꾼다.
TypeScript — 자바스크립트에 타입 표시를 더한 언어. 브라우저는 못 읽어서, 실행 전에 자바스크립트로 바꾼다.

자바스크립트 코드가 길어지면 파일을 여러 개로 나누게 된다. 나눈 파일들을 브라우저에 어떻게 불러오느냐가 이 글의 주제다. 방법이 두 가지 있고, 그 차이가 "더블클릭으로 열리느냐"까지 갈린다.

두 방식을 코드로

클래식 스크립트 — <script src>

<!-- 비프리 게임 index.html -->
<script src="js/leaderboard.js"></script>   <!-- Leaderboard 를 만든다 -->
<script src="js/game.js"></script>          <!-- Leaderboard 를 그냥 쓴다 -->

game.js는 Leaderboard가 어디서 왔는지 적지 않는다. 앞 파일이 전역 공간에 올려 둔 걸 그냥 쓴다. 그래서 두 줄의 순서가 바뀌면 깨진다. game.js가 먼저 돌면 아직 Leaderboard가 없다.

ES 모듈 — <script type="module">

<!-- 범퍼카 index.html -->
<script type="module" src="js/main.js"></script>

// js/main.js
import * as THREE from "../vendor/three.module.min.js";
import { GLTFLoader } from "../vendor/addons/loaders/GLTFLoader.js";

// GLTFLoader.js 안쪽 (요약)
import { Loader, FileLoader, ... } from "three";
export { GLTFLoader };

HTML 에는 시작 파일 하나만 적는다. 나머지는 main.js가 import로 "이 파일의 이것이 필요하다"고 적어 두면, 브라우저가 그걸 따라가며 받아 온다. 다른 파일이 쓸 수 있는 건 export로 내보낸 것뿐이다.

ES 모듈 (ESM) — ECMAScript(자바스크립트의 표준 이름) 2015 판에 들어온 공식 모듈 문법. import / export를 쓴다.
클래식 스크립트 (classic script) — HTML 표준이 type="module"이 없는 보통 <script>를 부르는 이름. 모듈이 생기기 전부터 있던 방식이다.

왜 더블클릭으로는 안 열리나

파일을 더블클릭하면 주소가 file:///C:/.../index.html이 된다. 이 상태에서 모듈을 부르면 크롬은 콘솔에 이렇게 남기고 멈춘다. 

Access to script at 'file:///C:/.../js/main.js' from origin 'null'
has been blocked by CORS policy

모듈은 처음부터 다른 사이트의 코드도 import 할 수 있는 구조로 설계됐다. 그래서 브라우저는 모듈을 받을 때마다 "이 페이지가 이 파일을 가져가도 되나"를 확인하는 절차(CORS)를 거친다. 확인하려면 페이지가 어디서 왔는지(출처)를 알아야 하는데, file://로 연 페이지는 출처가 null이다. 확인해 줄 서버도 없다. 그래서 막는다.

클래식 스크립트는 모듈보다 훨씬 오래된 방식이라 이 확인을 하지 않는다. 그래서 더블클릭으로도 열린다.

출처(origin) — 주소의 프로토콜 + 도메인 + 포트 묶음. https://gangmini.com과 https://bamti-bomb.fly.dev는 출처가 다르다.
CORS — 출처가 다른 곳의 자원을 쓸 때 브라우저가 서버에게 허락을 묻는 규칙. 같은 출처끼리는 묻지 않는다.

이름만 쓰는 import 와 import map

위의 GLTFLoader.js는 from "three"처럼 경로 없이 이름만 쓴다. 브라우저는 이걸 그대로는 못 찾는다. 어느 파일인지 알려 주는 게 import map이다. 범퍼카 index.html에 이 한 줄이 있다. 

<script type="importmap">
  { "imports": { "three": "./vendor/three.module.min.js" } }
</script>

번들러를 쓰는 프로젝트에서는 번들러가 node_modules에서 알아서 찾아 주기 때문에 이 지도가 필요 없다. 빌드 없이 브라우저에서 바로 모듈을 쓰려면 이게 그 역할을 대신한다.

bare specifier — "three", "react"처럼 ./나 주소 없이 이름만 쓴 import 경로. 브라우저 혼자서는 해석하지 못한다.

실무에서는 어디에 쓰이나

요즘 프론트엔드 코드는 거의 다 import / export로 쓴다. 다만 그걸 브라우저가 그대로 받는 경우는 드물고, 보통 번들러가 사이에 낀다.

  • 번들러. 개발할 땐 파일 수백 개를 모듈로 나눠 쓰고, 배포할 땐 번들러(Vite, webpack, esbuild 등)가 몇 개의 파일로 묶는다. 파일 수백 개를 따로 받으면 요청이 너무 많아지기 때문이다. Vite 는 개발 중엔 브라우저의 ES 모듈을 그대로 쓰고, 배포할 때만 묶는다.
  • 앱도 같다. 학창시절 다이어리(Expo · React Native) 코드도 전부 import로 쓰지만, Metro 라는 번들러가 하나로 묶어서 앱에 넣는다.
  • 서버(Node.js)는 두 방식이 섞여 있다. Node 는 원래 require()를 쓰는 CommonJS 방식이었고, 나중에 ES 모듈을 지원했다. package.json에 "type": "module"이 있거나 파일이 .mjs면 ES 모듈로 읽는다. bamti-bomb 서버는 require()를 쓰는 CommonJS 다.

비프리 게임은 파일이 두 개라 클래식 스크립트로 충분했다. 범퍼카는 Three.js 와 그 부품(모델 읽기, 뼈대 복사)이 서로 import 하는 구조라 모듈이 아니면 쓰기 어려웠다. 그 대가가 "더블클릭으로 안 열린다"였고, 그래서 실행.bat과 작은 서버가 생겼다. 같은 자바스크립트라도 type="module" 한 줄이 실행 환경까지 바꾼다.

이어서 적을 것

  • 범퍼카 2026 — 이 차이를 처음 겪은 프로젝트
  • CORS — 출처, 사전 요청(preflight), 그리고 그림 요청은 왜 예외인가
  • 번들러는 무엇을 하나 — 묶기, 트리 셰이킹, 코드 나누기
